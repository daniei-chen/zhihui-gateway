# 已知缺口：上游的「等多久」被丢掉了

> 调查日期：2026-11-15
> 状态：**未实现**。本文只记录调查结果与实现路径，供下一轮直接动手。

## 一句话

上游在限流/排队时会告诉客户端「等多久」，**网关拿到后把它丢了**，
只回一句「上游暂时不可用，请稍后重试」。

## 证据链

**上游确实会给出等待时间**（2026-11-15 从上游代码确认）：

- 排队响应有固定的标记与字段：业务码 `6020`，字段
  `estimated_wait` / `estimatedWait` / `retry_after` / `retryAfter` /
  `wait_seconds` / `waitSeconds`，单字段上限 7200 秒（超过按脏数据丢弃）。
- 上游把解析出的时长映射成 **`Retry-After` 响应头**下发。

**网关这边没有接**：

- 全仓搜索 `retry_after`，命中的都是**网关自己产生**的响应
  （预算错误、密钥核对、容量保护），**没有一处读上游的响应头**。
- 上层能拿到的只有**异常对象**，而那个异常**不带等待时间字段**。
- 最终对外文案固定为「上游暂时不可用，请稍后重试」+ 一条提示。

## 为什么这不只是「少个字段」

客户端的退避库在没有 `Retry-After` 时只能自己猜：常见默认是立刻重试或固定 1 秒。
**而真实的等待可能是几十秒到几分钟。** 于是它在窗口内反复撞，越撞越远。

同一形状已经在本仓库里出现过两次，都修过了：

| 位置 | 修法 |
| --- | --- |
| 限流（网关自己产生的 429） | 已带 `Retry-After` + 体内 `retry_after_seconds` |
| 预算不足 | 已有 `retry_after` 字段，且注释写明「头透传不稳，写进体」 |

**只有「上游返回的等待时间」这一路还是断的。**

## 实现路径（四步，缺一不可）

1. **底层请求处**读 `resp.headers.get('Retry-After')`，解析成整数秒；
   非法或缺失按「无」处理，**不要默认成某个数**（默认值会变成假信息）。
2. **异常类型**加一个可选字段把它带上来。这一步不做，后面三步都拿不到值。
3. **上层的错误文案函数**接受这个值；**没有值时不写字段**，而不是写 0。
4. **最终响应**同时写响应头和错误体（延续既有做法：头在反向代理链路上不稳，
   体字段客户端能可靠读到）。

## 安全边界（不能破坏）

对外文案**必须保持脱敏**。上游的原始错误文本里可能带凭据、代理地址、
内部 socket 地址，那条边界是刻意设的，**不能为了透传等待时间把它打开**。

**只透传「等多少秒」这一个数字**，不带上游的原文。

## 验证方式

- 单测：构造带 `Retry-After` 的响应，断言最终对外响应里既有头也有体字段，
  且**不含上游原文**。
- 单测：上游没给这个头时，**对外响应里不该出现该字段**（不能编一个 0）。
- 真机：部署后确认正常推理请求不受影响（这条路径只在错误分支上）。

## 为什么当时没做完

调查用了 8 次调用才把链路摸清（上层拿到的是异常、异常没有该字段、底层才有响应头），
而完整实现要改四处并逐处验证。**在余量不足时动手改四处，风险高于留一份准确的记录。**

这一条不是「以后再说」的托词 —— 四步路径、安全边界、验证方式都已在上面写清，
下一轮可以直接执行。
