# 上游的「等多久」曾经被丢掉（已实现）

> 调查：2026-11-15 · **实现：2026-11-15（v1.2.165）**
> 状态：**已实现**

## 一句话

上游在限流/排队时会通过 `Retry-After` 告诉客户端「等多久」。**网关此前拿到后丢掉了**，
只回一句「上游暂时不可用」。现在会转发它。

## 曾经的断点在哪

- 上层只能拿到**异常对象**，而那个异常**不带等待时间字段**。
- **只有最底层的请求处**才看得到响应头。
- 处理上游错误的那个分支里，**body 原样透传、响应头没有人接**。

结果：客户端只知道「出错了」，不知道「等多久」，退避库按默认值猜（常见 1 秒），
**而真实等待可能是几十秒。于是它在窗口内反复撞，越撞越远。**

同一形状此前已经修过两次（网关自己产生的限流、预算不足），**只剩「上游返回的」这一路断着。**

## 上游侧的证据（当初为什么确定它会给）

- 排队响应有固定标记：业务码 `6020`。
- 等待字段族：`estimated_wait` / `estimatedWait` / `retry_after` / `retryAfter` /
  `wait_seconds` / `waitSeconds`。
- 单字段上限 `7200` 秒，超过按脏数据丢弃。
- 上游把这些时长映射成 **`Retry-After` 响应头**下发。

**当初为什么没一次做完**：摸清这条链跑了八次往返，而当时那轮的余量已经不多。
在余量不足时改四处并逐处验证，风险高于留一份准确的记录 —— 记录里带着落点、
取舍与验证方式，下一轮才能直接执行。这一条不是「以后再说」的托词，
它确实在下一轮被照做完了。

## 现在的做法

| 步骤 | 落点 |
| --- | --- |
| 读上游响应头 | `_upstream_retry_after()` |
| 解析与可信度判断 | 同一函数：只认整数秒、上限两小时、拿不到返回 `None` |
| 转发 | 上游错误分支里**响应头 + 错误体字段双写** |

**头 + 体双写的理由**：响应头在反向代理链路上透传不稳（仓库里既有结论），
而错误体字段任何 OpenAI 兼容客户端都能原样读到。**两个都写，谁通就用谁。**

## 两个刻意的取舍

**只认整数秒，不解析 HTTP-date。** 规范允许日期形式，但上游从不用它；
为那种形式写一套日期解析，只会多出一条没人验证的路径。

**拿不到就不写字段，而不是写 0。** 一个假的等待时间比没有更糟 ——
客户端会照着它去撞。超过两小时按脏数据丢弃（与上游侧同一口径）。

## 安全边界（保持）

对外文案仍然**脱敏**：上游原始错误文本里可能带凭据、代理地址、内部 socket 地址，
那条边界是刻意设的。**只透传「等多少秒」这一个数字**，不带上游原文。

上游若已经给出自己的 `retry_after_seconds` 字段，**保留它的值**，不覆盖成头部那个。

## 验证

- 单测覆盖六种输入：整数、带空白、零、缺失、非数字、日期形式、负数、超上限、
  恰好等于上限、读头失败。
- 边界值 `7200` 必须被保留（不能被上限误杀）。
- 真机：部署后确认正常推理不受影响（这条路径只在错误分支上）。
