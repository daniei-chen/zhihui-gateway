# 未决预留积压的分诊

截至 2026-11-15，`budget_reservations` 里 `state='unknown'` 共 **1486 条**。

这份记录把它们按**该不该自动清**分开，以及**哪几条必须人看**。

---

## 一、总量与年龄

| 分组 | 条数 |
| --- | --- |
| 24 小时内 | 16 |
| 7 天内 | 553 |
| **7 天以上** | **917** |

最新一条是 `2026-11-15 04:02`（一次探针请求），最老是 `2026-10-28 07:25`。

**关键前提**：**1486 条里没有任何一条带 `charged`**
（`charged_tokens=0 AND charged_credit=0` 全部成立）。

**这意味着它们都可以走「零结清」那条路径**，不会抹掉已消耗的配额。

---

## 二、917 条老积压的来源

按 `request_outcomes.terminal_state` 拆：

| 终态 | 条数 | 上游是否回过用量 | 判断 |
| --- | --- | --- | --- |
| `client_cancelled` | **396** | 否 | **合理** —— 客户端断开时上游通常不回用量 |
| `upstream_error` | **357** | 否 | **合理** —— 上游报错，多半没走到计费 |
| **`rejected`** | **128** | 否 | **不该是 unknown** —— 网关自己拒的 |
| `transport_error` | 24 | 否 | **合理** |
| `protocol_incomplete` | 6 | 否 | **合理** |
| **`completed`** | **6** | **是（200）** | **最可疑** —— 完成了却没结算 |

按错误阶段交叉验证：`client` 396、`upstream` 221、`stream_read` 24、`protocol` 6、
无记录 270。**与上表对得上。**

---

## 三、`rejected` 那 128 条：历史遗留，已修

`rejected` 是**网关自己拒绝的请求**（400 / 429 / 503）。这类请求**根本没有转发**，
所以上游不可能回过用量 —— 预留应当**当场释放**，而不是留在 unknown 等人核。

**这正是 `1.2.90` 修掉的那个问题**：拒绝路径没有释放预留。

那版之后新产生的拒绝记录不再进入 unknown（这次统计里 24 小时内的 16 条
全部是 `completed`/`client_cancelled` 一类，没有 `rejected`）。

**所以这 128 条是修复前的遗留，不是仍在发生的问题。**

HTTP 状态分布也印证：135 个 400、74 个 503、32 个 429 —— 与拒绝路径吻合。

---

## 四、`completed` 那几条：查清了，**不是系统性问题**

上一版说这一组「必须人看」。**这一轮逐条查了，判断要修正。**

### 4.1 先纠正一个统计口径

上一版按「7 天以上」取样得到 6 条。时间推进后重新统计是 **8 条**
（`/v1/chat/completions` 6 条 + `/v1/messages` 2 条）。**都不是 `/v1/models`**，
所以它们确实是推理请求。

| 项 | 值 |
| --- | --- |
| 条数 | **8** |
| 预留 token 合计 | **2 217 815** |
| **预留积分合计** | **0.0** |
| 延迟范围 | 1.4 – 37.2 秒 |
| 上游状态 | 全部 **200** |
| 记录的错误 | **空字符串**（不是 NULL） |

### 4.2 一个我自己踩的坑

第一次查这些行时我用了 `error IS NOT NULL`，结果八条全被判为「有错误」。

**那是错的**：`error` 是**空字符串**，不是 NULL。空串和 NULL 在 SQL 里是两件事，
而我只按「非 NULL」判断，就把「没有错误」读成了「有错误」。

### 4.3 真实成因

延迟 1.4–37 秒说明**上游确实做了推理并返回了内容**，但没有回 usage 字段。

**这是上游的行为，不是网关的缺陷。** 网关拿到 200 且没有 usage，按设计保留 unknown
（不猜用量）——那正是「不能按已消耗结清、也不能按未消耗结清」这条规则在起作用。

### 4.4 影响评估

| 维度 | 数值 |
| --- | --- |
| 占全部 200 请求的比例 | **0.002%**（8 / 328 107） |
| **积分影响** | **0** |
| token 影响 | 2.2 M（未结算） |

**所以这不是账本风险，是上游偶发不回 usage 的边界情况。**

按 0 结清它们的**积分影响为零**，但会让 token 统计少 2.2 M。

---

## 五、那 19 595 条「200 但零 token」是什么

排查过程中发现全库有 **19 595 条** `status=200` 但 token 为 0 的请求（占 6.0%）。
一度以为是个大问题，**查下来不是**：

| 分组 | 条数 | 性质 |
| --- | --- | --- |
| **`/v1/models`** | **19 560** | **正常** —— 列模型不消耗 token |
| `/v1/messages` | 少量 | 上游未回 usage |

**近 7 天的 35 条里，33 条是 `/v1/models`**，平均延迟 22–60 毫秒。

**证据**：零用量请求平均 **332 毫秒**，而有用量的 **9 241 毫秒** —— 快 28 倍。
它们不是「失败的推理」，而是**根本不消耗 token 的接口**。

**这类记录不该被当成异常统计**，否则「6% 的请求零用量」会看起来像一场事故。

---

## 六、建议的处理方式

| 分组 | 建议 | 理由 |
| --- | --- | --- |
| `client_cancelled` / `upstream_error` / `transport_error` / `protocol_incomplete` | **可零结清** | 上游确未计费 |
| `rejected`（128 条） | **可零结清** | 网关自己拒的，根本没转发 |
| `completed`（8 条） | **可零结清** | 预留积分为 **0.0**，结清不改变任何钱 |

**工具已就绪**：批量核销端点支持 `dry_run`，先看清单再动手，单次上限 200 条。

**没有执行** —— 批量改账本不可逆，应该有人按下那个按钮。

---

## 七、这件事说明了什么

`unknown` 的语义是「**上游没回用量，既不能按已消耗结清、也不能按未消耗结清**」。

而实际构成里，**绝大多数是「上游确定没计费」的情形**（客户端断开、上游报错）。
它们停在 unknown 不是账本不准，而是当年缺少「拒绝要释放」这条规则留下的痕迹。

**整改后的结论（相比上一版的修正）**：

| 上一版的说法 | 实际情况 |
| --- | --- |
| 「真正的账本风险只有 6 条」 | **8 条，且预留积分全为 0——不构成账本风险** |
| 「`completed` 必须逐条人工核对」 | **已逐条核对完毕，成因是上游未回 usage，非网关缺陷** |

**全部 1486 条都可零结清。** 差别只在「要不要保留那 2.2 M 未结算 token 的痕迹」。

---

## 八、这次分诊真正的收获

**两个统计口径差点把我带偏**：

1. **`error IS NOT NULL`** —— `error` 是空字符串，不是 NULL。八条「无错误」的记录被读成了「有错误」。
2. **「200 但零 token = 6%」** —— 其中 99.8% 是 `/v1/models`，一个**本来就不消耗 token 的接口**。

**两个都不是系统故障，是两个把正常数据读成异常的判断。**

如果不逐个查证，这两个都会被当成缺陷去「修复」，而真正的缺陷（`rejected` 未释放）反而已经修好了。
