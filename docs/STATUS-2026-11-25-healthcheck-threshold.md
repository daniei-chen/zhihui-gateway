# 巡检的阈值必须来自线上（第 63 轮）

## 1. 一条每天都出现、却毫无意义的警告

巡检连续多天报同一句：

```
warn  3 次流式请求首字节超过 60 秒（最长 87 秒）
```

而线上实际预算是：

```
WB_FIRST_BYTE_TIMEOUT_S=240
```

**那个 60 是个没有出处的魔数。**它既不等于线上超时（240），也不等于
`server/config.py` 里的默认值（60，但那个值线上没用到），更不等于任何
一档配置。

后果很具体：**60 到 240 秒之间给出首字节是正常的**，但每天都被算成警告。
运维看到「超过 60 秒」会以为接近故障，实际还有 3 分钟余量。

## 2. 这是第十八条 pitfall 的第二次发作

`docs/OPS-PITFALLS.md` 第十八条叫「代码里的默认值不是线上值」，当时的例子是：

```
first_byte_s = 60.0          # 代码默认
# 注释说 180
WB_FIRST_BYTE_TIMEOUT_S=240  # 线上
```

**同一个数字，三个地方，三个含义。**那次修的是文档和注释；
这一轮发现**巡检也吃了同一个亏** —— 它直接硬编码了 60。

所以修法不是把 60 改成 240（那还是魔数，下次调配置又会脱节），
而是**从运行中的服务读**：

```bash
unit_env() {
    local value
    value=$(systemctl show "$1" -p Environment --value 2>/dev/null \
        | tr ' ' '\n' | sed -n "s/^$2=//p" | head -1)
    case "$value" in
        '' | *[!0-9]*) printf '%s' "$3" ;;
        *) printf '%s' "$value" ;;
    esac
}
```

## 3. 兜底分支是必需的，不是形式

```bash
case "$value" in
    '' | *[!0-9]*) printf '%s' "$3" ;;   # ← 这一个分支
```

因为下游是算术展开：

```bash
... WHERE v > $((fb_budget * 1000))
```

**`fb_budget` 是空串时这一行会直接报错**，整个巡检脚本挂掉。
而巡检是规范 §5.1 要求的「一条命令给出全局结论」的那个命令 ——
它自己不能因为读不到配置就崩。

这个兜底有测试守着：

```python
def test_unit_env_has_a_non_numeric_fallback(self):
    self.assertIn('[!0-9]', block)
    self.assertIn('"$3"', block)
```

## 4. 前后对照

**改前**：

```
warn  3 次流式请求首字节超过 60 秒（最长 87 秒）
ok 25 项，警告 4 项，问题 0 项
```

**改后**：

```
流式 5637 次：p50 2807ms，p95 8573ms，最长 87320ms（预算 240 秒）
ok    流式请求全部在 240 秒预算内给出首字节

ok 26 项，警告 3 项，问题 0 项
```

**最长 87320ms = 87 秒**，在 240 秒预算内 —— 那 3 条警告从头到尾都是误报。

`ok` 多了一项，`warn` 少了一项，这是同一件事的两面。

## 5. 剩下 3 条警告都是真的

| 警告 | 性质 |
|---|---|
| 1 次内存不足杀进程 | 备份期间的 OOM，已知 |
| 7 次上游无可用账号（503） | 上游侧，运维需充值 |
| `workbuddy_low_accounts` | 2 个账号余额低于 1000 分 |

**这条很重要**：消除误报的价值不在于数字好看，而在于**剩下的数字变得可信**。
以前 4 条里有 1 条永远存在且无意义，人就会开始整体忽略这个列表。

## 7. 本轮还修正了自己上一轮的错误

`docs/ALERT-ROUTING.md` 里我写「steward 的 14 条规则」，列了 15 个名字。

实际是 **16 个规则名**：`steward_rules.py` 里有个三元组循环，
同一个 `Signal(` 调用点展开成 `channel_verification`、`upstream_authorization`、
`pool_capacity` 三条。数 `Signal(` 得到 14，数规则名才是 16。

**我数的是代码里的调用点，写进文档时却当成了规则数。**
参考文档写错比没有更糟 —— 下次有人照着这份清单判断「哪些会发邮件」，
他会漏掉 `upstream_authorization`（上游授权失败，3 次触发）。

## 8. 一条可以推广的做法

**判警告用的阈值，凡是从配置来的，就不要在检查工具里重写一遍。**

`deploy/preflight-gate.py` 和 `deploy/verify-runtime-config.py` 已经是这个思路
（用真实的 systemd 环境去校验 schema）。这一轮把 `healthcheck.sh` 也纳入同一条线。

下一个候选项：巡检里还有多少这样的魔数？

```bash
grep -nE '[^a-zA-Z_][0-9]{2,}' deploy/healthcheck.sh
```

值得单独查一轮 —— 但不在本轮做，因为规范说一次只动一件事。
