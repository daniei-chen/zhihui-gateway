# v1.5.78：回滚演练暴露的真实缺陷（第 38 轮）

## 1. 为什么要做回滚演练

规范 §3.5 写着「任何一步验证不通过：`release.py rollback`」。这条兜底手段从我接手以来
**一次都没有真正执行过**。

这很危险：如果回滚本身有问题，出事时会掉进更深的坑 —— 而发现问题的最好时机，
是系统还健康的时候。

## 2. 演练设计

选在流量较低的时段，走完整链路，全程用滚动中继兜住：

```
1) release.py rollback          指针 → v1.5.76
2) rollout-rolling.sh v1.5.76   重启，验证服务真的在跑旧版
3) release.py activate v1.5.77  指针 → v1.5.77
4) rollout-rolling.sh v1.5.77   重启，恢复
```

**风险可控**：每次重启都有中继重试覆盖 6 秒空窗；且两步都是刚验证过的路径。

## 3. 演练结果：能力可用，但有一处会误导

**回滚本身工作正常：**

| 步骤 | 结果 |
|---|---|
| `rollback` 后指针 | `v1.5.76` |
| `rollout-rolling.sh v1.5.76` 后 `/api/release` | `v1.5.76`，`source_commit=e8f1383` |
| 该窗口 5xx | **36 请求 / 0 个** |
| 切回后 `/api/release` | `v1.5.77`，`source_commit=dbbb8cc` |
| 两次切换合计 | **119 请求 / 0 个 5xx** |

## 4. 但演练当场暴露了一个缺陷

执行 `rollback` 之后、重启之前，我查了一次：

```
== rollback：v1.5.77 → v1.5.76 ==
   **下一步必须在宿主执行**：sudo systemctl restart workbuddy-web

指针：v1.5.76
/api/release：{"release_id":"v1.5.77","version":"1.5.77", ...}
```

**指针已经切了，服务还在跑出故障的那个版本。**

这不是实现疏漏 —— 指针切换与进程重启分离是**刻意设计**：重启要 sudo、要配合中继重试，
而 `release.py` 只碰文件与指针，不碰进程。

**问题在于提示的分量。**命令返回 `0`（成功），输出里只有一行「下一步必须在宿主执行」。
出故障时人处于紧张状态，看到「成功」就往下走，很容易跳过这一行。
**而跳过它的后果是：以为回滚了，实际故障继续。**

## 5. 改法

```
== rollback：v1.5.78 → v1.5.77 ==

  ** 注意：只切了指针，服务还在跑旧代码。回滚尚未生效。 **

  必须立刻执行下面这条，否则故障会继续：
      cd /opt/workbuddy-manager/deploy && sudo ./rollout-rolling.sh v1.5.77

  然后验证版本真的变了：
      curl -s http://127.0.0.1:7866/api/release
  返回的 version 应当是 1.5.77。
  如果仍是回滚前的版本，说明服务还没重启。
```

三处变化：
1. **「回滚尚未生效」** —— 直接否定「已经成功了」的错觉
2. **给出可直接粘贴的命令**（含绝对路径与目标版本），不用现场拼
3. **给出验证方法** —— 一条命令就能确认版本到底变没变

## 7. 这一轮的价值

**不是「修了一个文案」，是「在还来得及的时候发现了兜底手段会骗人」。**

如果没有这次演练，第一次真正需要回滚时，很可能就是线上正在出故障的时候 ——
那时才发现在「回滚成功」之后服务还跑着坏版本，代价不是几分钟的调试，而是故障时长的延长。

**演练的成本是 119 个请求的两分钟；不演练的代价是故障时的一次误判。**

## 8. 顺带确认的事

- **`release.py rollback` 的路径检查是可用的**：`.previous` 为空、回滚目标目录不存在，
  都会明确报错而不是静默失败
- **`rollout-rolling.sh` 要求指针已指向目标版本**，所以回滚必须「先 rollback 再 rollout」，
  顺序反了会被它拦住 —— 这个设计是对的
- **两次切换合计 119 个请求、0 个 5xx**，第 19、20 个真实流量窗口同样零中断
