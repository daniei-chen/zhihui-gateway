# v1.5.86：巡检补上「配置会不会被拒」（第 56 轮）

## 1. 规范说巡检应该给全局结论

规范 §5.1：

> **`./healthcheck.sh`** —— 一条命令给出全局结论（服务、版本一致性、反代接线、
> 页面、24 小时错误率、磁盘、数据库）。

上一轮查清 2026-11-23 那次 8 分钟崩溃重启的原因：**配置与代码不匹配**。
而在这份「全局结论」里，**没有任何一项**能看出「当前配置会被正在运行的版本拒绝」。

也就是说：那次故障的唯一成因，恰好是巡检的盲区。

## 2. 补的两项

### 2.1 配置校验

```bash
if verify-runtime-config.py "$current" workbuddy-web; then
    pass "配置校验通过（$(basename "$current")）"
else
    broken "当前配置会被 $(basename "$current") 拒绝：..."
fi
```

**报 `FAIL` 而不是 `warn`。**区别很重要：

| 级别 | 含义 | 这次为什么不用 |
|---|---|---|
| `warn` | 值得关注，但服务在跑 | 配置被拒意味着**重启后起不来** |
| `FAIL` | 必须处理 | 现在能跑是因为还没重启 |

报 warn 会让它混进「3 次首字节超过 60 秒」那一堆里，而它的后果完全不是一个量级。

### 2.2 发布树字节码残留

```bash
stale=$(find releases -maxdepth 3 -name __pycache__ -type d | wc -l)
```

上一轮踩过：检查工具 import 发布树代码时会生成 `__pycache__`，而发布树完整性校验
**拒绝任何 `__pycache__`**，`seal` 直接失败：

```
REJECTED: 发布树里有 __pycache__：.../releases/v1.5.85/server/__pycache__
```

那一轮是手工 `ls -d releases/*/server/__pycache__` 查出来的。现在巡检会自己数。

## 4. 巡检仍然只读

这个原则上一轮刚学过：**检查工具绝不能改变被检查对象。**

新代码里唯一的 `rm` 是删它自己建的临时文件：

```bash
rm -f /tmp/hc-config.$$
```

并加了一个测试守住 —— 用正则扫脚本里所有 `rm -rf` / `rm -f`，**除了带 `hc-` 的都算违规**：

```python
dangerous = [line for line in SOURCE.splitlines()
             if re.search(r'\brm\s+-[rf]', line) and 'hc-' not in line]
self.assertEqual(dangerous, [], '巡检里出现了删文件的动作')
```

## 6. 一个连续三轮的模式

第 54 → 55 → 56 轮其实是同一件事的三个阶段：

| 轮次 | 做了什么 |
|---|---|
| 54 | 日志考古发现 8 分钟崩溃重启这件事 |
| 55 | 加 `verify-runtime-config.py`，发布时拦截 |
| 56 | 把它接进巡检，平时也能看见 |

**第 55 轮只解决了「发布时」，没解决「平时」。**如果配置是在两次发布之间被改坏的
（drop-in 随时可以改），发布前检查帮不上——那时根本没有发布动作。

巡检补上之后，这两条路都覆盖了。
