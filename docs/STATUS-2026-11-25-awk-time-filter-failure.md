# 一次让「交叉核对」失效的 awk 错误（第 26 次测量工具怀疑）

## 1. 发现过程

发布 v1.5.94 后做双源核对，我用的命令是：

```bash
awk -v s="2026-11-25T19:45" -v e="2026-11-25T19:57" \
  '$4 ~ /\[/ { t=substr($4,2); if (t>=s && t<=e && $7 ~ /^\/v1\// && $9 ~ /^5/) c++ }' \
  /var/log/nginx/access.log
```

结果：`v1 requests=6003  5xx=8`。

而数据库同一时段只有 **29 条推理请求、0 个 5xx**。

差了 200 倍。这个矛盾必须查清 —— 如果真有 8 条是我们自己的 5xx，那是 P0。

## 2. 那 8 条 502 是什么

把命中的行打出来：

```
183.167.146.132 - - [25/Nov/2026:13:29:05 +0800] "POST /v1/chat/completions" 502 130 "-" "deepseek-harness/0.2.2-rc.5 ..."
183.167.146.132 - - [25/Nov/2026:16:09:48 +0800] "POST /v1/chat/completions" 502 130 "-" "deepseek-harness/0.2.2-rc.5 ..."
183.167.146.132 - - [25/Nov/2026:17:20:40 +0800] "POST /v1/chat/completions" 502 130 "-" "deepseek-harness/0.2.2-rc.5 ..."
```

**时间全是 13:29、16:09、16:10、17:20 —— 都早于 19:45 的部署。**

## 3. 根因：字符串比较，两种时间格式

nginx 的时间是 `[25/Nov/2026:19:55:33 +0800]`，`substr($4,2)` 取出：

```
25/Nov/2026:19:55:33
```

而我传的边界是：

```
2026-11-25T19:45
```

awk 做的是**字符串比较**，逐字符比：

```
'2' vs '2'  → 相等
'5' vs '0'  → '5' > '0'  → 结果为 true
```

所以 `t >= s` **恒为真**。同时 `t <= e` 恒为假（因为第一个不同字符就决定了大小），

两个条件一与，**结果永远为假** —— 一条都不该匹配。

但命令输出了 6003 和 8。这说明在某些行上 `t <= e` 也意外成立（比较在更靠后的字符才分出胜负时），

总之这次过滤既不是「全选」也不是「全不选」，而是**不可预测的一部分**。

**一个不可预测的过滤器比没有过滤器更糟**：它会给出一个看起来很具体的数字。

## 4. 更严重的问题：之前几次的「交叉核对」也失效了

我在 v1.5.91 / v1.5.92 / v1.5.93 的发布说明里写过：

> 同一时段用两个独立数据源交叉核对（网关自己的请求记录、服务器访问日志），都是 0。

用的就是同一个 awk 模板。既然过滤条件是坏的，那几次的「nginx 也是 0」

**不是一个有效结论，只是恰好撞上了全假的分支**。

真正有效的只有数据库那一侧。**我把一个失效的工具当成了第二证据。**

## 5. 修正后的核对

把边界改成 nginx 自己的格式：

```bash
awk -v s="25/Nov/2026:19:45" -v e="25/Nov/2026:19:57" \
  '$4 ~ /\[/ { t=substr($4,2,20); if (t>=s && t<=e && $7 ~ /^\/v1\//) { n++; if ($9 ~ /^5/) c++ } }' \
  /var/log/nginx/access.log
```

结果：

```
v1 requests=37  5xx=0
```

37 个 `/v1/` 请求。数据库说 29 条推理请求 —— 差 8 条是 `/v1/models` 这类非推理端点，

它们被数据库的 `protocol != 'http'` 条件排除，但确实走了 nginx。**两个数对得上。**

这次才是真的零中断。

## 6. 修正后做了两个对照组

修好不等于对。用两个边界反过来验证过滤器真的在工作：

| 对照组 | 边界 | 期望 | 实际 |
| --- | --- | --- | --- |
| 不可能匹配 | `25/Nov/2026:99:99` | **0** | **0** ✓ |
| 全天 | `25/Nov/2026:00:00` ~ `23:59` | 一个很大的数 | **6,011** ✓ |
| 真实窗口 | `25/Nov/2026:19:45` ~ `19:57` | 几十条、5xx 为 0 | **43 条 / 0 个 5xx** ✓ |

第二个对照组还有个附带价值：全天的 6,011 与错误命令先前给出的 6,003 几乎一致 ——

这反证了那条错误命令实际上把**全天**都算成了窗口，与我推断的「过滤失效」吻合。

**一个不值得信任的过滤器，也能通过「看起来合理」的检验。真正能验证它的是让它去算一个已知答案。**

## 6. 教训

**验证一个数字之前，先验证产生它的那个过滤器。**

判断过滤器有没有生效，最省力的办法是**用一个不可能匹配的边界跑一遍**，

看它是否真的返回 0。上面那条命令如果先用 `s="9999"` 试一次，立刻就会暴露问题。

还有一条更基本的：

**「两个数据源一致」只有在两个数据源各自都被验证过之后才算数。**

否则只是同一个错误被独立地相信了两次。
