# v1.5.82：中继的重试窗口不够长（第 48 轮）

## 1. 从一行日志看出来

第 47 轮查清了「29 次不明重启」其实是部署。但当时留了一个问题：
**29 次重启里，中继漏掉了 1 次。**

这一轮去翻中继自己的日志，找到了那次的完整过程：

```
11-24 19:19:35  200 OK                    183.167.146.132
11-24 19:19:39  503 Service Unavailable   175.2.132.122   ← 网关停了
11-24 19:19:40  502 Bad Gateway           175.2.132.122   ← 重试 1
11-24 19:19:42  502 Bad Gateway           175.2.132.122   ← 重试 2
11-24 19:19:44  502 Bad Gateway           175.2.132.122   ← 重试 3（进程已 Started！）
11-24 19:19:54  200 OK                    175.2.132.122   ← 才成功
```

**中继确实在重试，也确实最终成功了。但它放弃了 10 秒，中间那段无人保护。**

## 2. 关键发现：「进程起来」不等于「能服务」

对照 systemd 的日志：

```
19:19:39  Stopped workbuddy-web.service
19:19:39  Started workbuddy-web.service
19:19:44  python3: Started server process      ← 进程起来了
19:19:54  （第一条 200）
```

**从 19:19:44 到 19:19:54 还有 10 秒。**这段是签名校验 + 应用初始化。

而重试参数是：

```python
STARTUP_RETRIES = 4
STARTUP_RETRY_DELAY = 1.5
```

退避是 `1.5 × (attempt+1)` = **1.5, 3.0, 4.5 秒，累计 9 秒**。

**9 秒的窗口在 19:19:44「进程起来」那一刻就用完了。**后面 10 秒的初始化，
没有任何重试保护。那条 503 就是这么来的。

## 3. 改法

```python
STARTUP_RETRIES = 6      # 原来 4
STARTUP_RETRY_DELAY = 1.5
```

累计等待变成 **1.5 + 3 + 4.5 + 6 + 7.5 = 22.5 秒**，覆盖实测的 15 秒恢复时间，
留 7.5 秒余量。

### 代价

后端真的挂了时，要等 22.5 秒才报错（原来 9 秒）。

**可以接受**，因为这段代码只重试 `ConnectError` / `ConnectTimeout` —— 那是连接都没建立，
说明后端完全不可达。不可达 22 秒，确实该判定失败了。

而且这段逻辑本身有明确的边界（代码注释里写着）：**只重试 connect 阶段，进入读取阶段就不再重试**
—— 那时可能已经在生成答案并计费，重放会造成重复计费。

## 5. 实证：重启时打 14 个并发请求

重启网关的同时，向中继的 `/v1/chat/completions` 发 14 个并发请求：

```
result: 14 个全部 401
```

**401 是应用层返回的（缺认证），说明请求成功穿过了中继到达网关。**
没有一个是 502/503 —— 中继没有放弃任何一个。

对照 11-24 那次：**同样 5-6 秒的空窗，有 3 个 502。**

## 6. 这次验证的局限（必须写清楚）

**我这次重启的空窗只有 6 秒**：

```
15:15:53  Stopped
15:15:53  Started
15:15:59  Started server process     ← 6 秒
```

**6 秒在旧的 9 秒窗口内。**所以严格说，这次 14/14 成功**不能证明**「22.5 秒修复了 15 秒的场景」
—— 它证明的是「在当前的实际恢复速度下，中继不漏请求」。

11-24 那次是 15 秒（进程 19:19:44 起来，19:19:54 才接住）。
**修复针对的正是那种情况，而那种情况不可控地难以复现。**

**这一条没有在真实 15 秒场景下验证过。**我把它记下来，而不是含糊过去。

## 7. 顺带修的一个测量错误

查这条记录时我写了：

```sql
WHERE ts BETWEEN strftime('%s','2026-11-25 19:19:20','utc','-8 hours') ...
```

结果查出来的是 11-19 的数据。原因是把 `'utc','-8 hours'` 两个修饰符叠加用了 ——
`'utc'` 已经把本地时间转成 UTC，再减 8 小时就跑到前一天去了。

正确写法是 `strftime('%s','2026-11-25 19:19:20','utc')`。

**这是第 6 次「测量工具出错」。**前五次记在 `OPS-PITFALLS.md` 第十三条。

值得记下来的是：这次的错误方向是**把昨天的数据当成今天的**，然后差点得出
「今天有 8 个 5xx 且都是重启造成的」这个错误结论。
