### 四项实质性修复

**1. 出口归因退避（`egressBackoff` / `rotateEgressBackoff`）**

传输层失败后的轮转退避：`base · 2^n` 封顶 `cap`，带 ±25% 抖动。

**为什么重要**：传输层失败（连接被重置、DNS 抖动）如果立刻换账号重试，
会在上游已经不稳的时候再压一层。指数退避 + 抖动是为了避免所有实例同时重试。

**2. 排队等待识别（`IsQueueWaiting` / `ParseQueueWait`，issue #416）**

上游在排队时会返回固定的文案/字段，这里解析出预计等待时间，
让客户端知道该等多久，而不是盲目重试。

**为什么重要**：这正是「客户端反复重试」的一个来源 —— 它不知道上游在排队。
单字段有上限保护，异常值按脏数据丢弃，不会把离谱的数字当 `Retry-After`。

**3. tools 描述净化（`sanitizeTools`，issue #395）**

`sanitizeMessages` 只覆盖 `messages`，**`tools` 数组原样出站**。
而 Claude Code / Codex 这类客户端的 tool description 与 system prompt 同源，
都是固定模板句 —— **上游按逐字黑名单拦截，模板句正是高发区**。

这里对 `description` 做与正文相同的最小改写，**但不动 `name`** ——
名字参与客户端与上游的工具匹配，改一个字符就会让调用对不上。

**4. 429 报告最早的 reset 时间**

让客户端拿到准确的重试时间，而不是自己猜。

## 动这台机器之前该做什么

1. **先备份源目录**（至少 `/opt/workbuddy2api` 整个目录，或只备份 `git diff` 的输出）
2. **导出未提交改动**：
   ```bash
   cd /opt/workbuddy2api && git diff > /path/to/local-changes-$(date +%F).patch
   ```
   未跟踪的目录与文件也要一并处理（`git status --porcelain` 里以 `??` 开头的那些）
3. **确认新容器构建时间晚于源文件修改时间** —— 否则改动等于没进去
4. 重装后再对照本文档的四项修复，逐项确认行为仍在
