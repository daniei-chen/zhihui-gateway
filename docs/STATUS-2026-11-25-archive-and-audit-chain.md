# 归档与审计链：`archive_runs` 是 0 行，但不是缺陷（第 52 轮）

## 1. 引起怀疑的两件事

查库时看到两个互相矛盾的现象：

1. **`archive_runs` 表是 0 行** —— 归档功能一次都没跑过
2. **`request_logs` 最老的数据是 71 天前**（2026-09-14）

如果有人把「保留期 90 天」实现成「到期就删」，那么**19 天后就会开始删对账数据**，
而归档一次都没跑过。这直接违反硬约束「不许删对账数据」。

**所以必须查清楚裁剪到底是删还是归档。**

## 2. 第一层：`_prune_request_logs()` 现在不删数据

```python
def _prune_request_logs() -> None:
    try:
        from . import archiveworker
        archiveworker.notify()      # ← 通知归档，不是删
    except Exception:
        pass
    _prune_side_tables()            # ← 只清侧表
```

**它没有 `DELETE FROM request_logs`。**删除动作被移交给了 `archiveworker`，
而那个模块负责「先导出、再删」。

**设计是对的。**怀疑解除一半。

## 3. 第二层：`archive_runs` 为 0 是预期行为

`archiveworker.py:109` 的注释直接回答了这个问题：

> `ledger.verify_chain()` 早就存在，但**生产里从来没有被调用过**：
> 它只在 `retention.verify_admin_chain()` 里被用到，而那条路径挂在归档流程上 ——
> **归档按 90 天阈值触发，而库里最老的数据还没到那个年龄。**

**71 天 < 90 天。**所以归档不触发是**正确**的，`archive_runs` 为 0 也**正确**。

## 4. 第三层：那 90 天到了之后会不会安全

这是真正需要担心的：**触发那一刻的行为没人验证过。**

看了 `_check_audit_chain()` 的实现，发现它被**刻意**从归档流程里拆出来了：

> 实测全表 25993 行、断链检测 0.02 秒。归档周期默认 300 秒，
> 这点开销可以忽略，**比「等归档触发」可靠得多**。

也就是说：**审计链校验不再依赖 90 天触发**，每 5 分钟跑一次。这是对的 ——
「等一个 90 天才发生一次的事件来验证安全机制」本身就是设计缺陷。

## 5. 顺手做了一件一直没做的事：独立验证审计链

注释里提到「2026-11-15 手工验过：25993 行、创世 1 个、断链 0」。
但那是**有人去查**才发现的，不是系统自己说的。我用 SQL 独立验一次：

```sql
WITH ordered AS (
  SELECT id, previous_hash, event_hash,
         LAG(event_hash) OVER (ORDER BY id) AS prev_ev
  FROM admin_events
)
SELECT count(*) FROM ordered
WHERE prev_ev IS NOT NULL AND previous_hash IS NOT prev_ev;
```

结果：

| 项 | 值 |
|---|---|
| **断链数** | **0** |
| 缺失创世哈希的行 | **0** |
| 总行数 | **27,087** |
| 首行 `previous_hash` | `000000000000`（标准创世值） |
| 最后一行 | `id=27087`，`event_hash=391f706332c6` |

**从 25,993 行涨到 27,087 行（+1,094），链仍然零断链。**

## 6. 结论

| 疑问 | 结论 |
|---|---|
| 裁剪会删对账数据吗 | **不会**，删除移交给归档流程 |
| `archive_runs=0` 是缺陷吗 | **不是**，71 天 < 90 天阈值，属预期 |
| 90 天后触发会安全吗 | **设计上安全**（先导出再删），且审计链校验已独立成 5 分钟周期 |
| 审计链完整吗 | **是**，27,087 行零断链 |

**这一轮没有改代码，但消除了一条 P0 级别的怀疑。**

「19 天后会开始删数据」这个念头如果不查，下一次它还会冒出来，
而且每次都要重新想一遍。现在结论写在这里。

## 7. 一个仍然存在的风险（不是这轮的）

**归档流程本身从未在生产环境跑过一次完整周期。**阈值到之前无法验证，
阈值到之后才是第一次。这是「只能等」的事情，记在待办里。

如果要在阈值前验证，只能手工用较小的 `max_rows` 跑一次 `run_once()` ——
但那会真的产生归档记录，需要先确认目标目录和回滚方式。
