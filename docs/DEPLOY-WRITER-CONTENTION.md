# 部署时那个「额外写入者」

这份记录回答一个反复出现的部署摩擦：`prepare` 报

```
Rejected: unknown or additional writer blocks first migration
```

以及**它到底是不是看门狗**。

---

## 一、判据是什么

写入者校验要求：**进程列表必须恰好只有主服务一个**。

```
rows = self.inventory.processes()
if [r['pid'] for r in rows] != [identity['pid']]:
    raise Rejected('unknown or additional writer blocks first migration')
```

而「算作写入者」有四条判据：

| 判据 | 说明 |
| --- | --- |
| 命令含写入者标记 | 迁移脚本的名字出现在 cmdline |
| 命令含辅助脚本名 | 同上 |
| **cwd 在 `/opt/workbuddy-manager` 或 `releases/` 下** | 最容易误伤的一条 |
| **以可写方式打开数据目录下的文件** | 只读会话被排除（`_wal_coordination_only`） |

---

## 二、第一个假设：是看门狗

看门狗 `zhihui-steward-watchdog.timer`：

| 项 | 值 |
| --- | --- |
| 每轮运行 | 约 20 秒 |
| 间隔 | 60 秒 |
| `prepare` 本身 | 约 20 秒 |

**`prepare` 跑到一半，下一轮就起来了。**

### 修法与效果

`prepare` 期间**暂停 timer**（不暂停 service，在跑的那轮不受影响），
`trap EXIT INT TERM` 恢复。

| 场景 | 结果 |
| --- | --- |
| 修之前 | **4/4 全拒** |
| 修之后（第一次观察） | 重试 1 次通过 |
| 修之后（第二次观察） | **0 拒绝，一次通过** |

---

## 三、第二个假设：还有别的东西 —— **没有找到**

修完之后仍有过一次重试，所以我写了个嗅探脚本，每隔 0.4 秒枚举一次所有匹配判据的进程。

**结果：8 次采样，全部只有主服务自己。**

| 时间 | pid | 说明 |
| --- | --- | --- |
| 08:15:23 … 08:15:46 | 700830 | 主服务，每次都在 |
| 其他 | — | **没有** |

**结论：所谓「额外写入者」就是主服务本身被算成了「额外」** —— 也就是说，
失败时 `identity['pid']` 与 `rows` 里的那个 pid 对不上，而不是真的多了一个进程。

**而那次重试最可能的解释是**：暂停 timer 之前已经在跑的那一轮看门狗的**残留子进程**
（预检进程）还没退干净。`wait_for_watchdog` 等的是「看门狗与预检进程都退出」，
在第二次观察里它等满了 21 秒才放行，那一次就没有拒绝。

**所以这不是两个不同的原因，是同一个原因在不同时机下的两种表现。**

---

## 四、嗅探脚本本身先错了一次

第一次跑，日志是**空的**。

原因：`echo` 忘了重定向到日志文件，输出全被 `> /dev/null` 吞掉了。

**这直接导致我上一轮把这条线索记成「未解决」** —— 其实是工具坏了，
不是没问题可查。

**教训**：一个「什么都没抓到」的工具，先怀疑工具。

---

## 五、现在的位置

| 项 | 状态 |
| --- | --- |
| 暂停 timer 的修复 | **有效**（最近一次 0 拒绝） |
| 真正的原因 | 主服务与记录不一致，或看门狗残留子进程 |
| 是否完全消除 | **不确定** —— 只在两次部署上观察过 |
| 是否需要继续修 | **暂不需要** —— 失败时重试一次能过，且日志会给原因 |

**如果要彻底消除**，正确的方向是让 `wait_for_watchdog` 在返回前确认
**预检子进程也真的退了**，而不只是查那三个名字。这件事没有做，
因为当前成本（偶尔重试一次）远小于改错的风险。
