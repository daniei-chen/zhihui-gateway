# 同类竞品调研：该学什么、不该学什么（第 71 轮）

规范 §8 把「审计 GitHub 调研同类竞品，完善我们的智汇网关」列为完成条件之一。
这份文档是那件事的产出。

**它不是功能对照表。** 功能对照表的结论永远是「我们缺得更多」，
照着补就是把有限的维护能力摊薄到别人的战场上。
这里只回答一个问题：**在智汇网关这个具体场景里，哪些差距是真的，哪些不是。**

## 1. 调研对象与来源

| 项目 | 定位 | 看的是 |
|---|---|---|
| LiteLLM | 最广泛部署的开源 AI 网关 | 仓库 README 的顶层能力声明（4.1 万字，取其自述的四大能力） |
| Portkey | 开源网关 + 托管治理平台 | 第三方对比文章里的定位描述 |
| Kong AI Gateway / Apache APISIX | 通用 API 网关的 AI 插件 | 同上 |

**只看仓库自述和定位，不看功能清单。** 功能清单会让人误以为功能数量是价值。

## 2. LiteLLM 自述的四个顶层能力

读它的 README，真正的顶层能力只有四条：

1. **Unified API** —— 一套接口对接 100+ 家模型厂商
2. **Drop-in OpenAI compatibility** —— 换厂商不用改代码
3. **Production-ready gateway** —— 虚拟密钥、花费追踪、护栏、负载均衡、管理面板
4. **8ms P95 latency**

## 3. 逐条对着我们的场景看

### 3.1 「100+ 家厂商」——不是我们的战场

这是 LiteLLM 的护城河，也是它所有复杂度的来源。它要处理的是
「同一个请求在 OpenAI / Anthropic / Bedrock / Vertex 之间语义不一致」。

**智汇网关的场景不是这个。** 我们的上游是**一个**平台（WorkBuddy）的
**23 个账号**。真正的问题不是「厂商之间的语义差异」，而是：

- 哪个账号还有余额
- 哪个账号正在冷却
- 这个请求该记到谁的账上
- 账号池什么时候会枯竭

**这不是「支持更多厂商」能解决的问题，是运营深度问题。**
如果照 LiteLLM 的路子去做多厂商聚合，等于把精力花在一个我们没有的场景上。

**结论：不做。** 这条此前审计就反对过，这次从源码自述里得到了印证。

### 3.2 「虚拟密钥 + 花费追踪」——我们已经有，而且更深

LiteLLM 的 spend tracking 是「按 key / 按模型记账」。
我们有 `usage_daily`、`usage_events`、`request_logs`、`forwarding_events`、
`budget_reservations`，还有**逐日对账验证**：

```
request_logs 4,735 请求  prompt 738,380,286  completion 3,419,838
usage_daily              prompt 738,380,286  completion 3,419,838
```

两边一个 token 都不差。这个深度 LiteLLM 的 README 里没有承诺。

**结论：这块不落后，不用补。**

### 3.3 「护栏（guardrails）」——明确不做

LiteLLM 的 guardrails 是内容审核：PII 检测、敏感词、prompt 注入防护。

**我们的上游是单一平台的账号池，内容审核在那一边。**
在网关这层再加一道，只会增加延迟和误拒，而不会增加任何安全性 ——
真正的越权风险在「谁能拿到 key」，那由鉴权和 key 管理解决，不由内容过滤解决。

**结论：不做。** 这也与此前审计的判断一致。

### 3.4 「8ms P95」——不是我们的指标

LiteLLM 是纯转发层，可以谈毫秒级延迟。
我们的每个请求都要等**上游 LLM 生成**，P95 由上游决定（实测 31 秒量级）。

在 LLM 推理场景里宣传网关自己的 8ms 没有意义 —— 用户感知的是
「第一个字什么时候出来」，那是上游的事。

**我们该关心的是另一件事：上游慢的时候，用户能不能知道在等什么。**
第 69 轮把超时类型记进日志、第 63 轮把「首字节慢」的判断改成以实际配置为准，
都是在做这件事。这才是这个场景里真实的延迟问题。

**结论：不追这个指标。**

## 4. 那什么是我们该做的

从上面的对照反推，我们的差异化只有一条，但它很深：

> **把一个账号池运营得足够透明，让任何异常都能被看见、被归因、被对账。**

具体到已经做过的：

| 能力 | 状态 |
| --- | --- |
| 发版不打断在途调用（滚动中继） | 已交付，30+ 次发版窗口零 5xx |
| 五语言控制台 | 已交付 |
| 逐日对账（请求记录 ↔ 用量表，一个 token 不差） | 已交付并验证 |
| 上游超时按类型可区分 | 第 69 轮 |
| 账号余额低、额度将满主动通知 | 第 60/61 轮 |
| 健康巡检一条命令给全局结论 | 已交付，8 秒 |

**这些 LiteLLM 都没有，因为它们不是它的问题。** 反过来，它有 100+ 厂商，
因为我们不需要。

## 5. 调研过程中被排除的三个候选

按规范 §2.1「不要硬凑改动」，这三个查完之后都没做，理由如下。

### 5.1 多阈值配额告警（LiteLLM 最近加了）

LiteLLM 有 `multi-threshold budget alerts`（50%/80%/95%），我们只有
`QUOTA_WARN_RATIO = 0.8` 一个阈值。

看起来是差距，但查了实际数据：

```
id=55  日额度 200.0  已用 133.05 = 66.5%
id=107 总额度 700   已用 90.95
```

**全站只有 2 个 key 设了额度，且都没到 80%。** 加 50% 和 95% 两档，
在只有一个 key 会触发的地方，多出来的两档没有观测对象。

**等有更多 key 设额度时再做。** 现在做是给一个空房间装三个门铃。

### 5.2 账号池余额下降告警

2026-12-01 起上游积分有效期从 1 个月改为 7 天，池余额可能快速下降 ——
这是上一轮提出的候选。

查了实际趋势：

```
11-23  最小 77,361
11-24  最小 77,523
11-25  最小 78,079
```

**连涨三天。** 因为每日签到 23 个账号各 +100，而实际消耗低于补给。

**现在做这个告警，它永远不会响。** 而一个永远不响的告警，和没有告警的区别是
它还会在真该响的时候被怀疑是不是也坏了。

**等 12-01 政策生效后再观察。** 如果那时出现下降，再做。

### 5.3 告警重复抑制

查了 `operational_alerts`（结构是 `name/since/detail`，一个 name 一行）：

```
workbuddy_low_accounts  自 15:50:33 起活跃 3.3 小时
```

**3.3 小时里只有一行，没有重复告警。** 抑制机制已经在 `name` 是主键这件事上
自然成立了。

**结论：没有需要修的东西。**

## 6. 一句话结论

**竞品的功能多，是因为它要解决的问题多，不是因为它做得更好。**

智汇网关该做的事只有一件：把账号池运营得足够透明。
这件事 LiteLLM 没做，因为它不需要；而我们对它的理解比功能对照表能给出的更深。

照着竞品补功能，得到的是一份更长的功能表和一个更薄的维护能力。
**这一轮调研的最大价值，是确认了三件事不用做。**
