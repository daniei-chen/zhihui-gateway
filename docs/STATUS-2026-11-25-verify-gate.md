# 发布闸门能否拦住坏版本：实测（第 40 轮）

## 1. 为什么查这个

前两轮验证了两个兜底手段：

- **回滚**（第 38 轮）—— 发现提示会骗人，已修
- **备份**（第 39 轮）—— 东西是好的，但只有一份且在同一块盘

还有第三道闸没验过：**`release.py verify`**。它是指针切换前的最后一道门 ——
如果它拦不住坏版本，那么「门禁全绿」就只是自我感觉良好。

## 2. 这道闸做了什么

`cmd_verify` 的流程：

1. **`check_metadata`** —— 版本面一致性
2. **调 `deploy/preflight-gate.py`**
3. **要求 `returncode == 0`**，否则抛「启动门禁未通过 —— 不要切换发布指针」
4. **还要求输出里含「全部通过」**，否则抛「门禁输出缺少「全部通过」，拒绝放行」

**第 4 条是双重保险**：即使 gate 因为某种原因返回 0 却没真正检查，`verify` 也不会放行。
这一条不是装饰 —— 它防的是「闸门静默成功」，那比闸门明确失败更危险。

`preflight-gate.py` 检查的项目：

| # | 检查 | 强度 |
|---|---|---|
| 1 | `manifest.version == 目录名` | 弱（只防写错版本号） |
| 2 | `manifest.release_id == 目录名` | 弱 |
| 3 | **783 个文件逐个 sha256 + 权限位** | **强** |
| 4 | **清单的 Ed25519 签名** | **强** |
| 5 | **`server` + `deploy` 双向闭包** | **强**（多一个、少一个都报） |
| 6 | `writer-capabilities.json` 绑定（哈希、mode、release_id、version） | 中 |

## 3. 实测：四次注入，四次拦住

在 `/tmp/vtest` 复制一份 v1.5.78（**不碰生产**），逐项注入错误：

### 基线（未篡改）

```
== 全部通过，可以切换发布指针 ==
```

### 注入 1：改一个字节

```
[FAIL] 逐文件哈希与 mode: AssertionError: 1 项不符: ['hash:server/main.py']
== 有失败项，不要切换发布指针 ==
```

### 注入 2：多放一个文件

```
[FAIL] server+deploy 双向闭包: AssertionError: 多出 1 项 ['server/stray_file.py'] / 缺 0 项 []
== 有失败项，不要切换发布指针 ==
```

### 注入 3：删掉一个文件

```
[FAIL] 逐文件哈希与 mode: AssertionError: 1 项不符: ['missing:server/operational.py']
[FAIL] server+deploy 双向闭包: AssertionError: 多出 0 项 [] / 缺 1 项 ['server/operational.py']
== 有失败项，不要切换发布指针 ==
```

**两层同时拦住** —— 哈希检查和闭包检查各自独立发现了问题，不是靠单一机制。

### 注入 4：通过 `release.py` 端到端

```
干净副本：release.py exit=0   → == 全部通过，可以切换发布指针 ==
篡改副本：release.py exit=1   → == 有失败项，不要切换发布指针 ==
```

**退出码正确**。这一点必须单独验 —— 如果它拦住了但返回 0，脚本串联时会被忽略。

## 4. 一个测量错误，和三次同类失误

第一次测端到端时我写的是：

```bash
release.py ... 2>&1 | tail -4
echo "exit=$?"
```

拿到 `exit=0`，差点得出「它拦住了但退出码是 0」的错误结论。

**`$?` 是 `tail` 的退出码。**管道会吃掉前面命令的状态。

这和第 32 轮「`LIKE '/v1/chat%'` 查不到就以为没有推理调用」是同一类错误：
**测量工具本身出错，结论却照下**。已记在 `OPS-PITFALLS.md` 第十三条。

正确写法：

```bash
release.py ... > /tmp/log 2>&1
echo "exit=$?"        # 现在拿到的是 release.py 自己的
tail -4 /tmp/log
```

## 5. 结论：这道闸是可靠的

| 项 | 结论 |
|---|---|
| 改一个字节 | **拦住** |
| 多一个文件 | **拦住** |
| 少一个文件 | **拦住** |
| 端到端退出码 | **正确**（失败=1，通过=0） |
| 闸门静默成功的可能 | **被「全部通过」检查堵住** |

**这是三道兜底手段里最健康的一道。**回滚会骗人，备份缺异地，而发布闸门是真的。

## 6. 但它防不了什么

- **防不了「代码本身有 bug 但哈希正确」** —— 它保证的是「这份代码就是我审阅过的那份」，
  不是「这份代码是对的」。后者靠测试用例（1,117 + 245 例）。
- **防不了「清单和文件一起被改」** —— 如果有人能重新签名，闸门会放行。
  这一点靠私钥保管（`/opt/workbuddy-manager/engine/secrets/`）。
- **防不了运行时问题** —— 进程能不能起来、端口能不能绑，它不知道。
  这要靠部署后验证（`/api/release`、五页面、巡检）。

**闸门管的是「完整性」，不是「正确性」。**两者不能互相替代。

## 7. 三道兜底手段的横向对比

| 手段 | 状态 | 缺口 |
|---|---|---|
| 回滚 `rollback` | 可用，**已修提示** | 需两步，不能自动化 |
| 备份 `recovery` | 可用，**sha256 实测一致** | `offsite: false`，无异地副本 |
| 发布闸门 `verify` | **可靠，四次注入全拦住** | 只管完整性，不管正确性 |
