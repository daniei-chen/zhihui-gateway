# 发现但未查完：24 小时内 35 次服务重启（第 46 轮）

## 1. 怎么发现的

这轮本来在查数据库索引和定时任务，都健康。顺手看了一眼日志里的告警分布，发现
`workbuddy_low_accounts` 报了 **35 次**。追它的去重逻辑时，发现告警状态机
（`transition()`）是内存字典，进程重启就会清空 —— 于是去数重启次数。

**数出一个不应该有的数字。**

## 2. 事实

```

```

**按小时分布**（不是集中在部署时段）：

19:56  20:17  20:57  22:49  23:07  08:05  08:23  08:59  09:22  10:24

**除最后几次（13:47 之后是我的部署），前面 29 次的间隔是 12-40 分钟。**

## 3. 已排除的原因

| 推测 | 证据 | 结论 |
|---|---|---|
| 进程崩溃自动拉起 | `NRestarts=0`，每次都是 `Deactivated successfully` + `Stopped` | **不是崩溃** |
| systemd 定期重启 | `RuntimeMaxUSec=infinity`、`WatchdogUSec=0` | **不是 systemd 机制** |
| cron 任务 | root crontab 与 `/etc/cron.d/*` 全部检查，无一提到 `workbuddy-web` | **不是 cron** |
| `kagong-maintenance.sh` | 只重启 `kaogong-api` 和 `nginx` | **不是它** |
| `wanyu-monitor` | grep 无 `workbuddy`、无 `systemctl` | **不是它** |
| `wb-budget-autoreconcile` | 只有 `After=workbuddy-web.service`（依赖，不重启），每天 06:10 跑一次 | **不是它** |
| 手动敲的 | root `.bash_history` 里没有相关命令 | **未见证据** |
| 应用自己重启 | `server/*.py` 里没有 `systemctl restart workbuddy-web` | **不是** |

**每一条都是 `Deactivated successfully` —— 正常的、主动的停止。**不是被杀，是有人叫它停。

## 4. 为什么这件事重要

**每次重启都有约 6 秒空窗**（停旧进程 → 起新解释器 → 校验整份发布签名 → 初始化应用）。

滚动中继能兜住**发版时**的那一次重启 —— 那是我们计划内的，反代已经接好中继。
但**这 29 次不明重启，中继是不是也在兜？**这一轮没验证。

如果中继没兜住，那就是每天 29 次 × 6 秒 = 约 3 分钟的真实不可用时间，
而且**分散在全天**，用「发版窗口零 5xx」这个口径永远统计不到。

**这解释了为什么全天累计有 8 个 5xx，而部署窗口一直是 0。**

## 5. 这一轮没查完的部分

- **谁在调用 `systemctl stop/restart`** —— auditd 没记录（未确认是否启用）
- **中继有没有兜住这些重启** —— 需要对照重启时刻与 `request_outcomes` 的 5xx 时间戳
- **这些重启是否影响真实推理调用** —— 同上

**这是下一轮的第一件事。**

## 6. 一个方法论上的收获

这条线索不是从「系统有故障」出发找到的，是**追一条告警的重复次数**找到的：

```
告警报了 35 次
  → 为什么 35 次？去重逻辑是内存字典
    → 内存字典为什么清空？进程重启
      → 进程重启了 35 次？
        → 对一个只部署了 7 次的日期，这个数字不对
```

**「告警太多」本身可能就是「服务不稳」的症状。**如果只看「告警有没有触发」，
会认为 `low_accounts` 是个运营问题（账号确实只有 2 个），从而完全错过重启这条线。
