# 账号池调度不均衡 — 2026-11-15 观测

**结论**：96 个账号文件里只有 48 个在产生流量，用量最高与最低相差 **228 倍**，
其中一个**余额比第一名还多的账号只被用了 3 次**。

**调度不在智汇仓库里**，在 `workbuddy2api`（Go 程序）内部。这份记录说清现象、
证据和可操作的那部分。

---

## 一、观测到的分布

近 24 小时、按 `account` 分组：

| 指标 | 值 |
| --- | --- |
| 有账号标记的请求 | **8,622** |
| 实际产生流量的账号 | **48** |
| 平均每账号 | **180 次** |
| 最少 | **3 次** |
| 最多 | **685 次** |
| **最多 / 最少** | **228.3 倍** |

前五名：686、592、575、541、502 次。
后五名：3、5、5、6、6 次。

## 二、不均衡不是「账号坏了」

最容易的解释是那 48 个少用的账号失效了。**查过了，不是。**

`state.json` 里这 5 个账号的状态：

| 账号 | disabled | success_count（历史） | err_total |
| --- | --- | --- | --- |
| `c80dbc31` | false | **4,099** | 1 |
| `b7f1ad5f` | false | 1,129 | 1 |
| `b4cdcff1` | false | 900 | 1 |
| `45e09e89` | false | **5,951** | 0 |
| `de91ab54` | false | **6,353** | 11 |

**全部启用、历史成功率极高。** 它们不是坏账号。

## 三、也不是「余额用完了」

`credits` 字段：

| 账号 | credits | 近 24h 使用 |
| --- | --- | --- |
| `c80dbc31` | **4,274** | **3 次** |
| `cedf1312`（用得最多） | 4,146 | **686 次** |
| `b4cdcff1` | 3,091 | 5 次 |

**`c80dbc31` 的余额比用得最多的那个还高，却只被用了 3 次。**

只有一个例外：`b7f1ad5f` 的 `credits` 是 0、`credits_known` 是 false ——
那个不用是合理的。

## 四、也不是权重

96 个账号文件**只有两个顶层键**：`account`、`auth`。

**没有 `weight` 字段** —— 也就是说全部走默认权重，没有人为偏置。

顺便说：`state.json` 里有 **129 个账号条目**，而 `auths/` 只有 **96 个文件**。
多出来的 33 个是孤立状态（文件已删、状态还在），不影响调度。

## 五、所以调度在哪

| 组件 | 它做什么 |
| --- | --- |
| 智汇（Python） | 账号文件读写、权重设置、状态合并 |
| **workbuddy2api（Go）** | **实际挑选账号** |

智汇这边有 `set_account_weight`，**但没有 `pick_account` / `least_used` 这类选择逻辑**。

**换句话说：智汇能"给账号打分"，但真正挑选的动作不在它手里。**

## 六、这意味着什么

**每一半的闲置都是真实的容量浪费。** 48 个账号在扛全部 8,622 次请求，
而另一批余额充足、历史健康的账号几乎没被碰过。

**风险面**：如果那 48 个里有一批同时被限流，可用容量会骤降 ——
而另一半明明在那儿，却没有被用起来。

## 七、可做的与不能做的

### 可以先试的（在智汇侧，零风险）

`set_account_weight` 是可用的。如果 `workbuddy2api` 的调度**尊重权重**，
提高闲置账号的权重就是最直接的干预手段。

**验证方法**：给一个闲置账号设一个明显更高的权重，观察 10 分钟内它的请求数是否上升。

- 上升 → 权重生效，可以按余额批量调
- 不变 → 那个调度不读权重，这条路走不通

**这一步我没有做** —— 它会改动生产账号的调度行为，需要你确认。

### 不能做的

**不要在没有验证的情况下批量改权重。** 如果调度确实读权重，一次调错会让
几十个账号的负载同时倾斜，而回滚需要再改一遍。

### 属于上游的

真正的修法在 `workbuddy2api` 的账号选择算法里。那不在这个仓库，
改它需要单独评估。

## 八、怎么复测

```bash
DB=/opt/workbuddy-manager/data/manager.db

# 分布
sqlite3 "$DB" "WITH c AS (
  SELECT account, count(*) n FROM request_logs
  WHERE ts > strftime('%s','now')-86400 AND account != '' GROUP BY account)
SELECT count(*) accounts, sum(n) total, round(avg(n)) avg, min(n), max(n),
       round(max(n)*1.0/min(n),1) ratio FROM c;"

# 某个账号的余额与历史
grep -A 6 '"c80dbc31-' /opt/workbuddy2api/data/state.json \
  | grep -oE '"(credits|credits_known|success_count|disabled)": [0-9a-z.]+'
```

## 九、后续补测：它们不是「被调度但失败」

这份记录最初留了一个未验证的可能：**用量低也可能是「被调度了但每次都失败」**
（失败不会进请求记录的账号字段，所以从用量看不出来）。

**查过了，不是。**

`state.json` 里全部账号的错误计数：

| 字段 | 分布 |
| --- | --- |
| `err_total` | 17 个账号为 **0**；9 个为 1；9 个为 2；其余零星在 3–9 |
| `consecutive_fails` | **全部为 0** |

**错误总数的最大值只有 9，连续失败全部为 0。**

如果那 48 个闲置账号在被反复调度但一直失败，`err_total` 会明显偏高 ——
它们的历史成功次数是 900 到 6,353，错误只有个位数。

**结论收紧为：它们不是「试过但没成功」，而是**真的没有被选中过**。**

这让「调度不均衡」从推测变成了确认。

## 十、两处必须写清楚的更正

### 更正一：`credits: 0` 不等于「没钱」

本文第三节最初写「`b7f1ad5f` 的 credits 是 0，那个不用是合理的」。

**这句话是错的。** 它的完整字段是：

```
"credits": 0, "credits_known": false
```

**`credits_known` 为 false 时，那个 0 是「未知」，不是「零余额」。**

全部账号里 `credits_known: false` 的有 **14 个**。把它们的 0 当成没钱，
会把 14 个账号的真实状态全部读反。

### 更正二：调度根本不按余额

顺着上面那条往下看，反而得到一个更强的结论。

用得最多的五个里有**两个余额是未知的**（`3077172d` 502…541 次、`4c4db6fd` 502 次）。
如果调度按余额优先，未知余额的账号不可能排到最前面。

**所以「按余额降序挑选」这个可能性也排除了。**

再对一轮：

| 分组 | 余额（已知的那些） |
| --- | --- |
| 用得最多 | 4,146 / 1,602 / 3,650 |
| 用得最少 | **4,274 / 3,091 / 3,945 / 4,130** |

**两组的余额区间几乎重叠。** 用量和余额之间看不出关系。

## 十一、这份记录没有回答的

- `workbuddy2api` 实际用的是哪种策略（轮询 / 最少使用 / 加权 / 粘性会话）
- 权重是否真的被那个调度读取（**只有做第七节那个十分钟验证才能确认**）
- 既然不是按余额、也不是按权重（全部默认）、也不是因为失败 —— **那它到底按什么排序**
