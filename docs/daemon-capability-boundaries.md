# 上游调度层（daemon）能力边界

> 用途：回答「这项能力到底缺不缺、缺在哪、改它要付什么代价」。
>
> 起因：2026-11-23 做同类项目对标时，把四项调度能力记成了「我们没有」。核实后
> 其中两项**已经有基础设施**，一项是**产品策略**而非技术缺口。不做核实就照着
> 清单改代码，代价是动一个 245 个 Go 文件、170 个测试、承载全部模型调用的进程。
>
> 另见 `UPSTREAM-CAPABILITIES.md`：那份记录的是**协议层**实测行为（直连引擎测出来的
> 响应特征），本文记录的是**调度层**的能力与改动代价。两者不重叠。

调度层指上游 daemon（源码在部署机的 `/opt/workbuddy2api`，容器
`zhihui-workbuddy`，监听 `127.0.0.1:7863`）。我们的 Python 网关只是它的客户端，
**账号池、选号、熔断、冷却、会话粘性都在 daemon 里**。所以这些能力不可能在网关
层补 —— 网关层没有账号池。

## 一、跨域合池（cn / global）

**现状：已有能力，当前是产品策略选择。**

`internal/pool/pick.go` 的选号谓词是：

```go
realmOK := func(e *entry) bool { return realm == "" || e.a.Realm() == realm }
```

即：**不传 realm 就是全池选号**（两域账号一起参与），传了才过滤。daemon 早已
支持合池。

我们的网关按密钥的 `realm` 选上游（`server/keysvc.py` 的 `realm` 字段 +
`routers/gateway.py` 的 `_upstream_for`），于是表现为「国内密钥只能用国内账号」。
这是**刻意的隔离**：让国内套餐的密钥去消耗国际版账号的额度，属于计费与合规
问题，不是技术限制。

**结论**：不改。若要放开，应先定策略（哪些密钥允许跨域、额度怎么算）。

## 二、熔断账号提前测活

**现状：缺。这是四项里唯一需要新写逻辑的。**

daemon 的熔断靠时间：`breaker_cooldown`（15 分钟）到 `breaker_cooldown_max`
（2 小时）线性退避，**到期前完全不碰这个账号**。所以一个已经恢复的账号要等到
冷却结束才回到池子，期间容量白白少一份。

**缺什么**：一个独立的探测循环，对冷却中的账号按间隔发一次最小请求，成功即提前
解除熔断。

**改动位置**：`internal/pool/` 新增探测 goroutine，复用现有的健康判定与
`transition.go` 的状态流转；配置加 `pool.probe_interval`（默认关闭）。

**风险**：中。探测本身是对上游的真实调用，频率/时机不对会**加剧**风控（2026-11-19
那次批量吊销就是扇出特征触发的，`accountguard` 就是为它加的）。所以必须默认关闭、
按账号错峰、限最小间隔。

**建议**：可做，但要先在单账号上验证探测请求不会被判异常。

## 三、按账号出口代理

**现状：已有基础设施。**

`internal/pool/egress.go` 已经有 `EgressKey(proxyName, realm)` —— 出口代理的键
计算与分桶在池层已存在，说明「按出口聚合/区分」的机制是现成的。缺的是把「每个
账号绑定一个代理」接进 HTTP 客户端出站。

**风险**：高。这改变的是**所有请求的网络路径**。配错一个代理就是全站不可用，
而这类错误在日志里表现为「上游超时」，很难第一时间归因到代理。

**建议**：先做「只读可视化」——把每个账号当前生效的出口地址显示出来，确认映射
符合预期；确认无误后再切换实际路由。

## 四、HTTPDNS / 主备入口

**现状：缺，且收益与风险不成比例。**

上游域名解析由 Go 标准库完成。要做候选 IP + 主备熔断，等于自己实现一套 DNS
缓存与健康检查。

**风险**：高但价值有限——上游域名本身的可用性由服务方保证，我们自建解析只在那
一方 DNS 出问题时才有意义，而那时通常整个服务也不可用。

**建议**：不做自动切换。改为「解析失败时给出明确错误码与告警」，让人能判断是
网络问题还是上游问题。这一项在网关层就能做（不必改 daemon）。

## 五、为什么这轮不动 daemon

1. **它是唯一承载全部调用的进程。** 改坏 = 所有模型调用中断，且没有「灰度一半」
   的空间（单进程单端口）。
2. **验证只能在真实流量上做。** 四项里三项与「上游风控」直接相关，实验室环境
   测不出问题；而真出问题的形态是「账号被批量吊销」——那正是 2026-11-19 事故。
3. **顺序错了代价很大。** 先做「可见性」（出口地址、冷却状态、探测结果的可视化），
   再动路由，是唯一能安全推进的顺序。

所以本轮只交付网关层与面板层的能力；daemon 侧的建议按上表逐项评估后再动。
