# 恢复体系的超时链

这份文档记录 2026-11-15 那次「备份报告说 ok，加密快照却一整天没产出」的故障，
以及超时值该按什么来定。

## 现象

| 产物 | 状态 |
| --- | --- |
| tar 基线备份 | 照常产出 |
| 加密快照 | **一份都没有** |
| 备份状态文件 | `restore_check: ok` |

**三行都是真的**，而结论「备份正常」是假的。

## 成因

恢复脚本调基线备份的那一行写的是 **300 秒**超时：

```
base_result = json.loads(run(['.../backup_application.py'], timeout=300).stdout)
```

而实测基线备份需要 **300 秒出头**。差的那几十秒是这样分布的：

| 时间点 | 事件 |
| --- | --- |
| 04:15:36 | 基线备份进程启动 |
| 04:19:52 | tar 写完（256 秒） |
| 04:20:36 | **超时点**（300 秒） |

也就是说：**文件写完了，但进程还要 40 多秒做收尾**（落盘、校验、写状态）。
超时正好卡在这个缝里。

## 为什么基线备份还在

`run()` 等的是**子进程退出**。超时抛异常后父进程退出，子进程成了孤儿继续跑完 ——
于是 tar 出现了，`backup-status.json` 也被写了。

**而恢复脚本那一步已经判定失败**，后面的加密、打包、快照全部跳过。

## 为什么告警没报

备份过期告警看的是 `backup-status.json` 的年龄。那份文件是**基线备份的子进程**写的，
它以为自己成功了 —— 在它自己的范围内确实成功了。

**两层「成功」叠在一起，掩盖了中间断掉的那一环。**

## 超时该取多少

以实测为准：

| 环节 | 实测耗时 | 建议值 | 余量 |
| --- | --- | --- | --- |
| 基线备份 | 约 300 秒 | **900 秒** | 3 倍 |
| 整个恢复流程（含加密） | 约 12–13 分钟 | systemd 1 小时 | 约 4.5 倍 |

**基线备份是唯一卡在边缘的一步**，所以只改它。

## 不能动的部分

基线备份服务的 IO 优先级被刻意压到最低。这一条**不要为了提速去改**：

| 窗口 | 请求平均延迟 |
| --- | --- |
| 备份期间 | 5540 ms |
| 备份前一小时 | 5472 ms |
| 备份后一小时 | 6376 ms |

**没有可测出的影响** —— 降优先级确实保护了线上。

所以方向永远是**延长超时**，不是给备份加资源。

## 改这个文件要注意

恢复脚本**不在**发布闭包（`host-files.json`）的校验范围内，也不在本仓库里。
它位于部署侧的持久目录，改动不会随版本发布走。

**所以改完要记在这里**，否则下次重建部署目录时会退回去。

改动前的备份留在 `/root/recovery_v3.py.bak-<时间戳>`。

## 相关指标

| 指标 | 回答 | 备注 |
| --- | --- | --- |
| `workbuddy_backup_age_seconds` | 基线报告是不是新的 | 可用 |
| `workbuddy_snapshot_age_seconds` | 加密恢复点还在不在推进 | **当前读不到**（见下） |

第二条读的是快照目录，而网关以非 root 身份运行、那个目录在 `root` 家目录下。
**它现在不输出任何值。**

要让它工作，需要恢复脚本把快照元数据写到网关可读的位置 —— 就像它已经在写
`backup-status.json` 那样。这件事本仓库做不了，记在这里备查。
