# 恢复体系的超时链

这份文档记录 2026-11-15 那次「备份报告说 ok，加密快照却一整天没产出」的故障，
以及超时值该按什么来定。

## 现象

| 产物 | 状态 |
| --- | --- |
| tar 基线备份 | 照常产出 |
| 加密快照 | **一份都没有** |
| 备份状态文件 | `restore_check: ok` |

**三行都是真的**，而结论「备份正常」是假的。

## 成因

恢复脚本调基线备份的那一行写的是 **300 秒**超时：

```
base_result = json.loads(run(['.../backup_application.py'], timeout=300).stdout)
```

而实测基线备份需要 **300 秒出头**。差的那几十秒是这样分布的：

| 时间点 | 事件 |
| --- | --- |
| 04:15:36 | 基线备份进程启动 |
| 04:19:52 | tar 写完（256 秒） |
| 04:20:36 | **超时点**（300 秒） |

也就是说：**文件写完了，但进程还要 40 多秒做收尾**（落盘、校验、写状态）。
超时正好卡在这个缝里。

## 为什么基线备份还在

`run()` 等的是**子进程退出**。超时抛异常后父进程退出，子进程成了孤儿继续跑完 ——
于是 tar 出现了，`backup-status.json` 也被写了。

**而恢复脚本那一步已经判定失败**，后面的加密、打包、快照全部跳过。

## 为什么告警没报

备份过期告警看的是 `backup-status.json` 的年龄。那份文件是**基线备份的子进程**写的，
它以为自己成功了 —— 在它自己的范围内确实成功了。

**两层「成功」叠在一起，掩盖了中间断掉的那一环。**

## 超时该取多少

以实测为准：

| 环节 | 实测耗时 | 建议值 | 余量 |
| --- | --- | --- | --- |
| 基线备份 | 约 300 秒 | **900 秒** | 3 倍 |
| 整个恢复流程（含加密） | 约 12–13 分钟 | systemd 1 小时 | 约 4.5 倍 |

**基线备份是唯一卡在边缘的一步**，所以只改它。

## 另一个更致命的问题：校验归档的方式

修好超时之后，同一轮里又发现了一处更严重的问题。

### 现象

基线备份很快完成，但恢复流程**跑了 25 分钟仍没有任何加密产物**，而且：

| 观察 | 数值 |
| --- | --- |
| 无间写入字节数 | **完全不变** |
| 累计读取字节数 | **18.6 GB**（归档本身只有 2.4 GB） |
| 线程数 | 1 |
| 打开的文件 | 只有归档本身与锁文件 |

**它在反复读同一个归档。**

### 成因

校验归档的写法是：

```
with tarfile.open(path, 'r:gz') as archive:      # gzip 不支持随机访问
    names = archive.getnames()                    # 遍历一遍
    manifest = archive.extractfile('…manifest.json')   # 又一遍
    for row in manifest['files']:                 # 四万多个文件
        info = archive.getmember(row['path'])     # 每个成员都会从头重新解压
```

**gzip 不支持随机访问。** `tarfile` 在 `r:gz` 模式下，每定位一个成员都要从归档开头
重新解压一遍。于是实际读量是：

**成员数 × 归档大小** ≈ 46 550 × 2.4 GB ≈ **111 TB**

按实测 1.3 MB/s 的解压速度，那是**永远跑不完**的，而 systemd 只给 1 小时。

### 为什么以前没暴露

归档小时，这个公式的乘积仍然可接受。数据一天天变大，某一天就越过了能跑完的边界。

**11-14 能成功、11-15 卡死**，中间没有代码变更 —— 变的是数据量。

### 修法

清单在归档旁边**本来就有一份 sidecar 副本**（写入端关闭时落的），所以不必从归档里
再解一遍。改成**一遍顺序遍历**：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 读取量 | 约 111 TB | **2.4 GB** |
| 遍历次数 | 成员数 + 2 | **1** |

**所有校验一条没删**：重复成员、成员清单一致、不安全路径、逐文件哈希与字节数、
符号链接目标、硬链接目标是否为普通文件、目录类型、数据库完整性、应用归档校验。

### 我在这处改动上引入的回归

改成读 sidecar 之后，第一次完整运行在**本地解密校验**那一步失败：

```
FileNotFoundError: .../local-check-xxxx/recovery-manifest.json
```

原因：`verify_local` 会把密文**解密到临时目录**再调 `check_archive`。那个临时目录里
**没有 sidecar** —— sidecar 只存在于原始快照目录。

**同一个函数有两个调用点，我只考虑了其中一个。**

修法是让清单获取走两条路径：

| 顺序 | 来源 | 代价 |
| --- | --- | --- |
| 1 | 归档旁的 sidecar | 一瞬间 |
| 2 | **从归档里顺序扫一遍取** | 多解压一遍 |

第二条只在「没有 sidecar」的场合发生（本地解密校验），不是常态。

**教训**：改一个被多处调用的辅助函数的**数据来源**时，必须把每个调用点的现场条件
都过一遍。原实现从 tar 里读清单，所以在任何目录下都能工作；改成读 sidecar 就
悄悄加了一个「sidecar 必须在场」的前置条件。


### 这里的教训

`getnames()` 看着只是「拿个名字列表」，`getmember()` 看着只是「取一个成员」。
在**未压缩**的 tar 上它们确实是廉价的；在 `r:gz` 上它们各自都要重解压整卷。

同一个 API，代价在两个模式下差三个数量级 —— 而调用点读起来没有区别。

## 备份为什么有 2 GB

打包的目录清单里包含 `/opt/zhihui-release` 整棵树。而它的子目录：

| 子目录 | 大小 | 内容 |
| --- | --- | --- |
| `writer-state/transactions` | **5,343 MB** | **133 个部署事务** |
| `audit-20261029-staging` | **2,752 MB** | 一次性的审计暂存产物 |

**部署事务没人清理。** 每次部署都会复制一份完整版本进 `transactions/`，完成后不删；
`writer-guard` 里也没有任何 prune / cleanup / gc 逻辑 —— 它的日志把这件事称作
"retained history"，是有意的设计。

于是：发了几十个版本 → 5.3 GB 垃圾 → **每次备份都把它们重新压一遍**。

这解释了备份体积从早期的几百 MB 涨到 2 GB 以上，也解释了打包阶段为什么越来越久。

**清理它需要运维决定**（历史事务可能被当作审计证据），本文档只记录事实。

### 修法是排除，不是删除

备份脚本里本来就有一个 `excluded(path)` 排除清单 —— `audit-20261029-staging` 早就在里面，
说明「有些东西不该进备份」这件事之前就想过，只是漏了 `transactions`。

补上一条：

```
if path == Path('/opt/zhihui-release/writer-state/transactions'):
    return True
```

**为什么选排除而不是删除：**

| 做法 | 后果 |
| --- | --- |
| 删掉 5.3 GB 事务 | 备份变小了，但垃圾还会重新长出来 |
| **排除这个目录** | **备份不再随部署次数增长**，历史事务原样保留 |

部署事务是**历次部署的中间副本**，不是能恢复系统的东西。备份要的是后者。

**这也意味着：即使事务堆到 50 GB，备份大小也不受影响。**

注意只排除 `transactions` 这一个子目录。`writer-state` 下还有 `floor.json`、`ingress.json`、
`migration/` 等文件，那些是**当前状态**，必须留在备份里。

## 不能动的部分

基线备份服务的 IO 优先级被刻意压到最低。这一条**不要为了提速去改**：

| 窗口 | 请求平均延迟 |
| --- | --- |
| 备份期间 | 5540 ms |
| 备份前一小时 | 5472 ms |
| 备份后一小时 | 6376 ms |

**没有可测出的影响** —— 降优先级确实保护了线上。

所以方向永远是**延长超时**，不是给备份加资源。

## 改这个文件要注意

恢复脚本**不在**发布闭包（`host-files.json`）的校验范围内，也不在本仓库里。
它位于部署侧的持久目录，改动不会随版本发布走。

**所以改完要记在这里**，否则下次重建部署目录时会退回去。

改动前的备份留在 `/root/recovery_v3.py.bak-<时间戳>`。

## 相关指标

| 指标 | 回答 | 备注 |
| --- | --- | --- |
| `workbuddy_backup_age_seconds` | 基线报告是不是新的 | 可用 |
| `workbuddy_snapshot_age_seconds` | 加密恢复点还在不在推进 | **当前读不到**（见下） |

第二条读的是快照目录，而网关以非 root 身份运行、那个目录在 `root` 家目录下。
**它现在不输出任何值。**

要让它工作，需要恢复脚本把快照元数据写到网关可读的位置 —— 就像它已经在写
`backup-status.json` 那样。这件事本仓库做不了，记在这里备查。
