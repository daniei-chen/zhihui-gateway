# v1.6.0 全面审计记录

**日期**：2026-11-25
**范围**：智汇网关（`zhihui-gateway`）全部代码、配置、生产运行态
**方式**：四路并行只读审计（安全 / 数据可靠性 / 代码质量 / 前端）+ 生产侧手工排查
**结论**：没有发现可直接远程利用的严重漏洞；修了 8 项，记录了 12 项不修的及理由。

---

## 一、为什么要做这一轮

上一版 v1.5.94 发布后，用户要求做「最高级别审计、全面修复」。所以这一轮不是
按某个具体故障去修，而是反过来：**先把面铺开查一遍，再用生产数据判断哪些是真问题**。

这个顺序很重要。静态审计很容易产出「看起来严重但实际没发生」的条目，这一轮就出现了
三个这样的判断，见第四节。

## 三、修了的 8 项

### 1. 命令注入：签到失败重试把 `uid` 拼进 `sh -c`（`server/credit_watch.py`）

```python
# 原来
setup += (' && for f in /app/auths/workbuddy-%s*.json; do ... done' % uid)
subprocess.run(['docker', 'exec', name, 'sh', '-c', setup], ...)
```

`uid` 来自 `checkin_logs` 表，被 `%` 直接拼进 shell 脚本文本，而这个容器挂着全部
账号 token。

**触发前提（如实说明）**：面板写入路径有正则白名单
（`services/tencent.py` 的 `re.fullmatch(r'[0-9A-Za-z_-]{1,80}', uid)`），所以正常
流程带不进恶意字符。恶意 uid 需要从旁路进入 `auths` 目录（手工放置、备份还原、
上游自己写入）。**所以这是防御纵深破裂，不是现成的远程 RCE。**

**修法**：uid 改走 argv，脚本里用 `"$u"` 引用，shell 不对它做任何解析；另加一层
`re.fullmatch(r'[0-9A-Za-z_-]{1,80}')` 格式闸门作为第二道保险。

### 2. 初始管理员密码被打印到 stderr（`server/security.py`）

stderr 会进 journald，`systemd-journal` 组成员、日志采集侧车、`docker logs` 都能读到，
而这份密码在改密前一直有效 —— 等于给凭据开了一条绕过 0600 文件权限的旁路。

**这个改动有历史包袱**：原代码的注释记录了 issue #179 —— 「密码只在 stderr 打一次，
错过就永远登不进去」（库里只有 pbkdf2 哈希）。所以不能简单删掉打印。

**修法**：保留提示、去掉密码，并直接把文件路径写出来。可恢复性还在，凭据不进日志。

### 3. `/api/health/alerts` 的回环判定绕开统一来源解析（`server/main.py`）

原来读 `request.client.host` 并和 `('127.0.0.1', '::1', 'localhost')` 比对。
这个值在反代之后取决于 uvicorn 的 `proxy_headers` 与 nginx 是否真的传了
`X-Forwarded-For` —— 那是没写进代码的隐式前提。

**修法**：改用全站唯一的 `iputil.client_ip()`（按 `WB_TRUSTED_PROXY_CIDRS`
从右往左数跳数，与 IP 白名单、登录锁定、密钥 `max_ips` 同一套口径），
再用 `ipaddress.ip_address(...).is_loopback` 判定。

顺带补上原先漏掉的：`is_loopback` 覆盖整个 `127.0.0.0/8`，以前 `127.0.0.2` 会被误拒。

### 4. `docs/README.md` 63 行链接是未求值的 PowerShell 模板

```
| [$(@{N=account-egress-routes.md; L=45}.N)](account-egress-routes.md) | 45 |
```

这张表是**我自己**在之前某次会话里用 `pwsh` 生成的，`$(@{...}.N)` 被当成字面量
写进了文件，没有求值。渲染出来是一串乱码，63 行全部不可读。

**修法**：正则替换成 `[文件名](文件名)`。已逐行验证 63 条链接指向的文件全部存在。

### 5. `docs/README.md` 的文档数声明过期

写的「37 份文档」；实际 `docs/` 根目录 170 个 `.md`，索引收录 63 条。
**修法**：改成实际数字并说明口径（收录的是「你会主动去找」的那些，不是全部）。

### 6. `docs/PRODUCT-RELEASE.md` 自称版本权威却写着 1.2.28

实际版本 1.5.94，中间隔了约 300 个发布段落。而这份文档是 `docs/README.md` 指给
读者的「版本号在哪些地方必须一致」的入口。

**修法**：不写死版本号，改成指向 [`VERSION`](../VERSION)，并列出 6 处由
`tools/bump_version.py` 同步、由 `test_release_consistency.py` 断言的位置。
**写死的版本号必然过期**，这是根本原因。

### 7. 删除 GBK 乱码的重复文档

`docs/WorkBuddy-WebUI璁捐涓庡疄鐜版柟妗_md` 与 `docs/WorkBuddy-WebUI设计与实现方案.md`
字节完全相同（SHA256 均为 `6D42A153…BBB142D`，63,768 B）。文件名是 UTF-8 被按 GBK
解码后的产物。**修法**：`git rm` 乱码那份，保留正常名。

### 8. 清理冗余常量 `SCRIPT_KIND_LABELS`（`server/services/tasklog.py`）

它与 `KIND_LABELS` 里的 `'school'` / `'cat'` 重复，从未被引用。见第四节第 3 条 ——
审计报告说它是「中文名不显示」的 bug，实际不是。

## 四、判断错的三次（这一节比修了什么更重要）

静态审计会产出「看起来严重、实际没发生」的条目。这一轮有三个，全部用生产数据推翻：

### 1. 「`usage_daily.requests` 系统性少计」

审计推演：上游流式响应没回 usage 时（`pt=ct=0`、`credit=NULL`），`bump_usage` 被
`if total or credit:` 跳过，于是 `request_logs` 有行而 `usage_daily` 没有 —— 两个页面
数字会分裂。

**生产数据**：符合该条件的推理请求**只有 26 条**，跨度 2026-10-28 至 11-23，
占 56.6 万条总数的 **0.005%**。

**结论**：口径分裂是真的，但影响可忽略。降级为「记录不修」。

### 2. 「`budget.finish` 失败会让配额密钥永久 429」

审计推演：`finish` 的 UPDATE 撞上 `database is locked` → 异常被吞 → 行停在 `forwarded`
→ 在途闸统计不带时间窗 → 配额密钥（limit=1）此后每个请求都 429，只有重启能解。

**生产数据**：`budget_reservations` 里 `forwarded` 只有 **3 条，最老 0 分钟** ——
全是正常在途。`settled` 229,105 条。

**结论**：理论风险成立，实际未发生。降级为「记录不修」。

### 3. 「`SCRIPT_KIND_LABELS` 未合并导致 school/cat 中文名永远不显示」

**实际**：`KIND_LABELS` 第 133-134 行已经有 `'school': '开学季任务'` 和
`'cat': '夜猫任务'`，且 `accounts.py:1889` 在用它，`test_tasklog.py:563-564`
还专门断言了这两项存在。

**结论**：中文名显示正常。那个常量只是纯冗余。

### 教训

**「两个数据源一致」只有在两个各自都被验证过之后才算数；同理，「一个 bug 看起来会发生」
只有在生产数据里确认它发生了才算数。**

## 七、这一版没做到的

- **没有动态验证**。四路审计全是只读静态分析，没有起服务、没有 fuzz、没有渗透测试。
  第四节那三个判断能纠正，靠的是查生产数据，不是靠跑起来试。
- **qtgcore 子系统的 29 个死代码没有判断**。它占全部死代码的六成，需要先回答
  「这个子系统还有维护意图吗」，而不是逐个删。
- **依赖没有做 CVE 比对**。只确认了 28 条全部精确锁定、没有明显危险的旧版本。
  另外注意：`starlette==1.6.0`、`uvicorn==0.53.0`、`certifi==2026.10.19` 这批版本号
  明显超前于公开 PyPI 序列，建议确认安装源与 SBOM 来源可信。
- **前端审计的最后一路**（国际化完整性、可访问性、构建产物）在本文件成稿时尚未返回。
