# v1.5.76 端到端验证（第 32 轮）

## 1. 先纠正一个我自己的查询错误

上一轮收尾时我用 `endpoint LIKE '/v1/chat%'` 查最近推理调用，返回空。当时没有深究。

这轮换成显式端点名，结果是：

```
endpoint                n(2h)   max(http_status)
/v1/chat/completions     463         200
```

**推理流量一直都在，而且不小。**上一条查询的空结果不是「没有调用」，是我的查询方式
有问题。这类「查不到就以为没有」正是本项目已经记过两次的坑
（第 19 轮「归档从未运行」、第 27 轮「日志里没有异常」），这是第三次。

| 指标 | 值 |

| 5xx | **0** |
| 429 | **0** |

说明不了「稳定」。

## 4. 修复是否真的解决了「内部错误」

部署后全部记录里，`gateway.application.error` 出现 **0 次**。

对比修复前：`v1.5.56` 时期每天 1 条左右，`v1.3.4` 时期单日最高 51 条。

**但同样受样本限制。**3 分钟 0 条，不能推出「再也不会出现」。真正需要的是
跨天观察，而这个只能靠时间累积。

## 5. 这一轮没有改代码

理由：上一步刚发完版，线上只有 3 分钟。在样本这么小的时候立刻再改一版，
一旦出问题无法区分是上一个改动还是这一个 —— 规范 §2.2 要求「一次只动一件事」，
而「刚发完就再发」违反了这条的精神。

本轮做的是**把「上线了」变成「验证过」**：§7 要求的五项
（版本、页面、产物、Release、用户可感知变化）里，第 3 项与第 5 项之前只是
「看起来对」，现在有了实测数据。

## 6. 三次同类失误的归纳

| 轮次 | 错误 | 本质 |
|---|---|---|
| 19 | 「`archive_runs` 空 = 归档从未运行」 | 把「没有记录」当成「没有发生」 |
| 27 | 「19:19 这段日志没有异常 = 没有日志」 | 用单个时间点代表整体 |
| 32 | 「`LIKE '/v1/chat%'` 空 = 没有推理调用」 | 查询写法出错，结论却照下 |

三次都指向同一件事：**「我查不到」和「它不存在」是两回事。**
正确的顺序是：先证明查询本身有效（拿一个已知存在的样本试），再用它下结论。

第 19 轮的文档里已经写过「『没有记录』必须先问『应该不应该有记录』」，
但那条只覆盖了「该有记录却没有」的情形，没覆盖「查询写错了」。
这轮补上这一条。
