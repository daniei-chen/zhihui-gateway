**安全方向没有缺口。**

## 2. 延迟：样本不足，不下结论

近 24 小时成功请求：

```
n=7708   avg=5222ms   p50=4254ms   p95=16215ms   max=300338ms
```

推理接口 `/v1/chat/completions` 平均 7696ms —— 那是生成本身的耗时，正常。

看起来最可疑的是控制台用的统计接口：

```
/api/stats/by-key     n=15  avg=851ms
/api/stats/by-model   n=15  avg=850ms
```

**我差点就去优化它了。**然后做了两件事：

一是把那条聚合 SQL 单独跑了一遍：

```
30 天窗口 174,282 行 → 89 ms
request_rates 查询      → 205 ms
usage_daily 聚合        → 约 10 ms
```

**三个查询加起来约 304ms，不是 850ms。**

二是回头看样本量：**`n=15`**。

**15 个样本的平均值不能代表稳定开销** —— 里面只要有两三次冷启动，均值就被拉上去了。

**所以这一项没有结论。**改索引或改查询都是没有依据的改动，不做。

（这是这一轮第二次遇到「数字看着不对但证据不足」。上一轮是时区，这一轮是样本量。）

## 3. 对账：三个口径差异是设计使然

```
usage_daily              688 行   139,839,367,404
usage_events(counted=1)  225,961 行 101,805,367,404
api_keys.used_credit_units  16 行  135,180,351,421
```

**三个数字差得很多。**第一反应是账不平。

但代码里 `credit-reconcile` 端点的注释已经把这个讲清楚了：

> 同一批用量在三个面上曾经各不相同 —— `usage_events`（账本，只覆盖账本上线后）
> 17.6k、`usage_daily`（展示，全量聚合）55.6k、`api_keys.used_credit_units`
> （配额执法）45.4k，最大差 3.17 倍。

三个口径的**定义**不同：

| 面 | 覆盖范围 | 用途 |
|---|---|---|
| `usage_events` | **只覆盖账本上线之后** | 不可变事件账本 |
| `usage_daily` | 全量按日聚合 | 界面展示 |
| `api_keys.used_credit_units` | **终身累计** | 配额执法 |

**差异是预期内的，不是漂移。**而且注释里还写明了为什么不能用明细覆盖执法值：
`request_logs` 有 90 天保留期，用它覆盖终身累计等于**把已消耗的配额退回去**，
越老越严重。代码侧已经封死（`db.assert_credit_units_unchanged`）。

**这一项不需要改。**

## 5. 这一轮的判断

**三个方向查完，三个方向都不需要改。**

规范 §2.1：「不要在没有 P0/P1 的时候硬凑改动。找不到值得做的，就做诊断和验证，把结论写清楚。」

这一轮就是这个情况。而且做得有价值的是**第二次拦住了自己** ——
统计接口那 850ms 看着就是个待优化项，如果我按第一直觉去改索引，
会得到一个"改了但没变"的结果，然后把原因归给"索引没用"。

**「数字不对」和「数字没意义」是两件事。先确认后者。**
