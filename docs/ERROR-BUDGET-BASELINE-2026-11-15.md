# 错误预算基线 — 2026-11-15

**近 7 天：36 603 次请求，36 043 次成功（99.0%）。**

这份文档记下**当前各类失败的实际占比**，用来以后回答一个问题：
**「这次变慢/变差，是异常，还是本来就这样？」**

没有基线的话，每一次 502 都会被当成新问题重新排查一遍。

---

## 一、七天总量与成功率

| 状态码 | 次数 | 占比 |
| --- | --- | --- |
| **200** | **36 043** | **98.5%** |
| 502 | 307 | 0.84% |
| 429 | 161 | 0.44% |
| 503 | 63 | 0.17% |
| 400 | 29 | 0.08% |
| **合计** | **36 603** | |

**成功率的算法有两种，两个都该看**：

- 按**全部请求**算：98.5%
- 按**排除 429 之后**算：**99.0%**（429 是主动限流，不是故障）

**这两个数差 0.5 个百分点**，而差额全部是限流。**只看一个数会得出相反结论**：
按全部算是「差一点到 99」，按排除算是「稳稳超过 99」。

## 二、最主要的失败，按次数

| 次数 | 状态 | 含义 | 判断 |
| --- | --- | --- | --- |
| **159** | 429 | 密钥并发容量已满 | **主动限流**，不是故障 |
| **60** | 502 | 上游传输失败，处理与用量未知 | **不确定但已明确声明**（见第四节） |
| **55** | 503 | 上游返回 503 | 上游不可用 |
| **33** | 502 | 上游首字节超出时间预算 | 上游慢 |
| **22** | 400 | 请求上下文过长 | **客户端参数问题** |

**前五类占全部失败的一半以上。** 其中两类不是故障：**429 是主动限流**、**400 是客户端参数**。

## 三、429 的两种子类型必须分开

| 子类型 | 含义 | 等待时间 |
| --- | --- | --- |
| `key_concurrency_exceeded` | 同一密钥的并发已满 | **1 秒**（当前请求结束就能进） |
| `rate_limit_exceeded` | 频率超过窗口上限 | **整个窗口**（60 秒） |

**这两种的等待时间差 60 倍，而状态码相同。** 客户端如果只看 429 不看 `Retry-After`，
会把「等一秒」的情况当成「等一分钟」处理。

**文案里已经分别写清**（「请等待当前请求结束」vs「{60}s 内超过 N 次」）。

## 四、`upstream_transport_uncertain` 的处理是对的

完整响应：

```json
{"error":{"code":"upstream_transport_uncertain",
 "message":"Upstream transport failed; processing and usage are unknown.
            Request was not replayed.","type":"api_error"}}
```

**两句话都是关键，都不能省**：

- **「Request was not replayed」** —— **没有重放**。重放一个 POST 可能造成上游重复处理、
  重复计费，而客户端会把重放的响应当成第一次的结果。
- **「processing and usage are unknown」** —— **不假装知道**。传输断了就是断了，
  不能编一个「成功」或「失败」出来。

**宁可返回一个诚实的 502，也不返回一个伪造的 200。**

## 五、这些数字怎么用

**判断「这次是不是异常」时，先看它有没有超出本表的量级。**

- 每天约 5 200 次请求，每周约 300 次 5xx —— **平均每天四十来次**
- **单日 5xx 超过 100 次**才值得当成异常去查
- 429 出现是**正常的**：它是限流在工作，不是故障

**反过来说**：**看到 429 就去「修」，是把保护机制当成 bug。**
前几轮已经确认过这一点（按密钥并发返回 429 是设计行为）。

## 六、这份基线的有效期

**它记录的是 2026-11-08 至 2026-11-15 这一周。**

流量结构变了（比如接入新客户端、换模型、改并发上限），这些比例就会变。
**变了之后应当回头更新这张表，而不是拿旧表去否定新现象。**

## 附：怎么重新生成这份数据

```sql
-- 状态码分布
SELECT http_status, count(*) FROM request_logs
WHERE ts > strftime('%s','now') - 604800
GROUP BY http_status ORDER BY 2 DESC;

-- 错误文本分布
SELECT count(*), http_status, substr(replace(coalesce(error,''), char(10), ' '), 1, 60)
FROM request_logs
WHERE ts > strftime('%s','now') - 604800 AND error IS NOT NULL AND error != ''
GROUP BY http_status, 3 ORDER BY 1 DESC LIMIT 12;
```
