# 备份与恢复的现状 — 2026-11-15

**结论先说：备份有三层，保留策略存在，每份都自校验。真正的缺口是「没有异地副本」。**

---

## 零、先纠正一个我说错的判断

此前几轮我反复说过「日常备份只保留最新一份，没有 N 天策略」。

**这句话是错的。** 我没有查过实际的备份脚本与保留逻辑，只是看到某个目录里只有一个文件就下了结论。

**实际做法比我说的完整得多**，见下一节。**这条纠正本身写在这里**，因为一个错误的判断
会让人去做不必要的改动 —— 而改动一个本来正确的备份策略，风险比不动它大得多。

---

## 一、实际有三层

### 第一层：每日整机恢复包

| 项 | 值 |
| --- | --- |
| 位置 | `/root/backups/workbuddy-daily/` |
| 单份大小 | **约 300 MB**（最新一份 326 851 257 字节） |
| 调度 | **每日 05:30**，由 root 定时任务调起 |
| 生成器 | `server/backup_application.py`，**限定 512 MB 内存**运行 |
| 内容 | 数据库 + 发布目录 + 状态文件 |

### 第二层：本地第二副本

| 项 | 值 |
| --- | --- |
| 位置 | `/root/backups/workbuddy-mirror/` |
| 调度 | **每日 05:50**（比第一层晚二十分钟） |
| 保留 | **最近 7 份** |
| 目的 | **防误删、防单目录损坏** |

### 第三层：保留策略

写在 `deploy/recovery_retention.py` 里，规则是：

- **最近 3 份**：无条件保留
- **7 天内**：保留
- **`latest.json` 引用的那一份**：**永不删除**（哪怕它已经很旧）

再加几道安全闸门（脚本注释里写明）：删除前**复算密文哈希**、按目录名时间戳排序、路径越界拒绝。

**「最新一份永不删」这条最值得记**：它保证任何清空操作都不会让系统失去「最后一份可用恢复点」。

---

## 二、每份备份都自校验

日志里每份记录都是这个形状（截取关键字段）：

```json
{
  "path": ".../recovery-20261115-053001.tar.gz",
  "sha256": "5a4db25a...",
  "bytes": 326851257,
  "request_rows": 334163,
  "restore_check": "ok",
  "paired_ledger_check": {
    "file_count": 105,
    "complete": true,
    "restore_check": "ok",
    "quarantined": true
  },
  "release_check": {
    "release_id": "v1.2.91",
    "files_verified": 651,
    "check": "ok",
    "signature_verified": true
  },
  "offsite": false,
  "retention": "retained pending offsite policy"
}
```

**四个字段说明它做了真实的校验，不是「打包成功就算成功」**：

| 字段 | 含义 |
| --- | --- |
| `restore_check: ok` | **真的解出来试过** |
| `file_count: 105` | 状态文件数量核对 |
| `files_verified: 651` | 发布目录里逐文件校验 |
| `signature_verified: true` | **签名验证通过** |

---

## 三、真正的缺口：没有异地副本

**`"offsite": false`，而 `"retention"` 字段自己写着 `retained pending offsite policy`**
—— 意思是「为了等异地策略，先都留着」。

**两份副本都在同一块盘上**（`/root/backups/` 的两个子目录）。

**那块盘坏了，两份一起没。**

这是**唯一**真实存在的备份缺口，而不是「保留策略缺失」。

---

## 四、一个曾经失败过的例子

日志里有一条 2026-11-13 的记录：

```
RuntimeError: managed recovery source hash mismatch: .version
```

**某一天的备份因为源文件的哈希对不上而失败。**

**这件事说明校验在起作用**：它没有把一个「内容不对」的包当成备份存下来 ——
那正是最危险的情况（**你以为有备份，恢复时才发现是坏的**）。

**但也要看到另一面**：那次失败之后，当天就没有新的可用恢复点。
**失败是响的（有异常），但没有人被通知到。** 定时任务的输出只进了日志文件。

## 五、建议（等你决定）

**唯一值得做的是异地副本**，其余不用动。

异地有两种做法，成本差别很大：

| 做法 | 优点 | 代价 |
| --- | --- | --- |
| 推到一个对象存储 | 真正的异地，抗整机损失 | 需要账号与凭据，**每份 300 MB** |
| 推到另一台机器 | 同样是异地 | 需要第二台机器 |

**300 MB × 7 份 ≈ 2 GB**，这是异地要占的空间量级。

**在决定之前，不做任何改动** —— 现有的三层结构是有效的，贸然改它只会增加风险。

---

## 六、这份文档怎么维护

**备份策略改了（份数、路径、调度），回来改第一、二节。**

**`offsite` 变成 `true` 之后，第三节要整段重写** —— 那是这份文档存在的理由。
