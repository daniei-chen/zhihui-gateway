## 5. 一处真正的口径矛盾（P2，未修）

`server/observability.py:402` 的 `_gateway_code()` 里，
**只有 `client.cancelled` 和「无错」两种情况不归 gateway，其余一律归 gateway**：

```python
if terminal == 'upstream_error':
    return 'gateway.upstream.error', ERROR_SOURCE_GATEWAY   # 名字说上游，归属说我们
if terminal == 'transport_error':
    return 'gateway.transport.error', ERROR_SOURCE_GATEWAY
```

而 `upstream_timeout` 在 `gateway.py:415` 等处用 `mark_error('upstream_timeout')`
—— `mark_error` 的**默认 source 就是 `ERROR_SOURCE_GATEWAY`**，
所以也归了我们。

**这和规范 §3.4 冲突**：

| 类型 | 规范 §3.4 | 代码实际 |
|---|---|---|
| 上游瞬时失败 | 否，记下来即可 | **算 gateway** |

### 为什么这一轮不修

三条理由，都不是「懒得改」：

1. **改了会断掉统计连续性。** `test_observability_contract.py:73` 钉着
   `(('upstream_error', 'upstream', 502), ('gateway.upstream.error', 'gateway'))`
   —— 这是有意的契约，不是疏忽。改它要同时改测试、改历史对比口径。
2. **影响面只有 17 条**（`gateway.upstream.error` 16 + `upstream_timeout` 1），
   占近 7 天 109 条的 15.6%。
3. **上一轮刚立的原则**：先让信息可见，再谈归因。现在 `error_code` 的名字
   已经能看出是上游（`gateway.upstream.error` 一眼就知道），
   只是 `error_source` 字段归错了。而 `error_source` 目前没有下游消费者
   —— 巡检、告警、控制台都不读它。

**要做就单独一轮做**：给 `_gateway_code` 加一个「上游责任」的判定，
同时提供历史数据的一次性重标注脚本，并更新那份契约测试。
混在这一轮里做，会让「零中断」的结论变得没法解释。

## 8. 一次差点违反 §1.4 的测量错误（第 22 次）

规范 §1.4 写着：

> **不许把「没机会出错」当「没出错」。** 报 5xx = 0 时必须同时给出窗口内请求数。

这一轮我自己差点栽在这条上，而且栽得很难看。

### 先搞错了「现在几点」

查 v1.5.92 / v1.5.93 的部署窗口时，我用的是记忆里的时间（20:00、21:30），
查出来两个窗口都是 `req=0, 5xx=0`。当时的第一反应是「哦，那段时间没流量」。

然后我去查流量分布，发现今天的数据只到 19 点就断了，心想「难道采集中断」。
一查才发现：

```
DB 认为: 2026-11-25 19:07:28 CST
主机说:   2026-11-25 19:07:28 CST
最新记录: 2026-11-25 19:07:27  /v1/chat/completions  200
```

**当时就是 19:07。** 我以为的「20:00 和 21:30」根本还没发生。
那两个窗口返回 0 不是因为没有流量，是因为**我在查未来**。

### 再搞错了 SQL 的时区

`strftime('%s','2026-11-25 17:35')` 把字符串**当 UTC** 解释，而我要的是 CST。
差了 8 小时。验证方式：

```
datetime(strftime('%s','2026-11-25 17:35'),'unixepoch','+8 hours')
  -> 2026-11-26 01:35        ← 错
datetime(strftime('%s','2026-11-25 17:35','-8 hours'),'unixepoch','+8 hours')
  -> 2026-11-25 17:35        ← 对
```

正确写法是 `strftime('%s','<CST 时间>','-8 hours')`。

### 修正后的真实窗口

```
版本      窗口(CST)        请求   5xx
v1.5.91   17:34..17:37      23     0
v1.5.92   18:34..18:38      26     0
v1.5.93   18:49..18:53      21     0
```

三处都用 `request_outcomes`（`protocol != 'http'`）和 nginx access.log
（`$7 ~ /^\/v1\//`）**两个独立来源交叉验证**，都是 0。

**这才是真的零中断：窗口里有 21-26 条真实推理请求。**

### 教训

如果我停在第一次的结果，报告里就会有一句
「v1.5.92 重启窗口 0 请求 / 0 个 5xx，零中断」。

那句话每个字都对，结论却是假的 —— 因为**空窗里说零中断不算数**。
而它看起来和真结论一模一样，没人会去核。

**「查出来是 0」和「确实是 0」之间，隔着一个「我查的到底是什么」。**
