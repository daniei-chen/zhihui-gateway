# 三次「首字节超过 60 秒」：不是故障，但注释骗了我一次（第 52 轮）

## 1. 巡检报出来的

```
warn  3 次流式请求首字节超过 60 秒（最长 87 秒）
```

87 秒才看到第一个字。对用户来说这跟卡死没区别，所以我按 P1 去查。

## 2. 三次请求的实际数据

```
时间                  model                 status  ttfb_s  total_s  key
2026-11-25 15:36:40  deepseek-v4.1-flash   200     79.9    80.8     57
2026-11-25 15:38:13  deepseek-v4.1-flash   200     87.3    88.2     57
2026-11-25 15:38:15  deepseek-v4.1-flash   200     69.7    83.6      1
```

三次都在同一个两分钟窗口内、同一个模型、全部 **200 成功**。

## 3. 第一层：代码默认值是 60 秒

`deadline.py`：

```python
class Budgets:
    connect_s: float = 5.0
    first_byte_s: float = 60.0      # ← 首包预算 60 秒
    stream_idle_s: float = 600.0
    total_s: float = 600.0
```

**如果 60 秒预算生效，87 秒的请求应该在 60 秒被切断，而不是返回 200。**

所以我当时判断这是一个真 bug：预算没生效。

## 4. 第二层：线上覆盖成了 240

查 systemd drop-in：

```ini
# WB_FIRST_BYTE_TIMEOUT_S=180：实测首包 p99=52.5s、max=210s，180s 覆盖 99.998%
Environment=WB_FIRST_BYTE_TIMEOUT_S=240
```

**线上是 240 秒。**所以 87 秒在允许范围内，**行为完全正确**。

我第一次判断错了 —— 我看了代码默认值，没看线上覆盖值。

## 5. 第三层：240 是有意放宽的，60 曾经造成事故

`deadline.py:147` 的文档字符串写着：

> `WB_FIRST_BYTE_TIMEOUT_S` 默认 = 读超时（旧版 first_byte 只记指标、无硬预算；
> **60s cap 会造成慢上游 502，2026-10-26 回归修复**）

`docs/LATENCY-ATTRIBUTION-2026-11-15.md` 里有更直接的数据：

> 这正是 `WB_FIRST_BYTE_TIMEOUT_S=240` 存在的原因（实测有 **158 次首字节超过 60 秒**…）

**也就是说：把首包上限设成 60 秒，会有 158 次请求被误杀成 502。**

现在这个 240 秒是有证据支撑的正确选择。

## 6. 唯一真正的问题：注释和配置不一致

那个 drop-in 文件里：

```ini
# 注释说 180
Environment=WB_FIRST_BYTE_TIMEOUT_S=240    # 实际 240
```

**有人改过值没改注释。**

这构成一个隐蔽的陷阱：读这个文件的人（包括我）会以为上限是 180，
然后看到 87 秒觉得「超过了一半，很危险」，或者看到 200 秒觉得「绝对该拦下来」。

实际是 240。

## 7. 为什么这一轮不改

| 原因 | 说明 |
|---|---|
| 文件不在仓库里 | 它是主机上的 drop-in，`deploy/systemd/` 只有 `socket` 和 `INSTALL.md` |
| 改 systemd 文件被 guard 拦 | `systemd-unit-write` 无论 sudo 都拒绝 |
| 代码侧无需改动 | 240 是正确值，代码读环境变量的逻辑是对的 |
| 仓库里的副本是对的 | `workbuddy-web-helper.service` 里写的就是 240 |

**所以这是一次纯记录。**但记录本身有价值：下一个看这个文件的人不必再困惑一次。

## 8. 这一轮的第三个「测量工具出错」

本轮我犯了三次同类错误：

1. 查 `first_byte_ms` 用错了表（在 `request_logs` 不在 `request_outcomes`）
2. 看代码默认值（60）当成了线上值（240）
3. 一度以为「60 秒预算没生效」是真 bug

**第 2 条是这一轮的核心教训**：代码里的默认值、注释里的数字、线上的实际值
是**三个不同的东西**。看到任何一个都不能直接当结论。

规范 §2.2 说「先读再改，改之前必须有证据表明现状是这样」。这里的教训是：
**「读代码」不等于「知道现状」**。现状在运行中的进程里，得去 unit 文件、
环境变量、实际数据里找。
