# v1.5.77：把一条常年亮着的警告关掉（第 34 轮）

## 1. 怎么找到这一项的

前几轮都在做验证，没有真实改动。这轮从巡检的 3 条警告逐条看：

```
warn  5xx 占比 0.10%，低于 1% —— 多半是推理调用在上游侧失败
warn  近 24 小时 7 次「上游无可用账号」（503）
warn  1 项预警：workbuddy_low_accounts
```

第二条、第三条是上游侧的事实，不该静音。**第一条不是事实，是判断错了。**

## 2. 判断错在哪

`healthcheck.sh` 里：

```bash
note() { warn=$((warn + 1)); printf '  warn  %s\n' "$*"; }
...
if [ "${errors:-0}" -eq 0 ]; then
    pass '近 24 小时无 5xx'
elif rate < 1; then
    note "5xx 占比 $rate%，低于 1%"
else
    broken "5xx 占比 $rate%，需要排查"
fi
```

**`note` 就是 `warn`。**所以「有 5xx 但低于 1%」被判成警告。

问题在于：**在 LLM 网关上这个条件几乎每天都成立**。上游模型服务本身会零星失败，
8,368 次请求里 8 个 5xx（0.10%）是常态。结果这一项常年挂在警告里。

规范第 3.4 节写得很明确：

> 报「零中断」时只限定在**部署窗口**内。全天仍有失败是正常的，LLM 上游本身就会失败，
> 但那不叫「零中断」，叫「今天有 N 条 5xx」。

**巡检这一行的职责是判断「能不能用」。低于 1% 能用，就该是 ok。**

## 3. 改法

```bash
elif rate < 1; then
    printf '  5xx 占比 %s%%（低于 1%%，属上游侧正常波动）\n' "$rate"
    pass '近 24 小时 5xx 低于 1%'
else
    broken "5xx 占比 $rate%，需要排查"
fi
```

**占比数字照常打印，没有被藏起来。**只是不再把一个「能用」的状态报成警告。

## 4. 部署验证

| 项 | 改前 | 改后 |
|---|---|---|
| 巡检 | ok 22 / 警告 3 / 问题 0 | **ok 23 / 警告 2 / 问题 0** |
| 那一行的输出 | `warn 5xx 占比 0.10%…` | `5xx 占比 0.10%（属正常波动）` + `ok` |
| 重启窗口 | — | **57 请求 / 0 个 5xx** |
| 部署后累计 | — | 36 请求 / 0 个 5xx |

## 5. 一处判断失误

部署时第一遍拿错了提交号：用代码提交 `dbbb8cc` 去取 `VERSION`，拿到的是 `1.5.76`。
因为 `bump_version.py` 是在代码提交**之后**才跑的，版本面文件在更晚的那个提交里。

这是 §2.4「先提交改动，再升版本号」的直接后果 —— 既然分成两个提交，
取版本面文件就必须用**后一个**提交。已用 `eae2182` 重新取，`VERSION=1.5.77`、
`source_commit=dbbb8cc` 都对上了。

**记下来：改动用代码提交号，版本面用 bump 后的提交号，两者不能混。**

## 6. 这一版的影响面

只改了运维巡检脚本，**推理链路一行没动**。

所以「用户会看见什么变化」这个问题的答案是：用户看不见任何变化。
看见变化的是运维 —— 少一条天天亮着的假警告。

按 §7 第 3 问的严格标准，这一版的用户价值接近于零。它属于 §2.1 里的 P2
（告警噪声），在 P0/P1 都不存在的当前状态下，这是可以做的、也确实值得做的一类改动。
