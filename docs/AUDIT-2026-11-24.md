| 维度 | 判决 | 最该做的一件事 |
|---|---|---|
| 可靠性 | **最严重**：每天 30–60 次启动被拒 + 重启窗口直接 502 | 守卫可诊断 + socket activation |
| 协议 | 宽但有三处静默走错路 | `count_tokens` 容错、responses 预算判定、缓存字段回落 |
| 计费 | 结构对，金额对不上发现不了 | 把已写好的对账接上线 |
| 数据 | 只能涨不会收 | 落地归档出口 + 容量上限 |

| 测试 | 970 只证明 17% | 门禁真实化 |
| 观测 | 有指标缺信号 | 事件循环延迟 + 首字节 + 启动原因码 |

### 2.1 可靠性：**最严重的一维**

**判决：失败模式集中在"启动期"和"事件循环被阻塞"，而不是上游。**

**R-1 启动守卫是黑盒（P0）**【实测 + 审计】
`writer_entry.py:210-226` 的 `except Exception:` 把所有原因压成一句固定文案，注释写明"Never include environment values, user documents or provider tokens"——**目的正当，做法过度**：连"是签名不符、是运行时锁被别人占着、还是状态机不一致"都不区分。205 次拒绝因此无法归因。
建议：改为打印 `REASON=<枚举码>`（不含值），或在 `/opt/zhihui-release/state/` 落一份只有 root 可读的原因码；顺带把这类守卫代码纳入仓库（现在真正切流量的那一步不在仓库里，也不被 CI 覆盖）。

**R-2 重启窗口直接变成 502（P0）**【实测】
每次重启 `RestartSec=3` + 启动约 5 秒 ⇒ 约 8 秒内 7866 上无人监听 ⇒ nginx 立刻 502。
两条修法，建议都做：
- 便宜：`systemd` **socket activation**（`ListenStream=127.0.0.1:7866`、`Accept=no`），重启期间连接进 backlog 排队而不是被拒；nginx `proxy_connect_timeout` 大于重启时间即可零 502。
- 兜底：nginx 加 `proxy_next_upstream error timeout http_502` + `proxy_next_upstream_tries 2`（单上游时仍需 handler 短重试才有效）。

**R-3 事件循环上的同步 SQLite（P1）**【审计】
单连接 + `threading.RLock`（无超时）+ `synchronous=FULL`（`db.py:600-614,1985-1993`），而热路径上这些都在事件循环线程里跑：鉴权 `SELECT * FROM api_keys`、`_log_ip`、请求结束的 `request_outcomes` INSERT、`budget.finish`、以及**流式结算 `_record`**（`gateway.py:3233`，作者自己在 `gateway.py:1150` 承认）。
后果链：任一线程持锁长事务 → 循环阻塞 → 所有在途 SSE 停止转发 → 恢复后 `Deadline` 已超时 → **一批假的 `transport_error`**；同时心跳/续约排队可能触发实例租约失守 → `drain.shutdown=True` → 此后**除控制路径外一律 503，且不自愈**（`drain.py:39-47,201-208`；`threadpools.py:9-14` 自己写"只能重启"）。
建议：`to_thread` 掉那四处写；给 `db` 加 `acquire(timeout)` 并在超时后降级为"无日志放行"。

**R-4 首字节与准入：参数是合理的，缺的是信号（P1）**【实测 + 审计】
生产实际配置（`systemctl show`）：`MAX_CONCURRENCY=64`、`LARGE_MAX_CONCURRENCY=28`、`KEY_CONCURRENCY=30`、`UPSTREAM_TIMEOUT=300`、`FIRST_BYTE_TIMEOUT_S=240`、`DRAIN_TIMEOUT_SEC=75`。首字节 240 s 是**有实测依据的选择**——drop-in 注释写着"实测首包 p99=52.5 s、max=210 s"。所以不建议压到 60–90 s（会误杀正常长思考请求）。
真正的风险在于：**上游挂住时，一条流会在 4 分钟内占着 28 个大请求名额之一，而对外只有一个 15 秒一次的 `: keepalive`（`sseheartbeat.py:29-32`），客户端和网关都"看起来还活着"**；准入只信 `active/large/inflight_bytes` 三个内存计数（`observability.py:1214-1231`），不看事件循环延迟、CPU、RSS。
建议：不动 240，改为①按账号统计 TTFT 并暴露指标，挂住的账号进冷却；②准入加入事件循环延迟信号；③给"首字节超阈值"单独告警（现在只有整体错误率）。

**R-5 重试与熔断错位（P1）**【审计】
- 重试判据依赖**响应体里的 code 字符串**（`gateway.py:333-376`），而 429 **不重试**（上游限流直接透传）。
- `NEVER_RETRY_PHASES` 含 `first_byte`（`deadline.py:94`）——恰恰是"还没吐一个字节"最该换账号的时刻。
- 没有账号级熔断：`x-wb-account-uid` 只写日志（`gateway.py:2949,3085,3132`），切号完全依赖上游 daemon。
- 每密钥一条 transport 分桶 + 全局仅 32 桶（`config.py:849-856`），密钥数≈用户数时退化为每请求握手。

**R-6 多 worker 是天坑（记录在案）**【审计】
`serve.py:51` / `Dockerfile:166` 都是单 worker；一旦有人加 `--workers N`，`_key_slots`/`_rate`/admission 计数/`_rejection_limit_cache` 全部按进程分裂，限额放大 N 倍（`observability.py:576-609`、`gateway.py:630-662`）。建议在 `serve.py` 里显式拒绝 `workers>1`，把"不能扩"变成代码约束而不是口头知识。

### 2.2 协议兼容：**宽，但有三处会让客户端静默走错路**

**判决：`/v1/chat/completions` 是真透传（`gateway.py:2966,3165`），另两个入口是手写状态机 + 局部补丁。**

**P-1 `POST /v1/messages/count_tokens` 遇到 tool 块必 500（P1，确定）**【审计】
`_text_of` 只接受 `text/image`（`anthropic.py:277-278`），count_tokens 无 try/except（`anthropic.py:1653-1656`），全局无兜底 handler。Claude Code 每次带历史工具结果调它 → `Internal Server Error`。

**P-2 `/v1/responses` 没有"预算耗尽"判定（P1，确定）**【审计】
chat 与 messages 都会报 `output_budget_exhausted`（`gateway.py:3173`、`anthropic.py:1542`），responses 全文无命中 → 发 `response.incomplete` + 空 output（`responses.py:1796-1816`）。客户端把"没钱了"读成"正常截断"，既不重试也不提示。

**P-3 `cached_tokens` 恒 0（P1，确定）**【审计】
responses 只读 `prompt_tokens_details.cached_tokens`（`responses.py:1068-1069`），而上游实际给的是 `prompt_cache_hit_tokens`（`anthropic.py:157-159`、`gateway.py:827-829`）→ 缓存收益对 Responses 客户端不可见。

**P-4 `/v1/responses` 未注入会话键（P2）**【审计】
`_inject_session_key` 只在 chat/messages 调用（`gateway.py:2787`、`anthropic.py:1269`），responses 没有 fallback（其 body 无 `messages`），后果是账号不粘、缓存命中受损（**命中率影响未验证**）。

**P-5 错误语义不齐（P2）**【审计】
429 在 messages/responses 无 `Retry-After`；配额耗尽把 OpenAI 专有 `insufficient_quota` 塞进 Anthropic 错误体（`anthropic.py:250-251`）→ Anthropic 客户端把它当可重试，无限退避；`content_filter` 映射成 `end_turn` 而官方是 `refusal`（`anthropic.py:61,829`）——被安全拦截的回答显示成"正常结束"。

**P-6 其余缺口（P3，记录）**：tool arguments 缓冲到收尾一次性发（长工具参数无流式）、`stop_sequence` 恒 null、responses 丢 logprobs/`metadata`、`parallel_tool_calls=false` 直接 400（`responses.py:660-661`）、Anthropic `cache_control` 完全未读取、图片输出被静默丢弃。

> **要不要继续投入？** 7 天 messages 48 次、responses 23 次。除 P-1/P-2/P-3（会让人误判）外，其余建议冻结。

### 2.3 计费与账本：**结构没断，但金额对不上无从发现**

**判决：幂等与事务做得比多数同类项目好；缺口在"对账没有出口"和"单笔敞口无上界"。**

**B-1 已做对的（不必重改）**【审计】：`request_id` 部分唯一索引 + `INSERT OR IGNORE` + 早退（`db.py:883,1463`、`gateway.py:1101-1103`）；五张事件表唯一键 + 禁改禁删触发器（`ledger.py:17-23,86-89`）；`prepare` 的"读余量→算→写预留"在同一个 `BEGIN IMMEDIATE` 内，无 TOCTOU（`budget.py:164-272`）；`usage_source ∈ {upstream,unknown,not_reported,not_applicable}` + `usage_complete`，**缺失时不估算、不补 0**（`gateway.py:1079-1080`）——这条做得比多数竞品诚实。

**B-2 五表对账出口零调用（P1，确定）**【审计】
`metering.reconcile`（`metering.py:260`）**没有任何生产调用方**，只有测试引用。等于对账能力写好了但没接线。

**B-3 token 侧完全没有对账（P1）**【审计】
`used_tokens` / `key_daily_usage` / `usage_events` 三者之间无任何交叉检查；`usage_daily` 重建用 `MAX` 而非 `SUM`（`db.py:1772`），重建后与明细不可比。

**B-4 客户端重试双计费（P2，确定 bug）**【审计】
`request_id` 是 uuid4，`X-Request-ID` 只落库不判重（`observability.py:67`、`gateway.py:1091-1094`）→ 客户端超时重发 = 上游两次、用户扣两次，系统无法发现。

**B-5 单笔敞口无上界（P3，设计取舍）**【审计】
门户钱包冻结"全部可用余额"而非本笔上限，结算只扣 `min(供应商成本, 冻结额)`（`portalwallet.py:82-87,210-211`）→ 余额 1 的账户可发起成本 100 的请求，扣 1、平台承担 99。积分额度同理（`reserved_credit` 恒 0）。

**B-6 三处时间/路径错误（P1，确定）**【审计】
`stats.py:229,519,724,728` 仍用 `time.strftime`；`credit_watch.py:67-78,357` 用 `localtime/mktime` 分日（生产 TZ 恰好是 Asia/Shanghai 才没炸）；`operational.py:265` 硬编码 `DATA_DIR/'manager.db'` 而真实路径是 `config.DB_PATH`（可被 `WB_DB` 覆盖）。

**判决：schema 只会前进、不会后退；备份能起来但含明文凭据；迁移失败是静默的。**

- **不可回滚的库**：`schemaver.py:33-34` 明示"版本只前进，绝不还原旧库"；`release.py:373` 写 `database_rollback: False`。批准 v90（删 `usage_daily.credit`）后旧代码读不了新库。

### 3.3 该抄的六个机制（具体到可落地）

1. **Bifrost 的 `failure_class` 11 分类**：把"是否重试 / 是否换号 / 是否退避 / 是否直接失败"从 HTTP 状态码解耦。你的上游用 `400` 表示各种不同语义，只按状态码判断必然错。
2. **LiteLLM 在 fallback 前重新校验目标模型的预算与权限**：转卖场景下这是致命漏洞——"零价模型失败 → 静默落到付费模型 → 绕过预算"。你现在没有这层校验。
3. **Portkey 的策略可递归嵌套 + 按策略路径独立计熔断**：一套 JSON 表达"fallback 的 target 是 loadbalancer、loadbalancer 的槽位里再挂 fallback"。
4. **Sub2API 的粘性会话**：同一对话固定同一账号（长上下文不串号）。你的 chat 路径有 `_inject_session_key`，**responses 路径没有**。
5. **Kong 的 `X-Cache-Status` / `X-Cache-Ttl` 响应头**：让调用方自己看见缓存命中，不用来问你。
6. **Helicone 的 P2C + PeakEWMA 选号**：每次随机取两个候选取较优，用指数加权移动平均压抖动——比"最低延迟"抗毛刺，实现只要几十行。

### 3.4 明确不该抄的

- **Kong 的 Konnect 控制面/数据面分离 + license 门槛**：几十人单机，控制面是纯负债；AI 语义缓存/token 限流都在企业 tier。
- **Agent Router 的 CRD + ext-proc + 独立 ratelimit service 三件套**：为一个 FastAPI 单机引入 K8s 网关、外部限流服务和 Redis 三套运维面。
- **Bifrost 把语义缓存绑死向量库**、**默认全局开语义缓存**：聊天机器人 ROI 高，agentic 多轮流量会严重出错；转卖额度场景命中率本就低。
- **LiteLLM 的 `usage-based-routing`**：官方文档自己写"不推荐生产，Redis 每请求 incr/mget 显著加延迟"。
- **40+ guardrail 插件市场 / prompt 模板管理 / OIDC 用户同步**：平台公司抢地盘的产物，你只需要一个可插拔 hook 点。

### 4.2 勘误：本轮审计犯过一个系统性错误（2026-11-24 14:00）

**错在哪。** §2.6/§4.1 曾断言「`/api/platforms` 后端不存在，385 次 404 是控制台的功能性缺陷」。这条是**错的**。该路由由 qtgcore 兼容层提供，7 天里 **907 次 200**；385 次 404 全部发生在 **2026-11-20 14:28 之前**，是前后端版本错配的滚更窗口，之后没有再现。

**为什么会错。** 我用的是「7 天按端点分组计数」，得到 `404 × 385` 就直接下结论，**没看最后一次发生时间**。一个窗口期的旧错误，在 7 天累计视图里和当前正在发生的错误长得一模一样。

**正确的查法**（`request_outcomes` 有 `ts`，不用猜）：

```sql
-- 每个端点的状态码分布 + 最后一次发生在什么时候
SELECT endpoint, http_status, COUNT(*) AS n,
       datetime(MAX(ts),'unixepoch','+8 hours') AS last_seen
FROM request_outcomes
WHERE ts > strftime('%s','now') - 7*86400
GROUP BY endpoint, http_status
ORDER BY n DESC;
```

判据：**`n` 再大，只要 `last_seen` 不在最近一两小时，它就不是"当前故障"**，而是历史事件或滚更窗口。

**用这个方法复核了全部 11 条"404 端点"**，结论与本轮审计原文差别很大：

| 端点 | 7 天 404 | 现状 | 结论 |
|---|---|---|---|
| `/api/platforms` | 385 | 200 × 907 | 正常，404 已停于 11-20 |
| `/api/settings/proxy-pool` | 23 | 200 × 17 | 正常 |
| `/api/alerts` | 12 | 200 × 15 | 正常 |
| `/api/agents` | 8 | 200 × 4 | 正常 |
| `/api/logs/retention/status` | 8 | 200 × 4 | 正常 |
| `/api/trae/usage/stats` | 7 | 200 × 5 | 正常 |
| `/api/auth/poll` | 6 | 200 × 1,729 | 正常（404 停于 11-21） |
| `/api/checkin-logs/clear` | 8 | 401 × 1 | 需查（写端点，可能是方法/路径变更） |
| `/api/usage/token/` | 22 | 只有 404/401 | **从未成功**，待查 |
| `/api/members` | 10 | 只有 404 | **从未成功**，待查 |
| `/api/logs/attempts` | 6 | 只有 404/422 | **从未成功**，待查 |

### P3 · 架构与决策（季度内，需你先拍板）

1. **协议面收敛**：messages/responses 只修 P1-5/6，其余冻结；在 README「能力边界」里明确标注为 semi-supported。
2. **账号级熔断 + 半开探测**：需要上游 daemon 暴露选号结果，否则只能在网关侧按 `x-wb-account-uid` 连续失败下发禁用。
3. **单写者架构的上限**：现在 DB 靠全局锁串行，横向扩展为 0。若请求量翻 10 倍（≈26k/天）就必须改读写分离 + 独立写队列，否则 p99 会被 fsync 拖死。
4. **单笔敞口上界**：钱包/积分改"冻结本笔上限"需要先有定价表；这是金额风险最大的一项，但改动会触碰结算主流程。
5. **上游凭据应用层加密**：成本最高（密钥管理 + 轮转 + 迁移），先把备份加密做完再评估。

- 40+ 内容护栏插件市场
- 直接复制 New API / Helicone / Sub2API 代码（AGPL/GPL 传染 + 维护状态不佳）
