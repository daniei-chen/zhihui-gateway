# 智汇管家 / v0.0.3

看清状态，再做判断。管家沿用现有 FastAPI、SQLite 和网关计量路径，不增加另一个 AI 服务。

## 功能与权限

设置页保留现有九项，在末尾追加「管家」「预警」。管理员可查看脱敏状态、事件和投递结果；只有人类超级管理员会话可以修改预警、设置邮箱、发起测试邮件和消耗模型额度的研判。机器管理 Token 不接受这些人类会话接口。

- 管家读取资源、最近调用、预算待核对、账本通道、三平台账号池总量、任务计划、安全统计、应用限制和发布/备份证据。
- 工具不读取账号令牌、原始请求/回答、IP、用户名或配置秘密；不提供 shell、文件路径读取、重启、删除、签到、修改密钥和结清账务能力。
- DeepSeek 最多两轮模型请求、四次有限工具查询、80 秒总分析窗口；通过普通网关密钥调用 `/v1/chat/completions`，不绕过模型范围、平台范围、日配额、计量和账本。
- 当前对话只保留于页面；问题及脱敏快照会发送到所选 DeepSeek。AI 输出只是建议，不是已证实根因，也不作为告警是否触发的条件。

## 持续告警

规则采集、邮件投递和 AI 研判是三个独立任务。内置工作器持有进程生命周期文件锁，阻止两个 Manager 实例同时派发；过渡实例 `WB_BACKGROUND_JOBS=0` 不启动它。

预警覆盖存储、内存、失败率、成功调用总耗时 P95、预算 unknown、账本、备份、证书和各平台只读探针。本次稳定性版追加渠道拒绝、上游授权失败和号池不可用的稳定分类，不读取原始请求或私密上游日志。证书仅读取固定公开 certbot 回执，七天以上视为过期证据；剩余 21 天提醒，3 天内升级严重，不读取私钥，也不冒充公网证书链验收。缺失证据不填零；样本不足不会把原故障误报为恢复。采集周期 30–300 秒，异常按配置连续轮数触发，恢复要求连续两轮。

事件、每个收件人的邮件尝试、AI 任务均持久化。2026-11-01 稳定性版已取消独立 AI 补充邮件；下述降噪策略已上线，旧回执保留为历史。恢复会取消仍待发的过时故障通知。明确的连接失败/暂时拒绝最多三次安全重试；SMTP DATA 之后失联、发送进程中断均保留 `unknown`，不自动重发。人工必须核对邮箱/SMTP 证据，不提供无证据的“一键改成功”。SMTP `accepted` 只表示服务器接受，不是收件匣送达证明。

### 小汇邮件与半小时合并（2026-11-01 已上线）

- 同一规则、同一收件人，告警发送尝试建立持久30分钟窗口；故障升级、恢复后又复发均不绕过窗口。确认恢复的通知不受告警窗口限制，仍要求连续两轮恢复证据。
- 不因窗口结束重放被合并的邮件，不对持续的同一事件每30分钟刷屏；不同问题或不同收件人分别处理。明确未被SMTP接受的安全重试属于同一封邮件；结果未知不重试。重启和时钟回退不能清空窗口。
- 内置管家和独立看门狗分别实施相同策略；两者只拥有互不重叠的业务/就绪规则。旧告警定时器已停用并禁用，旧 service/OnFailure 通过追加 drop-in 转交签名看门狗，不再调用旧脚本。已在途邮件未被强制终止，原配置和历史未删除。
- 规则通知不等AI。分析若赶在原通知派发前完成，可附入同一封；否则在预警页查看已脱敏结果，不再发独立AI邮件。升级取消旧待发补充，保留既有投递历史和不确定回执。
- 发件显示名为「小汇」，沿用原SMTP账号；正文嵌入现有Z标志PNG（38,371字节），CID内联，不拉远程图片。此标志不是收件箱列表头像：后者取决于收件邮箱的联系人/品牌认证规则，SMTP不能强制设置。

SMTP 每次尝试在私有子进程中执行，凭据与邮件只走匿名管道，不进入命令行或临时文件。除 15 秒 socket 超时外另设 45 秒总时限，覆盖 DNS 和缓慢逐字节响应；到期终止并回收该子进程，保留 `unknown` 而非假定未发送。后台关闭仍等待本次有界尝试及结果持久化后再释放单实例锁；看门狗每轮三封的 SMTP 窗口最多 135 秒，不依靠 systemd 最后强杀来控制正常投递。

每轮模型请求及工具查询之前重新核对授权或当前告警策略；第一轮发送后撤销用户、关闭 AI 或恢复故障会阻止新的工具/模型轮次。已发送的上游操作不能撤回，仍按真实回执计量，不向失效会话返回分析。所有会话收尾和阻塞工作保持归属，取消不能释放仍在运行的单例槽。

已上线的交互补丁将分析任务与完成时的策略 revision、事件严重级别绑定。故障升级会取消
旧的待分析/待发分析通知；运行中的旧分析即使随后遇到降级，也不能重新变成当前结论。
修改设置、关闭 AI 或移除收件人后，旧分析在提交及 SMTP 派发前会被再次拒绝。
模型单例在任何请求发出前忙碌，仅将事件退回待分析；其他异常不按“没发送”自动重试。
该补丁有独立的签名包及生产回执，见[交互补丁回执](STEWARD-EXPERIENCE-PATCH.md)，
不使用初始 v0.0.3 的旧回执替代。

## 邮件通道与专用密钥

公开预警配置存 SQLite；凭据只由运维在服务器的受保护文件中配置，不能从面板读取或交给模型。

| 环境变量 | 文件用途 |
| --- | --- |
| `WB_STEWARD_SMTP_FILE` | 绝对路径的 SMTP JSON，字段仅 `host`、`port`、`username`、`password` |
| `WB_STEWARD_KEY_FILE` | 普通长随机 `sk-` 或兼容的 `wbk_` 调用密钥，不是管理 Token 或共享的上游密钥 |

仅接受 `smtp.qq.com` 465（隐式 TLS）/ 587（STARTTLS，先加密再登录），以及现有通道 `smtp.163.com` 465（隐式 TLS）。发信供应商与收件邮箱是两回事，可以继续通过现有 163 发件账号向 QQ 收件箱投递，不把 163 授权码拿到 QQ 服务器尝试。没有任意主机、非 TLS 或本机地址入口。文件必须是单链接常规文件，最终路径不能是符号链接，POSIX 权限不允许组/其他用户访问。文件拥有者为运行用户或 root；父目录也由运维保护，不可交给不可信用户写入。

为管家创建独立、可撤销、限制 DeepSeek 模型、限制 WorkBuddy 平台和 loopback 来源的普通密钥；设置每日 Token/积分上限，验证真实扣账后再启用定时 AI。积分上限是基于上游回执的准入控制，不是上游每次账单的硬性封顶。不要复用旧外部脚本中隐藏的 DSH/API 凭据。

## Manager 之外的看门狗

`manager/deploy/steward_watchdog.py` 仅监测 Manager 最小 `/readyz` 和管家采集心跳，不重启服务、不启动容器、不调用模型，不重复承担内置业务规则。脚本先验证签名发布闭包再导入本版邮件渲染器。

配套的 `zhihui-steward-watchdog.service` / `.timer` 已于 2026-10-31 安装并启动，实际执行与心跳核验见[发布回执](RELEASE-0.0.3.md)。独立持久队列位于 `/var/lib/zhihui-gateway/steward-watchdog/worker`（0700）；外层是 systemd 管理的 root 所有、0711 仅可穿越目录，避免下一次启动把 worker 内已有证据递归改归 root。Linux 文件锁互斥；发送前持久化 `sending`，中断转未知。发布锁持有期间最多静默 15 分钟，超时恢复观察，不能永久遮蔽故障。每轮最多三封邮件，保留未知记录；终态历史保留七天。

看门狗 Python 以 Manager 的 uid/gid 10001 读取其 0600 数据库，capabilities 和附加组为空；系统沙箱将业务目录设为只读，并屏蔽 Docker socket、账号目录和旧通知配置。SMTP 凭据文件须由运维设置为该 uid 所有、0600。该主机没有 uid 10001 的 NSS 用户记录，systemd 直接 `User=10001` 会 217/USER 失败；因此固定启动命令先由主机信任引导器校验签名、设置专用状态目录所有权，再用 `setpriv` 清空所有 capabilities/附加组并降权进入 Python。不是以 root 执行应用脚本，也不依靠待验证代码自行宣布可信。

只读数据库暂不可用时，最多使用 24 小时以内的公开策略缓存继续故障通知。当前策略读取成功时立即优先；当前策略损坏则失败关闭，不悄悄使用旧收件人。主机全部失联、邮件通道故障或系统定时器自身失效仍需独立外部监测，不能把同机看门狗称为完整灾备。

## 迁移旧“大肥鱼”通知与发布验收

初始管家批次完成通道迁移、受限普通密钥和持续策略启用；当时测试、规则及 AI 补充取得 SMTP accepted。2026-11-01 稳定性版取消独立补充邮件并完成旧 OnFailure 有限转交，旧脚本和配置仅保留取证，不再由旧单元执行。实际收件匣和受控真实故障恢复仍待验收；不导入或复制旧脚本的隐藏凭据。

1. 在发布/备份协调锁下保存旧告警脚本、配置权限与 systemd 单元的确切哈希及可恢复副本；盘点旧 timer 和 `wb-alert-onfailure@.service` 的所有调用方。
2. 服务器内迁移已经在用的 SMTP 配置到受保护的新文件，只打印字段存在性/权限检查结果，不打印授权码、邮箱明文或密钥。不修改发信供应商。新模型密钥采用独立额度，记录仅含密钥 ID 的回执。
3. 签名候选通过原严格 Linux 门禁、真实 Nginx 路由矩阵、身份/额度/回退验证，再安装新程序与单元；用 `systemd-analyze verify` 和真实沙箱读权限验证，不以模板存在替代现场验证。
4. 只在确认新内置规则及独立看门狗健康后停用旧 timer，并将既有 on-failure 调用替换为无参数的新有限接口；不能把旧 `--onfailure` 参数直接传给新脚本。避免两个系统重复发送。
5. 超级管理员从面板发一轮测试，核对持久队列、SMTP 接受结果以及实际收件匣，再验收一次受控告警/恢复、DeepSeek 工具调用及普通网关账本扣账。真实测试与合成测试分别留证。
6. 回退代码、单元与路由，不恢复旧业务数据库/用户/账号/密钥/撤销状态；新表为追加式，旧版代码回退也不得削弱已有权限和配额保护。验证回退后仍保持至少一条经过验收的告警链路。

候选代码的单元测试不证明生产已上线、QQ 邮件已进入收件匣、三平台真实推理验收或异地冷恢复已通过。完整审计中的旧账本待核对、公开领取凭据、最小权限、供应链和灾备缺口必须分别关闭，不能因新增管家功能而标为完成。

## 收件人持久性修复（2026-11-01 已上线）

- `POST /api/steward/settings/recipients` 以当前 revision 原子追加一个邮箱；`/remove` 只移除明确选择的一个。已有地址、阈值、开关全部保留，并发冲突不自动重试或覆盖。
