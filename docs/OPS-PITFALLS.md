# 运维与发布坑位清单

> 全部来自 2026-11-14 / 15 两天里的真实误判。
> **每一条都对应一次「我以为是 A，实际是 B」**，不是通用建议。
>
> **它们的共同点是：它们都不报错。** 只是让某个东西悄悄地不对 ——
> 推送没上去、权限没生效、校验把正常文件判成污染、下载到的是错误页。
>
> **会报错的容易修；不报错的会一直改不掉。** 这就是这份清单存在的理由。

## 一、`| Out-Null` 会让退出码说谎

**症状**：脚本报「推送成功」，但远端分支没有变化。

**原因**：

```powershell
git push github main 2>&1 | Out-Null
if ($LASTEXITCODE -eq 0) { "push ok" }   # ← 这个判断是假的
```

管道之后 `$LASTEXITCODE` 反映的是**管道末端命令**的状态，不是 `git` 的。

**后果**：我用假的「push ok」构建了一个**并不存在的版本**，直到 `git ls-remote` 显示远端还停在旧提交才暴露。

**正确做法**：不要吞输出，直接看它说了什么。

```powershell
git -c http.sslBackend=openssl push github main 2>&1 | Select-Object -Last 3
Write-Output "exit=$LASTEXITCODE"
```

**判据**：**远端有没有那个提交，用 `git ls-remote` 确认**，不要相信自己打印的「ok」。

## 二、不要编造提交标识

**症状**：构建报「仍然对不上（想要 X，得到 Y）」。

**原因**：只看到短形式 `0fce14f`，就凭空补全了后 32 位。

**构建是对的，我是错的。** 它拒绝了一个不存在的提交，这正是它该做的。

**正确做法**：任何提交标识都从 `git rev-parse HEAD` 读，**从不补全**。

## 三、用旧工具造新工具

**症状**：修了构建脚本的权限逻辑，但新版本里那个权限问题依然存在。

**原因**：构建脚本是**从当前发布目录取的**（`current/deploy/build-release.sh`），
而当前发布里那份**还是旧的**。**它无法把自己的修复应用到自身。**

**这不是 bug，是自举的必然。** 修复要等**下一次**构建才生效。

**判据**：改了构建脚本之后，**下一版才会用上新逻辑**；要确认，就去看新发布里的那份文件。

## 四、列举式清单会静默失败

**症状**：新加的脚本落地后是 `Permission denied`，而**发布过程完全没报错**。

**原因**：权限恢复用的是一份**手写的脚本名清单**，新脚本没加进去。
**而没人去执行它，所以没有任何声音。**

**这类失败最危险**：它不报错，只是让某个东西**悄悄地不能用**。

**正确做法**：用模式（通配）覆盖，新增自动包括；
确实需要精确控制时，**必须有一个检查去验证「清单是否漏了」**，否则等于没有清单。

## 五、注释里引用代码会让字符串匹配失效

**症状**：断言「这段代码不存在」失败，但它明明已经被删掉了。

**原因**：**注释里引用了那段代码**来说明「以前是这么写的」。按裸字符串搜索会命中注释。

**这个坑在两天里踩了三次**（构建脚本的校验、脚本的删除命令、测试的断言）。

**正确做法**：匹配**带缩进的实际代码行**（`\n        command\n`），或者只检查非注释区域。

**反过来的教训**：**写注释时引用代码是有价值的**（它记录了历史），
所以不该为了避免这个问题就不写——该改的是**检查方式**。

## 六、下载到的是错误响应，不是文件

**症状**：产物里某个文件的内容是 `{"message":"API rate limit exceeded"...}`。

**原因**：请求额度耗尽后，服务返回的是错误页，而下载代码把它当成了文件内容。
「文件非空」这一关因此通过。

**正确做法**：**两道校验**——先看**形状**（JSON 必须以 `{` 开头、不含错误标记），
再看哈希。**形状不依赖任何人填的期望值**，所以期望值本身写错时它仍然有效。

**而形状的标记必须带结构**（JSON 键名 + 值），**不能用裸词** ——
裸词会命中注释和断言，把正常文件判成污染。

## 七、`rm -rf` 之前先离开那个目录

**症状**：`fatal: Unable to read current working directory`，看起来像网络或权限问题。

**原因**：删除缓存目录时，**shell 的当前目录正在那个目录里**。
删完之后 cwd 指向一个不存在的 inode，**之后任何命令都起不来**。

**正确做法**：`cd /` 之后再删。

## 八、先用最小代价探通，再扑上去

**症状**：`git clone` 卡满超时，重试三次全失败。

**正确做法**：先 `git ls-remote --heads <url> <branch>` ——
**几秒内返回就说明通，超时就说明不通**，不要用一个要传几百 MB 的操作去试探网络。

## 九、同名资源可能不止一个

**症状**：按名字查到一个资源、删掉，但「它」还在。

**原因**：**同一个名字下存在两个不同的东西**（那次是两个同 tag 的发布，各带不同资产）。

**正确做法**：删除之前**列出全部匹配项并逐一确认标识**，不要「查到一个就动手」。

## 十、`0` 有三种含义

| 场景 | 零的含义 |
| --- | --- |
| 错误数、限流数 | **健康** |
| 「还没遇到触发条件」的计数器 | **功能正常，只是没发生** |
| 心跳、存活类 | **异常** |

**分不清就会在正常时报警、在异常时放过。** 每个指标的说明里必须写清它属于哪一种。

## 维护说明

**新增一条时请写明「症状 → 原因 → 正确做法」三件事。**

只写「不要做 X」没有用 —— 下一个人不知道为什么要避免它，就会在看起来更合理的时候再做一次。
