# 运维与发布坑位清单

> 全部来自 2026-11-14 / 15 两天里的真实误判。
> **每一条都对应一次「我以为是 A，实际是 B」**，不是通用建议。
>
> **它们的共同点是：它们都不报错。** 只是让某个东西悄悄地不对 ——
> 推送没上去、权限没生效、校验把正常文件判成污染、下载到的是错误页。
>
> **会报错的容易修；不报错的会一直改不掉。** 这就是这份清单存在的理由。

## 一、`| Out-Null` 会让退出码说谎

**症状**：脚本报「推送成功」，但远端分支没有变化。

**原因**：

```powershell
git push github main 2>&1 | Out-Null
if ($LASTEXITCODE -eq 0) { "push ok" }   # ← 这个判断是假的
```

管道之后 `$LASTEXITCODE` 反映的是**管道末端命令**的状态，不是 `git` 的。

**后果**：我用假的「push ok」构建了一个**并不存在的版本**，直到 `git ls-remote` 显示远端还停在旧提交才暴露。

**正确做法**：不要吞输出，直接看它说了什么。

```powershell
git -c http.sslBackend=openssl push github main 2>&1 | Select-Object -Last 3
Write-Output "exit=$LASTEXITCODE"
```

**判据**：**远端有没有那个提交，用 `git ls-remote` 确认**，不要相信自己打印的「ok」。

## 二、不要编造提交标识

**症状**：构建报「仍然对不上（想要 X，得到 Y）」。

**原因**：只看到短形式 `0fce14f`，就凭空补全了后 32 位。

**构建是对的，我是错的。** 它拒绝了一个不存在的提交，这正是它该做的。

**正确做法**：任何提交标识都从 `git rev-parse HEAD` 读，**从不补全**。

## 三、用旧工具造新工具

**症状**：修了构建脚本的权限逻辑，但新版本里那个权限问题依然存在。

**原因**：构建脚本是**从当前发布目录取的**（`current/deploy/build-release.sh`），
而当前发布里那份**还是旧的**。**它无法把自己的修复应用到自身。**

**这不是 bug，是自举的必然。** 修复要等**下一次**构建才生效。

**判据**：改了构建脚本之后，**下一版才会用上新逻辑**；要确认，就去看新发布里的那份文件。

## 四、列举式清单会静默失败

**症状**：新加的脚本落地后是 `Permission denied`，而**发布过程完全没报错**。

**原因**：权限恢复用的是一份**手写的脚本名清单**，新脚本没加进去。
**而没人去执行它，所以没有任何声音。**

**这类失败最危险**：它不报错，只是让某个东西**悄悄地不能用**。

**正确做法**：用模式（通配）覆盖，新增自动包括；
确实需要精确控制时，**必须有一个检查去验证「清单是否漏了」**，否则等于没有清单。

## 五、注释里引用代码会让字符串匹配失效

**症状**：断言「这段代码不存在」失败，但它明明已经被删掉了。

**原因**：**注释里引用了那段代码**来说明「以前是这么写的」。按裸字符串搜索会命中注释。

**这个坑在两天里踩了三次**（构建脚本的校验、脚本的删除命令、测试的断言）。

**正确做法**：匹配**带缩进的实际代码行**（`\n        command\n`），或者只检查非注释区域。

**反过来的教训**：**写注释时引用代码是有价值的**（它记录了历史），
所以不该为了避免这个问题就不写——该改的是**检查方式**。

## 六、下载到的是错误响应，不是文件

**症状**：产物里某个文件的内容是 `{"message":"API rate limit exceeded"...}`。

**原因**：请求额度耗尽后，服务返回的是错误页，而下载代码把它当成了文件内容。
「文件非空」这一关因此通过。

**正确做法**：**两道校验**——先看**形状**（JSON 必须以 `{` 开头、不含错误标记），
再看哈希。**形状不依赖任何人填的期望值**，所以期望值本身写错时它仍然有效。

**而形状的标记必须带结构**（JSON 键名 + 值），**不能用裸词** ——
裸词会命中注释和断言，把正常文件判成污染。

## 七、`rm -rf` 之前先离开那个目录

**症状**：`fatal: Unable to read current working directory`，看起来像网络或权限问题。

**原因**：删除缓存目录时，**shell 的当前目录正在那个目录里**。
删完之后 cwd 指向一个不存在的 inode，**之后任何命令都起不来**。

**正确做法**：`cd /` 之后再删。

## 八、先用最小代价探通，再扑上去

**症状**：`git clone` 卡满超时，重试三次全失败。

**正确做法**：先 `git ls-remote --heads <url> <branch>` ——
**几秒内返回就说明通，超时就说明不通**，不要用一个要传几百 MB 的操作去试探网络。

## 九、同名资源可能不止一个

**症状**：按名字查到一个资源、删掉，但「它」还在。

**原因**：**同一个名字下存在两个不同的东西**（那次是两个同 tag 的发布，各带不同资产）。

**正确做法**：删除之前**列出全部匹配项并逐一确认标识**，不要「查到一个就动手」。

## 十、`0` 有三种含义

| 场景 | 零的含义 |
| --- | --- |
| 错误数、限流数 | **健康** |
| 「还没遇到触发条件」的计数器 | **功能正常，只是没发生** |
| 心跳、存活类 | **异常** |

**分不清就会在正常时报警、在异常时放过。** 每个指标的说明里必须写清它属于哪一种。

## 十一、把「验证」和「提交」写进同一条命令，失败不会中断它

**症状**：提交并推送之后，才发现测试是红的。

**原因**：把「跑测试」和「`git commit`」放在同一条命令里。测试失败只是让那一段输出变红，
**后面的提交照常执行** —— 因为命令之间没有用 `&&` 串起来，也没有单独判断退出码。

**这条我犯了三次**，每次都靠 `amend` + 强制推送收拾。

**代价不只是多一次操作**：强推会改写远端历史。如果别人在那期间拉过这个分支，
他们的本地历史就和远端分叉了。

**正确做法**：**分成两次调用。**

1. 第一次只跑测试，看退出码
2. 通过了，第二次才提交

**判据**：**一次工具调用里只要既跑测试又提交，它就是错的** —— 不管当时测试是不是真的过了。
因为这个写法在测试失败时会静默地继续，而**静默的正确和静默的错误长得一样**。

## 十二、别把「配置上限」当成「限制用户」

**症状**：看到「输出被截断」的告警，第一反应是「上限设小了，该调大」。

**实际**：生产上限是 **16 MiB**，触发截断的那六次，延迟都在二十到一百秒之间 ——
**是超长回答真的撞到了上限**，不是上限不合理。

**上限的意义是防止一次请求吃掉整个进程的内存**，不是给正常回答设门槛。

**判断方法**：**先看触发时的实际大小与耗时**。如果它们离上限很近，那上限是对的；
如果它们只有上限的百分之几，那才是设错了。

## 十三、查不到，不等于没有

**症状**：某个查询返回空，于是得出「这东西从来没发生过」的结论。

**三次都踩了同一个坑**：

| 轮次 | 当时的结论 | 实际情况 |
| --- | --- | --- |
| 19 | `archive_runs` 表是空的，所以归档任务从未运行 | 表空是正确状态，任务按需触发 |
| 27 | 某段日志里没有异常，所以那段没有日志 | 换个时间点就有，且完整 |
| 32 | `endpoint LIKE '/v1/chat%'` 返回空，所以近期没有推理调用 | 两小时内 463 次，是查询写法有问题 |

**原因**：把「我的查询没找到」和「世界上不存在」当成了同一件事。
空结果有三种可能 —— 真的没有、查询写错了、查的地方不对。
**默认假设第一种，是最贵的错误。**

**正确做法**：下结论之前，**先用一个已知存在的样本验证查询本身有效**。

```
# 先确认查询方式没问题：拿一个确定存在的端点试
SELECT count(*) FROM request_outcomes WHERE endpoint='/api/release';
# 能返回非零，说明表名、字段名、连接都没问题，再去查目标端点
```

**教训**：**「没有记录」必须先问「应该不应该有记录」，再问「我是不是查错了地方」。**
前一问已经写进第 19 轮的记录，但只覆盖了「该有却没有」；后一问是这轮补上的。

## 十四、改一处之前，先把同类的地方全列出来

**症状**：修好了一处，同样的毛病在另一处还在，测试当场抓住。

**实例**：`server/qtgcore/errors.py` 里的 `install_handlers()` 从未被调用，
导致受控错误全被兜成 500。第一反应是「在 `main.py` 里加一行调用」。

加上去，四个测试立刻失败 —— 因为那个函数里**注册了三个处理器**，
不只 `QtgError` 一个：参数校验的、通用 HTTP 异常的，各自独立构造响应体。
改了一个，另外两个照样生效。

**原因**：看到一个「入口」，就以为它是全部。
**同一个函数里并列的东西，不会因为你改了一个就一起改变。**

**正确做法**：动手前先列全。

```
grep -n 'exception_handler\|^def install_\|^    def _' server/qtgcore/errors.py
```

**教训**：**「找到一处」和「找到全部」之间隔着一次列举。**
列举的成本是几秒钟，不列举的成本是一轮发版作废。

## 十五、版本面用 bump 之后的提交号，改动用代码提交号

**症状**：部署脚本用代码提交号去取 `VERSION`，拿到的是上一版的版本号。

**原因**：发布拆成两个提交 —— 先提交改动，再 `bump_version.py` 提交版本面。
`VERSION`、`product-release.json`、`provenance` 这些**只在后一个提交里才是新的**。

用前一个提交号去取，拿到的自然是旧值。**它不会报错，只会安静地给你上一版。**

**正确做法**：

```bash
code=$(git rev-parse HEAD)      # 改动提交 —— 用于 source_commit
python tools/bump_version.py X  # 产生版本面
git commit -m 'chore(release): X'
sha=$(git rev-parse HEAD)       # 版本面提交 —— 用于取 VERSION / provenance
```

取文件时按用途分开：**代码类文件用 `code`，版本面文件用 `sha`**。

**教训**：**两个提交号各管一半，混用不会失败，只会拿错。**

## 十六、检查工具不能改变被检查对象

2026-11-25 写了一个「发布前用新版本代码校验配置」的脚本，第一次在生产试跑就把发布树搞脏了：

```
REJECTED: 发布树里有 __pycache__：/opt/workbuddy-manager/releases/v1.5.85/server/__pycache__
```

脚本 `sys.path.insert` 到发布目录后 import 了 `server.configcontract`，
Python 默认把 `.pyc` 写进 `server/__pycache__`，而**发布树的完整性校验拒绝任何 `__pycache__`**。

**seal 直接失败。**

修法是在任何 import 之前：

```python
sys.dont_write_bytecode = True
```

`healthcheck.sh` 里也有同类风险的写法（临时文件），所以那里定了规则：
**巡检里唯一的 `rm` 只允许删它自己建的 `/tmp/hc-*`**，并用测试扫脚本守住。

**推广**：任何「读取/校验」类工具，落地前问一句「它会不会在目标目录里留下东西」。
缓存文件、锁文件、临时文件、日志，都算。

## 十七、测试通过 ≠ 测试被执行

改动加了 5 个用例，跑门禁显示 **1,117 passed**，和改之前**一模一样**。

原因是 `tools/ci_regression.py` 不是自动发现，而是**显式列出的模块名**。
新文件不在列表里就永远不会被跑，而输出照样是绿色的「全部通过」。

加入列表后变成 **1,122**。

**判据**：**新增测试后，门禁的用例数必须变。**数字没变就是没跑。
这比看「是否通过」可靠 —— 没跑的东西永远不会失败。

## 十八、代码里的默认值不是线上值

查一次「首字节 87 秒」的告警时看到：

```python
class Budgets:
    first_byte_s: float = 60.0      # ← 代码默认值
```

87 > 60 却返回 200，看起来就是「预算没生效」的真 bug。查下去才发现 systemd drop-in 覆盖成了：

```ini
Environment=WB_FIRST_BYTE_TIMEOUT_S=240
```

**240 秒，87 秒完全正常。**而且 240 是有意放宽的 —— 注释写明「60s cap 会造成慢上游 502，2026-10-26 回归修复」。

**三个不同的东西**：

| 来源 | 值 | 是不是「现状」 |
|---|---|---|
| 代码里的默认值 | 60 | 否 |
| 配置文件里的注释 | 180 | 否（注释过期了） |
| systemd 实际生效 | **240** | **是** |

**推广**：`grep` 到 `SOMETHING = 123` 只是「默认值是 123」。
要知道现状，得去 `systemctl show -p Environment`、`/api/release`、实际数据里看。

同类错误在这一章里反复出现（第 10 次计数），归到一条：
**测量工具会骗人，且骗的方式千变万化。**

## 维护说明

**新增一条时，写成「症状 → 原因 → 正确做法」三段。**

只写「不要做 X」没有用 —— 下一个人不知道为什么，就会在看起来更方便的时候再试一次。

**每条都必须对应一次真实的失败**，不要写通用建议。通用建议读起来都对，
但一条也记不住；真实失败有细节，细节才记得住。

## 十九、纯文档提交也能让 CI 变红

2026-11-25 有一次 CI 失败，提交是 `75431fc`（只改了 `docs/OPS-PITFALLS.md`）：

```
FAIL: test_reviewed_patch_files_match_current_source
AssertionError: '264ef1f1518ca35434ea453d87425c2f470acdcf657ce957cba8721236ae4f10'
                not found in {'00...}
Ran 1127 tests
FAILED (failures=1)
```

### 为什么

`server/release-provenance.json` 里的 `reviewed_patch_files` 记着受保护文件的哈希。
测试要求每一个记下的哈希都能在当前源码里找到：

```python
for relative, expected in files.items():
    self.assertIn(expected, self._source_hashes(path), relative)
```

**这个断言只看源码状态，与「这次提交改了什么」无关。**

所以：如果版本面文件（`VERSION` / `product-release.json` / `release-provenance.json` /
`writer-capabilities.json`）处于「已经升过版本、但 `reviewed_patch_files` 没跟上」
的中间态，那么**下一个提交** —— 哪怕只改一个 markdown —— 都会把它带到 CI 上，红。

### 这次的成因

`bump_version.py` 会重算 `reviewed_patch_files`。但如果在某个环节漏了重算，
或者手工改过受保护文件却没跑 `deploy/protected-customizations.py --update`，
就会留下一个对不上的哈希。

它不会立刻暴露，而是**等到下一次推送到 CI 时才炸** —— 而那时推送的人
很可能正是「只是改了个文档」的那个人，于是第一反应会是「我什么都没动」。

### 怎么避免

**① 收尾时跑一次全门禁，哪怕这次只改了文档。**

```bash
python tools/ci_regression.py    # exit 0 才能推
```

成本是几分钟；不跑的成本是 CI 红一次，而那条红会挂在历史上。

**② 出现这类失败，先看 `git log` 里上一个碰过版本面文件的提交。**

`75431fc` 自己什么都没改坏 —— 它只是第一个把既存的不一致带上去的提交。

**③ 记住 `_source_hashes` 返回的是集合，不是单值。**

它同时接受 LF 与 CRLF 两种行尾的哈希（这个项目在 Windows 上开发、Linux 上部署）。
所以「哈希对不上」不是行尾问题 —— 别往那个方向查。

### 一句话

**CI 检的是仓库的当前状态，不是你这次提交的意图。**
