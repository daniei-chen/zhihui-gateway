# 同类竞品调研（2026-11）

> 目的：判断智汇网关「该补什么、不该跟什么」。
>
> 调研对象不是随便挑的：只取**同样把多个上游账号收敛成一个 API**的项目，以及
> 在**可观测性**上做得最深的项目。纯 SaaS（OpenRouter）与纯可观测（Helicone 托管版）
> 只在指标口径上参考，不作为功能对标。

## 一、结论先行

**智汇不需要跟进「多提供商聚合」。** LiteLLM / New API / One API 的核心卖点是
把 100+ 家服务商收敛成一个 key，而智汇的上游是**一条** WorkBuddy 授权链路
（多账号、同模型）。追这个方向等于换产品，不是改进产品。

**真正该补的是可观测性。** 所有竞品在这件事上都比智汇做得深，而智汇的审计
（`docs/AUDIT-2026-11-24.md`）也独立得出同一结论（P1-3 事件循环延迟、
P1-4 TTFT）。两条独立路径指向同一处缺口，这个结论比任何单一来源都可靠。

## 二、对比表

| 维度 | LiteLLM | New API / One API | 智汇网关 |
|---|---|---|---|
| 定位 | 多提供商代理（100+） | 多提供商中转 + 分销 | **单上游多账号**的受控授权与路由 |
| 路由 | `fallbacks` 链、`budget_fallbacks`、负载均衡 | 渠道池，失效自动切 | 账号池 + 健康检查 + 冷却 |
| 计费 | 虚拟 key、per-model 预算、spend logs | 兑换码、CNY 计费、多租户 | `usage_events` 不可变账本、`credit_units`、对账 |
| 预算耗尽 | `budget_fallbacks` 静默切到备用模型 | 拒绝 | 拒绝（错误可见） |
| 可观测 | spend logs、回调、Langfuse/OTel 集成 | 渠道状态、日志 | 巡检脚本 + `request_outcomes`；**缺 TTFT 与事件循环延迟指标** |
| 协议 | OpenAI 兼容 | OpenAI 兼容 | **OpenAI + Anthropic + Responses 三套并原生** |
| 发布 | 常规重启 | 常规重启 | **滚动中继零停机**（6 秒空窗由中继重试兜住） |
| 数据完整性 | 可改 | 可改 | `usage_events` 带 UPDATE/DELETE 触发器，**账本不可变** |
| 许可 | MIT（企业版闭源） | MIT / AGPL 分支混杂 | 自有 |

## 三、值得学的两个具体做法

### 1. `budget_fallbacks` 的思路：降级优于报错

LiteLLM `v1.92.0` 起支持：某个 key 对某模型的预算耗尽时，**不返回 `budget_exceeded`**，
而是按预设链切到下一个还有预算的模型，spend 记在备用模型上。

智汇**不适用**它的实现（没有多模型链），但**思路可以借**：当上游账号池里
某个账号额度耗尽时，现在是「换账号」；当**整池**额度都低时，现在是硬报错。
一个更温和的做法是把这种状态**提前暴露在巡检里**（用户还没撞上之前就看到），
而不是等人撞上 429 才排查。

这条**不需要改计费链路**，只需要在巡检/告警里加一项「池内剩余额度水位」。
属于 P2，但比「预算降级」便宜得多、风险也小得多。

### 2. spend logs 的可追溯性

LiteLLM 的 `/spend/logs?api_key=` 能把每一笔花费归到具体 key、模型、部署。
智汇的 `usage_events` 在**数据完整性**上更强（不可变），但**对外可查性**弱：
管理员要回答「这个 key 昨天花在哪」得靠 `stats` 页面，而审计指出它的
`GROUP BY key_id` 是全表扫（P2-2），对账页 P95 超过 300 ms。

所以**不该照抄它的表结构**，该做的是审计已经写好的 P2-2（补 `(key_id, ts)`
覆盖索引或走 `usage_daily` 汇总表）。

## 四、明确不该跟的三件事

| 不跟 | 理由 |
|---|---|
| 多提供商聚合（100+ provider） | 换产品，不是改进。上游是业务约束，不是技术选择 |
| 语义缓存 / 向量召回 | 审计已明确反对。推理结果缓存会破坏「同 prompt 不同回答」的预期，且计费口径会变得不可解释 |
| 导入 AGPL 竞品代码（New API 部分分支） | 许可污染。智汇现有实现是自有的，没有理由引入 |

## 五、落到下一轮的具体动作

按投入产出排序：

1. **P1-4 TTFT 统计 + 挂住账号冷却**（审计估 1d）。竞品普遍有首字节时间指标，
   智汇没有。上游单账号挂住时，现在只能看到整体错误率上升，定位不到账号。
2. **P1-7 对账接进 15 分钟循环**（审计估 2d）。`usage_events` 的不可变性已经保证了
   「账本不会被改」，但**漂移不会自己报警**，仍靠人翻账。
3. **P2 池内额度水位进巡检**（本条调研新提出，成本最低）。把「整池额度将尽」
   在巡检里提前说出来，避免用户先撞上 429。
