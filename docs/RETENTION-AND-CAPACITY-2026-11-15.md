# 数据保留与容量规划 — 2026-11-15 实测

**结论先说**：保留策略是**设计好的且在生效**，当前**没有紧急风险**。
唯一无限增长的是几张账本表，按实测速率算，**大约七年**才会占满剩余空间。

---

## 一、保留策略（代码里读到的）

`retention.py` 把每张表归入一个类别，并给出动作：

| 表 | 类别 | 动作 | 保留天数 |
| --- | --- | --- | --- |
| `request_logs` | 派生日志 | **归档后清理** | **90** |
| `request_outcomes` | 派生日志 | **归档后清理** | **90** |
| `usage_events` | 账本事件 | 不删 | 永久 |
| `forwarding_events` | 账本事件 | **不删** | **永久** |
| `attempt_events` | 账本事件 | 不删 | 永久 |
| `usage_reset_events` | 账本事件 | 不删 | 永久 |

另有 `budget_reservations` 也在归档清单里。

**这个划分是有道理的**：

- **派生日志**（请求记录、结果）可以从别处重新推导，所以**到期归档再删**
- **账本事件**（用量、转发、尝试）是**计费与审计的依据**，删了就不可恢复，所以**永久保留**

**账本表不删是刻意的，不是漏了。**

## 二、为什么现在看不到归档痕迹

`request_logs` 里最老的记录是 **2026-09-14**，距今 **62 天**。

**62 < 90，所以还没有到触发点。** 这是正常的，不是「归档坏了」。

**顺带说明一个容易误判的地方**：`forwarding_events` 里最老的记录是
2026-10-05 —— 那是因为这张表**不在归档清单里**（永久保留），
不是因为它比 `request_logs` 年轻。

## 五、一个必须先说清的误解：归档**不释放空间**

我最初写的是「`request_logs` 有 90 天保留，所以会进入稳态」。**那句话是错的。**

归档目录是这么定的：

```python
out_dir = Path(out_dir or (config.DATA_DIR / 'archives'))
```

**`DATA_DIR` 就是数据库所在的那个目录。** 也就是说：

> 90 天后，行从**主表**搬到**同一块盘上的归档文件**，然后从主表删除。

**总占用不会下降** —— 只是从「一张大表」变成「一张小表 + 一堆归档文件」。

### 那保留策略有什么用

**它优化的是「主表大小」，不是「磁盘占用」。**

主表小了，这些操作都变快：

- 按时间范围的查询（索引更小）
- 写入（B 树更浅）
- 备份里的主库更快

**所以它不是白做的，但它的收益在性能侧，不在容量侧。**

### 作者知道这件事

`archiveworker.py` 里有一道检查：

```
if shutil.disk_usage(out_dir).free < 256 * 1024 * 1024:
    （跳过本轮归档）
```

**剩余不足 256 MB 就不归档。** 这行代码的存在本身就说明
「归档会占空间」是已知前提。

## 六、所以真实的容量画像

| 项 | 会不会无限长 |
| --- | --- |
| `request_logs` | 主表**会稳定**（90 天），但**归档文件持续增长** |
| `request_outcomes` | 同上 |
| `forwarding_events` | **无限增长**（无归档） |
| `attempt_events` | **无限增长** |
| `usage_events` | **无限增长** |

**「总占用」这一列没有一张表会稳定下来** —— 只是增长速度不同。

按实测，`forwarding_events` 每天约 2.3 MB。**其余几张账本表没有单独测**，
但它们加起来目前是 ~107 MB，比 `forwarding_events` 还小一些。

## 七、这份分析没有覆盖的

- **归档文件的实际体量**（目录还不存在，说明**归档从未跑过** —— 62 天 < 90 天）
- **索引与空闲页占比** —— 629 MB 里表数据约 359 MB，其余是索引与可能的空闲页
- **`VACUUM` 策略** —— 没有查是否定期整理
- **备份的体量** —— 它比数据库本身更占地方（另见磁盘预算记录）

## 八、现在要不要做点什么

**不用急着动。** 按实测数据，最近的瓶颈不是数据库。

**如果要做容量治理，优先级是**：

1. **决定归档文件放哪** —— 现在和主库同盘，等于「换个地方存」。
   如果目标是省盘，得把它挪到别的卷或对象存储
2. **`forwarding_events` 的分区或冷热分离** —— 它是唯一无上限且量最大的
3. **一次性 `VACUUM`** —— 清掉删行留下的空闲页（需要短暂写锁，要挑时间窗）

**第 1 条是这一版新发现的认知差**：一直以为「有保留策略 = 占用会稳定」，
**实际上它只稳定了主表**。
