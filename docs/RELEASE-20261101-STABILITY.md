## 现在的请求链路

```text
客户端：达到 256 KiB 才尝试 gzip；至少节省 10% 才使用（需客户端接入）
  → Nginx：128 MiB，连续停传 60 秒
  → Manager：鉴权先行，有界 gzip 解码与 JSON 校验
      上传累计 180 秒 / 停传 60 秒，先到者生效
      入站及转换后单请求各 128 MiB，保留字节总预算 384 MiB，大请求并发 16
  → WorkBuddy：单请求 128 MiB，原始 body 总预算 256 MiB，32 个租约
  → 官方上游：达到 256 KiB 采用最快级 gzip，至少节省 10% 才发送压缩体
```

Manager 到本机 WorkBuddy 的回环传输不额外压缩，避免重复压缩的 CPU 成本。
服务端不能替第三方客户端压缩已经上传到服务器之前的字节；配套 helper 见
`manager/client/zhihui_upload.py`。128 MiB 是上传字节上限，不会提高模型上下文、
图片格式或供应商本身的额度。Qoder、Trae 的独立引擎限制仍需分别遵守。

CRC、完整结束、压缩前后体积和总预算分别校验；不接收拼接 gzip 成员、尾随内容、
叠加编码或损坏压缩包。过载拒绝不判成账号故障，不无证据重放推理。
这些是保留字节预算，不是整个 Python/Go 堆内存的上限。
