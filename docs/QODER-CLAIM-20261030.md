## GitHub 对照

只阅读源码，没有运行第三方脚本，也没有整体替换生产引擎。

1. [当前引擎的同类问题 #20](https://github.com/shuishuipingan/qoder2api-hub/issues/20)：
   `ok` 代表执行未报错，不代表发放；必须区分已领取、无活动、名额耗尽与真实新增。
   [相应修复](https://github.com/shuishuipingan/qoder2api-hub/commit/1e2e9f32ef649a53091edb203eb7b5590e990d3b)
   也没有承诺每次执行必得积分。
2. [Zhengyuuuui/qoder2api 的固定版本](https://github.com/Zhengyuuuui/qoder2api/blob/8d49aa6e8262ca67b2ffc511292541b1197c6db2/checkin.go)：
   从 campaign 查询可领取项，再区分 `CLAIMED` / `replayed`；指出旧签到接口的
   409 可能不是有效领取事实。不过其历史统计存在默认补记 100 的路径，不能照搬。
3. [Buddy2api 的固定版本](https://github.com/wicm84266964/Buddy2api/blob/16a18af04fde8cd22c3e69ccfb1cce9045ac0ac1/providers/qoder/checkin.py)：
   分离 `claimed`、`already_claimed`、`no_campaign`。但它会把非已领取的未知活动状态
   当作可领取，且对空成功响应/409 的判断较宽，不能直接替代我们的确认边界。

三者都依赖上游活动资格与发放状态，不存在可靠的「强制到账」方案。
当前引擎已采用 campaign 领取而非只调用旧签到接口；未确认新增接口缺陷前，
不通过反复 POST、改造设备身份或跳过官方任务来试探发放。
