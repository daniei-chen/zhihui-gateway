# 路由与性能盘查 — 2026-11-15

上一版把可达性盘查的范围限定在 `qtgcore`。这一版补上**顶层路由**，并顺带量了性能。

---

## 一、路由：244 条全部注册

用 AST 解析源码，而不是靠请求逐个试。

### 1.1 方法

1. 解析主入口里所有 `include_router(...)` 调用，取出被注册的变量名
2. 解析这些变量名对应的实际模块名
3. 遍历 `routers/` 下每个文件，统计路由装饰器数量
4. 比对：**声明了路由的模块，是否都出现在已注册集合里**

### 1.2 结果

| 项 | 值 |
| --- | --- |
| 定义了路由的模块 | **24 个** |
| 路由总数 | **244 条** |
| 已注册的模块 | **24 个（全部）** |
| **声明了但未注册** | **0 个** |

**这是好消息**：上一版担心的「顶层路由有遗漏」不成立。

`qtgcore` 那五个 compat router 也在其中 —— 它们通过 `_QTG_INTERNAL` 前缀注册，不是遗漏。

## 二、重复路由：是设计，不是缺陷

盘查中发现**多组相同的 路径+方法 声明**：

| 路径 | 两处声明 |
| --- | --- |
| `GET /api/stats/summary` | `stats.py` 与 `compat_stats.py` |
| `GET /api/stats/upstream` | `stats.py` 与 `compat.py` |
| `GET /api/upstreams` | `upstreams.py` 与 `compat_fixes.py` |
| `POST /api/upstreams` | `upstreams.py` 与 `compat_settings.py` |
| `GET /api/status` | `accounts.py` 与 `compat_fixes.py` |

### 2.1 为什么不冲突

主入口的注释写明了意图：**compat 系列最后注册，作为兜底；真实 handler 必须在前**，
否则请求会打到 compat 的空实现上。

核对注册顺序：`accounts`（432 行）、`stats`（439）、`upstreams`（449）、`gateway`（491），
compat 系列在 **535 行**。**顺序正确。**

### 2.2 但两条路都会走

路径重写机制按平台头分流：带平台头的 `/api/stats/*` 会被改写到内部前缀，
走 compat 那一份；不带平台头的走 `stats.py`。

### 2.3 关键：compat 那一份是完整实现

抽查了 `compat_stats` 的统计汇总：它按平台分别调用上游实现、按 realm 校验参数、
没有账号时返回全零而不是报错。

**不是空壳。** 所以两条路都能给出正确答案，重复是**刻意的平台分流**，不是冗余。

## 三、性能：网关不是瓶颈

用生产指标实测（进程启动后累计，覆盖最近一小时窗口）。

### 3.1 端到端延迟

| 分位 | 值 |
| --- | --- |
| P50 | **4 995 ms** |
| P95 | **10 206 ms** |
| P99 | **29 151 ms** |

**只看这三个数会觉得网关很慢。但它们包含上游大模型推理时间。**

### 3.2 首字延迟（关键对照）

| 项 | 值 |
| --- | --- |
| 样本数 | 34 |
| 总耗时 | 137.5 秒 |
| **平均首字** | **4.04 秒** |
| ≤2 秒 | 9 次 |
| ≤5 秒 | 30 次 |
| ≤10 秒 | 32 次 |

### 3.3 结论

**总延迟 P50 约 5.0 秒，首字平均 4.0 秒** —— 差值约 **1 秒**。

也就是说：**一次请求里，绝大部分时间在等上游吐第一个 token 和后续生成，
网关自身的处理开销在 1 秒量级。**

配合另外两个数更能说明问题：数据库 659 MB，最常用的查询按小时过滤 24.9 万行
耗时在毫秒级；网关在飞请求 1、排队 0 —— **没有积压**。

**所以「网关慢」这个方向不成立。** 若要压缩端到端延迟，着力点在上游选择与模型，
不在网关代码。

## 四、一个未定位的问题

这两版跑回归时都撞到：`test_proxy_routes_api` 的 2 条失败，**单独跑通过**，
无本版改动时同样失败 —— 确认是**测试之间的互相污染**。

### 4.1 已经排除的

| 怀疑对象 | 排除理由 |
| --- | --- |
| 测试文件改全局配置没还原 | 它的 patch 都在 `tearDown` 里 stop 了 |
| 数据库连接残留 | 基类已经重置连接并重连 |
| 配置被缓存 | 读取方每次都取当前值，不缓存 |

### 4.2 所以根因未定位

**我停在这里，没有继续。**

理由是：确认「pre-existing」只需一次暂存对照，而定位需要逐文件 bisect 多轮。
**把它记成「未定位」比猜一个原因更有用** —— 猜错会让下一个来修的人走错方向。

### 4.3 它为什么仍然值得修

**测试污染会产生假阳性。** 这两版我两次撞到同一组失败，两次都要额外花一轮去确认
「不是我改坏的」。**这个成本会随着审计轮次持续计费。**

## 五、这轮没做什么

- 没有核对每条路由的**权限装饰器**是否与权限矩阵一致（那是另一个维度）
- 没有盘 `services/` 目录下模块的可达性
- 没有定位测试污染的根因
