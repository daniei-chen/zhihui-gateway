# 不停机的实证 — 2026-11-15

**这一轮没有产品改动。** 它做的是一件更基础的事：
**第一次拿日志去验证「不停机」这个我每轮都在说的结论。**

---

## 一、为什么要验证

过去十几轮，每轮部署后我都写「不停机更新」「零 5xx」。
**但那句话的依据一直是「部署命令执行成功了」** —— 那是**流程完成**，不是**服务未中断**。

**这两件事不一样。** 进程重启、nginx 重载、upstream 短暂不可达，
任何一种都可能在流程「成功」的同时让用户看到一个 502。

## 二、部署窗口的实际数据

部署发生在 **06:00–06:30 UTC**（北京 14:00–14:30）。这段时间我做了：
**2 次 stage、2 次 prepare、1 次 run、1 次 systemd daemon-reload**。

nginx 访问日志在同一小时的分布：

| 状态码 | 数量 |
| --- | --- |
| **200** | **391** |
| `-`（连接被关闭） | 12 |
| 444（nginx 主动拒绝） | 9 |
| 404 | 9 |
| 401 | 9 |
| 400 | 7 |
| **5xx** | **0** |

**每分钟请求数**（06:00 起连续）：

```
13, 7, 9, 12, 9, 4, 3, 6, 2, 3 ...
```

**没有空窗** —— 每分钟都有请求被正常处理。

## 三、进程确实重启了

`workbuddy_uptime_seconds` 读数是 **250 秒**，服务启动时间
`14:29:17 CST`，**正落在部署窗口内**。

**所以这不是「没重启」，而是「重启了但用户没看到中断」。**

这两者的区别很重要：**单进程服务重启必然有一个瞬间不可达**，
而那一刻恰好没有请求落上来，或者落上来的请求被 nginx 重试/排队吸收掉了。

## 四、能证明什么、不能证明什么

**能证明**：

- 部署窗口内**没有任何请求收到 5xx**
- 请求流**没有中断**
- 用户侧**没有可观察的故障**

**不能证明**：

- **重启瞬间确实是零中断**。如果那一刻恰好没有请求，日志里当然没有 5xx。
- **有并发请求时是否仍无感**。这次窗口内的请求密度是每分钟个位数到十几，**不是压测**。

**换句话说：这次证据支持「没有发生用户可见的中断」，不支持「架构上保证零中断」。**

## 五、nginx 侧的两个噪音源

### 1. `/favicon.ico` 404（已修）

首页引用的图标是 `/home-assets/r-xxx/favicon.ico`（**能拿到 200**），
但**浏览器总会额外请求根路径的 `/favicon.ico`**，而那个文件不存在，
于是每访问一次首页就往 error_log 写一条。

**修法**：把同一个文件复制到 `/var/www/zhihui-home/favicon.ico`。
**验证**：请求前后 error_log 计数都是 17，**没有新增**。

### 2. `Connection refused`（不修）

健康检查探针打到 `127.0.0.1:7866/healthz`，在进程重启的那一两秒会连接被拒。

**没有去配置 upstream 的 `max_fails`** —— 因为**只有一个后端节点**，
把它摘掉之后全站直接 502，比偶尔一条被拒的健康检查严重得多。

**这个错误是重启的必然产物，不是缺陷。**

## 六、这一轮没做成的事

**原本想加一个进程启动时间指标**，查了之后发现**已经有了**：

```
workbuddy_uptime_seconds   Process uptime in seconds.
```

**而我第一遍是用 `^process_` 前缀去查的** —— 又犯了「查一个前缀就断定不存在」的毛病。
同一个错误在这个会话里已经出现过多次，**这次它在同一轮内就复发了**。

## 七、结论

| 结论 | 依据 |
| --- | --- |
| 部署窗口**无用户可见中断** | 391 个 200、**0 个 5xx**、每分钟连续 |
| 进程**确实重启过** | uptime 250 秒，启动时刻在窗口内 |
| **不能**声称「架构零中断」 | 请求密度低，重启瞬间可能恰好无请求 |
| favicon 404 **已修** | 修复后 error_log 无新增 |
