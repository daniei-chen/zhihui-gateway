# 一份源码，三种身份

智汇产品的唯一源码与升级来源是 [`daniei-chen/zhihui-gateway`](https://github.com/daniei-chen/zhihui-gateway)。
这不是模型供应商地址，也不是把 WorkBuddy、Qoder、Trae 引擎改成 GitHub 服务。

| 身份 | 本版约定 | 含义 |
| --- | --- | --- |
| 当前源码产品版本 | `1.3.1` | 三步发布收成一条命令 —— 不再依赖记忆 |
| Manager 组件基线 | `v10.7.22+audit.20261029.2` | 继承源码的审计基线，不参与产品版本比较 |
| 源码与分发身份 | 输入源树 SHA256 与 Git commit SHA 分列 | 签名包绑定输入，公开分发提交在验收清单关联，不回写伪造先验提交 |

同一产品版本的部署可以使用独立构建标识，例如
`v1.3.1+build.20261114.1`。它只用于不可覆盖的发布目录、运行身份核验与回退，
不新增一条产品版本：界面和更新比较采用 `1.3.1`。部署时的 `.version`
与目录名一致，并受签名和完整测试回执覆盖；绝不覆盖已有发布目录。

这是产品版本归一，不是把旧组件版本当作产品的远端竞争版本。
历史发布目录、签名与回退证据保留原名；新版本比较在产品版本空间内进行。
旧的无仓库身份缓存不再用于新版本检测。

1.3.1 的功能、门禁与验收边界见仓库 [CHANGELOG](../CHANGELOG.md)、[上游复核](UPSTREAM-REVIEW-2026-11-14.md)、[线上审计](PRODUCTION-AUDIT-2026-11-14.md) 与 GitHub Release；更早文件保留原版本，只代表历史记录。源码拉取工具仍须提供匹配的完整提交 SHA；拉取不等于安装批准。旧网页覆盖安装已退役。

## 升级链路

```text
你的 GitHub 仓库
   │ 固定 commit / 经核对的 tag（不直接安装 main 最新状态）
   ▼
新源码工作目录 → 依赖锁 → 构建 → 隔离测试
   ▼
逐文件哈希 + Ed25519 签名 + 绑定输入与运行时的测试回执
   ▼
最低状态兼容检查 → 受控发布 → 运行身份与健康核验 → 记录版本与源码提交
```

`tools/repository_source.py` **只负责拉取固定源码，不负责安装或重启**：

```bash
python3 tools/repository_source.py \
  --commit <经审批的完整40位提交SHA> \
  --tag v0.0.3 \
  --destination /path/to/new/zhihui-source
```

它固定产品仓库，拒绝覆盖现有目录，核对 tag/commit/VERSION，且不接收任意仓库 URL。
拉取成功不等于产物可信或已部署；不能拿源码下载摘要代替受信签名。

## 三平台上游交接

v1.2.25 的 Qoder 与 Trae 数据面分别读取受保护的本机路由交接文件：
`/opt/workbuddy-manager/engine/var/qoder_gateway_base` 与
`/opt/workbuddy-manager/engine/var/trae_gateway_base`。缺失、非法或不安全的文件
会回退到签名版本中的可信默认端口；路由交接不包含凭据。
候选实例必须先在独立端口完成镜像摘要、运行身份、只读根文件系统和健康检查，再由受控发布器把稳定 relay 指向候选，最后用发布包内的工具原子写入 relay 地址：

```bash
python3 deploy/trae_route.py http://127.0.0.1:7867 \
  --route-file /opt/workbuddy-manager/engine/var/trae_gateway_base
```

Qoder 使用同一工具和校验合同，只需指定 /opt/workbuddy-manager/engine/var/qoder_gateway_base：
```bash
python3 deploy/trae_route.py http://127.0.0.1:8801 \
  --route-file /opt/workbuddy-manager/engine/var/qoder_gateway_base
```
工具拒绝公网地址、凭据、路径和非法端口；父目录必须已存在且不可被组或其他用户写入。root 发布时路由文件固定为 `root:10001`、`0640`，非 root 开发测试使用私有 `0600`。网关遇到缺失或不合规的路由文件会回到各平台的可信默认端口。路由文件只包含地址，不包含密钥；切换前后的健康、排空、账本和回退证据仍必须由受控发布器记录。

Manager 的不停机候选必须使用发布包内的 `deploy/workbuddy-web-helper.service`，并完整继承当前 serving 代的 admission 参数（容量、请求体预算、队列和密钥并发）；缺少任一参数会被共享 admission ledger 以 `shared_admission_policy_changed` 拒绝。relay 以 UID/GID `10001:10001`、只读状态运行，root 发布工具写出的路由文件合同为 `root:10001`、`0640`，不能把 root-only 的 `0600` 文件直接交给 relay。

## 回退不是时光倒流

回退代码/前端时不恢复旧账号、额度账本、设备授权和会话撤销状态。
必须检查数据库/接口向前兼容性，失败保留仍可能接收流量的实例，不能盲杀 helper。
角色与每日额度写入后，回退目标必须继续执行这些规则；旧版本仅能读取新表不等于安全可回退。
历史 `manager/.github` 和 `manager/deploy` 中的安装模板仅为继承组件参考，
不代表本机可信工具已被重新安装，也不应直接用于覆盖运行服务。

## 不夸大的边界

产品版本不是“所有审计项已关闭”的认证。真实供应商计量缺失仍记为未知；
没有付费端到端推理证据就不声称已完成供应商验收；本机加密备份不等于离机灾备。
前端来源为 reconstructed-source，新的 Git 提交不冒充复现历史原始提交。
新增管理能力、三平台授权边界与原生浏览器实验状态分别见
[授权合同](AUTHORIZATION.md)和[服务器代管浏览器](SERVER-ASSISTED-AUTH.md)。

## 最近的版本更新

这一节由 `CHANGELOG.md` 同步而来。**产品内的更新日志以前只写「详见仓库 CHANGELOG」** —— 那等于让人跳出去看，而这里本来就该写清楚。

## [1.3.1] - 2026-11-15

**归总版。这一版没有新功能，它把几百个版本做过的事收成一份可查的账，并修掉两件真实影响用户的事。**

**一、管理端登录全挂，原因不在应用**

当晚管理端所有人无法登录，页面显示「服务暂时不可用」。
**数据面 `/v1/*` 一直正常，`/healthz`、`/login`、`/dashboard/` 也正常** —— 只有 `/api/*` 全 503。
根因是 nginx 配置里的两行维护开关，写在 `server` 块最前面，**早于所有 `location`**，
所以下面那些精心配置的登录限流与转发一条都没机会执行。
**它是计划内的维护，而用户看到的是故障。** 恢复方式是注释这两行并平滑重载，**没有重启任何服务**。

**二、登录失败时，快到锁定了才告诉用户还剩几次**

有用户连续输错几次后来问「密码是不是换了」—— 因为每次都是同一句「用户名或密码错误」，
**他不知道自己已经接近锁定**。
计数本来就在手里，只是没往外递。现在**只在剩余一两次时**提示 ——
全程报进度等于把「还能试几次」送给爆破方，而临近锁定这条信息对正常用户最有用、对攻击者最没用。

**三、日志索引补齐到全覆盖**

**一百零七份文档里，索引只覆盖四十四份。**
补齐的方式是把未索引的分成两类：**仍然有效的技术说明**（四十三份）与**早期发布记录**（二十份）。
历史那部分保留，是为了查「当时为什么这么做」，但其中描述的做法不一定还适用于现在。
**还发现索引覆盖率检查本身有盲区**：它的字符集只认 ASCII，而其中一份文档的文件名是中文的 ——
**那条检查一直是绿的，但它从来没有检查过那份文件。**

**四、服务器清理**

清掉测试与构建残留、旧版本数据目录、早期发布快照，**共约 2.6 GB**，磁盘从 67% 降到 63%。
**只清确认无引用的东西，全程没有重启服务，清理前后都做了服务与公网探测。**
**日志没有动** —— 那是审计依据，不该为了腾空间删掉。

**五、这一版改了什么**

- `server/` 两处：登录失败提示带剩余次数、计数函数返回值
- `docs/` 索引与一份复盘
- **没有对外协议变更，没有数据库结构变更**

## [1.2.198] - 2026-11-14

**上一版加的证书检查，第一次运行就误报了 —— 而误报的原因值得记下来。**

**一、它报了什么**

证书剩余天数   FAIL   最近一张 zhihui.kaogong.art 只剩 29 天（阈值 30）
**主站确实是这台机器上最先过期的一张** —— 这一半是对的。
但「29 天」不是故障。

**二、为什么不是故障**

续期服务**每天成功执行**，而证书还是九月那张 —— 因为**它今天跑的时候剩余正好三十天**，
而续期在「剩余不足三十天」时才启动。
**明天那次会续。**

**三、阈值改成二十一天**

**三十天会在边界上必然报一次** —— 因为续期的启动条件和告警条件是同一个数字。
正常续期成功后剩余会跳到六十到九十天；**掉到二十一天以下，
说明续期连着失败了至少一周**，那才需要人介入。

**四、这是这个检查第一次真的发现问题**

前几轮的「缺口」都是检查本身有缺陷（清单没跑、回退走不到、前缀漏了主服务）。
**这一次它报的是一件事**：主站证书是这台机器上最先过期的，而这件事之前没人知道。
**它误报了一回，但方向是对的。**

**五、这一版只改检查脚本与测试**

没有改动运行时代码。

## [1.2.197] - 2026-11-14

**第七项检查：所有证书的剩余天数。**

**一、差点漏掉的事**

查主站证书时看到它十二月十五日到期，心里想「还有一个月，不急」。
**但同一台机器上还有七八张证书** —— 到期时间各不相同。
用一条「找到第一张」的命令只看到一个，**而哪一张先过期，没有人知道。**

**二、过期不是降级，是打不开**

**任何一张过期，对应的站点立刻不可用**，而且浏览器会把它报成危险页面。
它不是「慢了一点」，是「用户看到一个警告页面然后关掉」。

**三、这一项检查所有证书，报最近的那张**

阈值默认三十天。**少于阈值算失败** —— 因为自动续期如果坏了，
留给人工介入的时间只剩这么多。
**已过期和即将过期分开报** —— 那是两种不同的处置。

**四、这一版只改检查脚本与测试**

没有改动运行时代码。

## [1.2.196] - 2026-11-14

**上一版加的第六项检查有个缺口：它不查主服务。**

**一、上一版写错了前缀**

第六项「关键服务不得处于失败」只查 `zhihui-*`。
**而主服务叫 `workbuddy-web`** —— 不带那个前缀。
**也就是说主服务失败时这一项不会报，而那正是最该报的一个。**

**二、命名本来就不统一**

这台机器上，网关主体的 unit 叫 `workbuddy-web`，
后加的定时任务统一用了 `zhihui-` 前缀。**两个都得查。**

**三、不查什么，也说清楚**

**不查 `wb-*`** —— 那是告警用的模板实例，正常状态下就有非活动实例，
算进来只会产生与故障无关的噪音。
**不查别的应用** —— 它们的失败不该阻断这个网关的发布。

**四、这一版只改检查脚本与测试**

没有改动运行时代码。
