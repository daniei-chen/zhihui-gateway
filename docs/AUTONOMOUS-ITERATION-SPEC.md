# 智汇网关 · 自动迭代规范

这份文件是给「全自动迭代」用的操作规范，不是产品说明。它的每一条都来自实际踩过的坑，
目的是让每一轮迭代都能产出**可验证**的进展，并且**任何一次发版都不打断正在进行的 API 调用**。

---

## 零、一句话目标

让智汇网关持续变好，同时保证用户在任何时刻发起的推理调用都不失败。

「变好」的判据不是改了多少代码，而是：**门禁全绿 + 线上零中断 + 每轮有可复述的产出**。

---

## 一、硬约束（违反任何一条，本轮作废）

1. **发版不得打断在途调用。** 判定标准见第三节，不达标就等于没做完。
2. **不许删对账数据。** 计费明细、请求记录是账本，省空间不是理由。
3. **不许在无法审阅的规模上做自动修改。** 一次改超过 20 个文件的自动修复必须先停下来说明理由。
4. **不许把「没机会出错」当「没出错」。** 报 5xx = 0 时必须同时给出窗口内请求数。
5. **不许半途而废。** 一轮结束时要么已发布上线，要么已完整回退，不留半成品在线上。

---

## 二、每轮迭代的固定骨架

一轮 = 一次可发布的改动，按下面顺序走，任一步失败就停下修复或回退，不要往下推。

### 2.1 选活

来源按优先级：

| 优先级 | 类型 | 例子 |
|---|---|---|
| P0 | 线上故障 / 数据错误 | 502 集中出现、对账不平 |
| P1 | 影响用户的缺陷 | 界面写死中文、页面 404、发版丢请求 |
| P1 | 安全与可观测性 | 鉴权缺口、日志缺失、看不见的状态 |
| P2 | 体验与可维护性 | 分页体验、告警噪声、文档陈旧 |

**不要**在没有 P0/P1 的时候硬凑改动。找不到值得做的，就做诊断和验证，把结论写清楚。

### 2.2 改动

- 先读再改。改之前必须有证据表明现状是这样（`grep` 出来、`curl` 出来、查库查出来）。
- 一次只动一件事。同时改三个不相关的点，出问题时无法定位。
- 服务端返回的文案、上游的错误原文**不要翻译、不要改写**，只在本地兜底字面量上做国际化。

### 2.3 门禁（全绿才允许发版）

```bash
python deploy/protected-customizations.py --update    # 仅在改了受保护文件后
python tools/bump_version.py <版本号>
python tools/ci_regression.py                          # 必须 exit 0
```

`ci_regression.py` 会跑四件事，缺一不可：

- **后端用例**（1,100+ 例）
- **前端用例**（245 例）
- **静态检查**：F821 未定义名字 0 处 + F811 生产代码重复定义 0 处
- **哈希一致性**：受保护文件与已审阅文件清单

四道门禁有一道红，就不许发版。**不要用「先发后修」绕过门禁**。

### 2.4 版本面（六个地方必须一致）

改版本号时，`bump_version.py` 负责同步：

```
VERSION
server/product-release.json
server/release-provenance.json       ← 含 reviewed_patch_files 哈希
server/writer-capabilities.json      ← release_id
web/lib/product.ts                   ← PRODUCT_VERSION
CHANGELOG.md == server/CHANGELOG.md  ← 两份必须逐字节相同
```

提交顺序有讲究：**先提交改动，再升版本号**，否则 `source_commit` 会指向一个不含本次改动的提交。
升完版本号还要再提交一次 `provenance`，让 `source_commit` 指向真正的构建提交。

### 2.5 CHANGELOG 写法

写给用户看，不写内部实现细节：

- 说**用户能感知的变化**（「成员管理的用户列表支持五种语言了」），不说「重构了 i18n 模块」。
- 不出现函数名、文件路径、下划线开头的标识符、测试术语（门禁会拦）。
- 修 bug 就说清「原来会怎样、现在会怎样」。

## 三、发版规范（核心：API 不中断）

### 3.1 为什么需要专门规范

`systemctl restart` 实测有约 **6 秒空窗**：停旧进程 → 起新解释器 → 校验整份发布签名 → 初始化应用。
这段时间里 nginx 转过来的推理请求 connect 直接被拒。历史上因此真实丢过调用。

解法是**滚动中继**：推理流量先到一个转发层（`127.0.0.1:7867`），它按签名路由文件决定转发给
哪个后端实例；已开始的流留在原实例上；连不上后端时它会等（4 次尝试、累计 9 秒），正好盖住空窗。

### 3.2 发版顺序（颠倒就白做）

```
1) 部署新版本（stage → seal → verify → activate），此时网关还在跑旧代码
2) 重启中继（仅当中继代码变更时），此时反代还在直连网关，影响为零
3) 确认反代已接中继（变量 + 片段 + location 三样都在）
4) 重启网关 —— 空窗期由中继的重试兜住
```

**用脚本，不要手工敲**：

```bash
sudo ./rollout-rolling.sh --check              # 只体检，不动任何东西
sudo ./rollout-rolling.sh <版本号>              # 常态发布
sudo ./rollout-rolling.sh <版本号> --relay-changed   # 中继代码也变了
```

脚本自己统计重启窗口里的 5xx 并把它变成退出码：**0 才是零中断**。

### 3.3 判定标准

| 退出码 | 含义 | 处理 |
|---|---|---|
| 0 | 窗口内 5xx 为 0 | 可以宣称零中断，但要附窗口请求数 |
| 1 | 前置条件不满足 | 修环境，不许硬发 |
| 2 | 已上线但窗口内有 5xx | 立即排查，按下面第 3.4 节区分 |

### 3.4 5xx 归因（不许混成一个数字）

看到 5xx 先分三类，只有第一类是发版问题：

| 类型 | 特征 | 是否发版责任 |
|---|---|---|
| 部署窗口 | 时间落在重启前后 15 秒内 | **是**，发版失败 |
| 上游瞬时失败 | 集中在一个客户端、间隔固定（重试）、上游容器日志同期正常 | 否，记下来即可 |
| 容量拒绝 | 大量不同客户端同一分钟返回 503 | 是，需要扩容或限流 |

**报告纪律**：说「零中断」时限定在**部署窗口**内。全天仍有失败是正常的，LLM 上游本身就会失败，
但那不叫「零中断」，叫「今天有 N 条 5xx，来自 M 个客户端，其中部署窗口 0 条」。

### 3.5 回滚

任何一步验证不通过：

```bash
sudo ./rollout-rolling.sh <上一个版本号>   # 或
release.py rollback                        # 发布指针回退
```

回滚后必须重新验证页面与 `/api/release`，并把失败原因写清楚。

## 四、发布与同步

### 4.1 GitHub

```bash
git tag -a v<版本> -m "<一句话>"
git push origin main && git push origin v<版本>
```

推送后 CI 会构建并上传 4 个资产（源码包、wheel、zip、exe）。等资产齐了再
`gh release edit --draft=false --latest` 正式发布。

**Release 说明必须包含**：

- 这一版做了什么（用户视角）
- 部署验证表：版本号、页面状态、**重启窗口请求数与 5xx 数**、门禁结果
- 任何没做到的事，如实写

### 4.2 控制台

```bash
nohup ./publish-console.sh --web /tmp/zhihui-webout.tar.gz --version <版本> &
```

发布脚本会校验静态资源完整性。发完要抽查页面 200，**并且确认新代码真的进了产物**
（例如搜一下新加的文案键在哪个 chunk 里）。

## 五、诊断规范

怀疑有问题时，按这个顺序查，不要跳步：

1. **`./healthcheck.sh`** —— 一条命令给出全局结论（服务、版本一致性、反代接线、页面、
   24 小时错误率、磁盘、数据库）。
2. **看窗口流量** —— 在说「没问题」之前先确认那段时间有请求。
3. **看归因表** —— 5xx 是部署窗口、上游失败还是容量拒绝。
4. **查数据库** —— `usage_events` 的 `terminal_state` 与 `provenance` 会告诉你请求死在哪一环。
5. **查上游** —— 容器日志同期是否有对应记录；有成功记录而网关说失败，说明请求没到上游。

**不要**在没看日志的情况下猜原因，也不要把「重试后恢复」当成「问题不存在」。

## 六、明令不做的事

| 不做 | 原因 |
|---|---|
| 删计费明细、请求记录来省空间 | 那是对账依据，错的对账比没有对账更糟 |
| 对 700 MB 级数据库无脑 VACUUM | 先看空闲页；空闲页少说明没有碎片，VACUUM 只锁表不解决任何问题 |
| 全仓库跑自动修复 | 一次改 262 个文件没法审，含受保护文件时更危险 |
| 把「测试用例」「回归测试」写进 CHANGELOG | 用户不关心，且门禁会拦 |
| 改写上游返回的错误原文 | 那会把真实故障信息抹掉 |
| 在反代已接中继时先重启中继再重启网关 | 顺序反了，中继重启那 1-2 秒会丢请求 |
| 用「先发后修」绕过门禁 | 门禁存在的意义就是拦这种冲动 |

---

## 七、一轮结束时的自检

发布前问自己四个问题：

1. **门禁真的全绿了吗？** 贴出实际输出，不是「应该没问题」。
2. **重启窗口内有没有请求？** 有多少？5xx 几个？
3. **我改的东西，用户会看见什么变化？** 说不出来就说明这轮白做。
4. **如果这次改动有副作用，我会怎么发现？** 没有答案就先补观测，再发。

发布后必须做：

- `/api/release` 版本与提交号正确
- 五个页面全 200
- 控制台新产物真的生效
- GitHub Release 正式发布且是 Latest

---

## 八、完成判定

整个目标达成需要同时满足：

- 连续发版窗口零 5xx（且窗口内有真实流量）
- 门禁四道常年全绿
- 健康巡检 0 个 FAIL
- 用户可感知的能力（多语言、稳定性、发布不中断）已交付

**只要上述任一条还有缺口，目标就没完成**，继续下一轮。
不要因为「这一轮做完了」就说「整个目标完成了」。
