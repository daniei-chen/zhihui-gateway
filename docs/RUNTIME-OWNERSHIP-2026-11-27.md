# 请求持久化所有权与内存预算

## 已实施的运行合同

三种推理协议的完成记录统一经过 `gateway._record_async`。事务、失败回执和中间件的预算收尾使用专用持久化执行器：每个Manager进程最多4个运行任务、8个排队任务。达到提交容量后，请求在事件循环上异步等待，不再向执行器追加无界队列，也不会在事件循环上同步等线程信号量。

执行器外的等待请求也有上限。每个中间件实例的普通 HTTP 请求生命周期名额为 `max(16, 2 × WB_GATEWAY_MAX_CONCURRENCY + WB_GATEWAY_QUEUE_DEPTH)`；默认80个，名额持续到持久化收尾完成。此边界涵盖前置拒绝和管理请求，避免磁盘变慢时把无界队列转移到等待的协程中。满额后在读取正文及执行业务前返回503与1秒退避，仅累计固定的拒绝计数，不再为这次尚未接纳的请求排审计写入。每个实例的健康探针、就绪检查和排空控制另有4个名额，权限检查仍照常；公开健康探针不写请求账本。双实例重叠时各自保留这些名额，不能把80当作整组总上限；共享资源预算由协调器另行统一约束。

等待期间，请求保留既有的准入、密钥和内存租约。直接取消、反复取消以及流式迭代器关闭，都必须等待这次已知事实的事务或回执尝试结束后才能释放。任务复制请求上下文，账本的幂等键、用量来源、未知用量与计费语义保持原有合同。

若取消发生在完整上游响应的 JSON 解析期间，解析线程仍需完成；已经解析出的原始用量会走同一持久化路径保存，再传播取消。三协议均记录499与`client_cancelled`，保留真实用量；预算继续遵守既有取消后的`unknown`核对规则，不把客户端取消标为完成，也不重放已返回的上游请求。

持久化等待及执行同时计入 `drain.in_flight.persistence`。停机等待超时返回 `drained=false`，保留未完成数量；不会把超时描述为排空成功。预算 owner 的生命周期文件锁仅在已排空且已知持久化任务为零时主动释放，否则保留到进程退出。`/api/readyz/detail`（面板读权限）提供持久化容量、已提交任务、持有所有权的调用、等待名额数量和排空计数。

排空超时也不会提前关闭仍供请求使用的平台运行时、共享 HTTP 客户端或资源协调器，不会把实例账中的 owner 清空或标为`stopped`。诊断保留本次停机的`shutdown_drain`结果；内存排空状态继续拒绝新业务请求。平台运行时的关闭顺序移到排空判断和后台调度器收尾之后。

这不承诺 Python 可以强行终止卡在内核 I/O 中的线程。正常存储错误仍走原有 SQLite 超时和回执路径；强制杀进程仍需按现有 unknown/replay 恢复合同处理，不能凭 HTTP 连接已断开推断没有消费。

## 内存计费单位

`WB_GATEWAY_MAX_INFLIGHT_BODY_BYTES` 是请求相关保留内存的保守预算，默认 **64 MiB**；不是整个进程 RSS 上限。HTTP 连接、Python 运行时、后台工作和其他进程仍需要额外余量及宿主机/cgroup 限制。

| 内容 | 计费方式 |
|---|---|
| 入站缓存与序列化工作区 | 保留现有输入倍率，`WB_GATEWAY_BODY_PHYSICAL_FACTOR` 默认3、配置合同允许1–8 |
| JSON 对象图 | 解析前按字符串宽度、容器、标量及结构开销计算保守上界；解析后核对 `sys.getsizeof` 对象树占用 |
| 适配后的输入对象 | 兼容协议解析前预留源对象和适配工作区，转发前将同时保留的源对象和适配对象相加核对，序列化副本继续独立预留 |
| 解码输出 | 在交付下一块前按实际累计解码字节增长预留，覆盖缓冲及最终 bytes 副本 |
| 非流式输出 JSON | 构造对象图前预留结构与解码开销，之后核对保留对象大小 |
| 共享准入 | 与本地使用完全相同的 `charged` 值，不再以较小的逻辑线缆字节对冲物理预算 |

客户端 `max_tokens` 只用于初始输出预留优化；真实响应增长仍需获得额外预算。高密度 JSON 数组或对象可能在字节体积未达到单请求上限时被拒绝，这是内存保护而不是语法错误。解析和工作线程停止前不会释放保留量。

不超过64 KiB的单块转发正文按实际字节数预留，避免十几字节的请求因向上取整而额外占用64 KiB再乘倍率。较大正文仍按既有阶梯合并预留，保留大请求的协调器调用上界。

## 共享准入协议升级

此次资源协调协议 `response_budget_protocol` 从1升为2。它与账本 writer 描述文件的整数 `version=1` 是不同协议，不改变后者，也不改变业务库 schema。

旧协调器按逻辑字节计费，新协调器按保留内存计费，因此不能混用同一个策略而声称额度一致。候选在中间件构造/启动阶段遇到旧策略时明确拒绝接流量，并提示迁移工具。老 peer 在策略变更后也会失败关闭。

### 迁移前检查

以下命令只示例独立开发/维护环境；源码升级不会自动执行它们。路径必须指向实际的**资源协调库**，不是业务数据库。

```bash
python deploy/migrate_admission_policy.py \
  --database /path/to/data/admission-cohort.db
```

默认只读。工具核对旧策略及其父目录 `.budget-owners` 中的同机生命周期锁。活 owner、缺失/未知 owner、不可读锁、错误 owner 目录或不支持的协议都会拒绝迁移。即使某个活 peer 当前没有请求租约，它仍会阻止迁移。

### 应用迁移的前提

1. 入口停止向旧 cohort 派发新请求，并确认所有既有请求及持久化任务排空。
2. 停止旧 cohort 的全部 peer；候选保持未接流量。仅观察零请求数不能代替停止旧 peer。
3. 再次运行只读检查。成功后，维护者才对同一协调库显式加 `--apply`。
4. 工具在 `BEGIN IMMEDIATE` 中重新核对所有 owner，删除已证明死亡的资源租约，并原子切换协议到2。容量参数不变，业务账本不变。
5. 启动候选，确认共享协调器健康与就绪后再恢复入口。

这是资源协议跨版本维护步骤，需要明确的流量排空窗口；不能承诺旧、新协议无窗口混跑。不要删除活 cohort 数据库、绕过策略比较、把 `WB_SHARED_ADMISSION` 临时关掉来掩盖冲突，也不要恢复旧业务库回滚消费。

## 合成验收

`server.tests.test_runtime_ownership_memory` 覆盖：专用执行器容量、满池异步等待、300请求拒绝洪峰、排队及写入阶段反复取消、三协议完整响应解析阶段取消、真实 SQLite 用量提交、准入字节租约保留、排空超时及 owner 锁、密集 JSON 在解析前拒绝、真实输出增长、共享/本地计费一致，以及旧/新资源协议迁移隔离。

这些用例使用临时数据库和合成传输，不提供生产容量、真实磁盘故障或在线无中断升级的证明。生产部署仍需结合实际进程组内存、长流分布与存储延迟验收。
