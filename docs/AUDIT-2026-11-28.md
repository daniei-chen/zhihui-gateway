## 0. 结论摘要

**它是什么**：一个「四合一」单进程应用 —— WorkBuddy 授权/额度的转售与治理网关（上游账号池 + 按密钥的预算配额 + 不可变账本 + 三协议反代）、管理控制台、用户门户（注册/签到/红包/积分）、运维发布面。单进程、SQLite（95 张表）、Next 静态导出由 FastAPI 托管。复杂度不在转发，在**钱与状态机**和**三套协议适配**。

**能跑吗**：能。干净检出安装依赖后 `uvicorn server.main:app` 可启动，`/healthz` 200；`npm run build:export` 成功（156s，`web/out` 6.1MB），构建后 `/`、`/login` 200。注意：生产锁文件是 **Linux 锁**（含 `uvloop`），Windows 上原样 `pip install` 会失败。

**测试绿吗**：**Linux CI 绿，Windows 本机不绿**。PR #58 的 CI 3/3 success。本机全套门禁：unittest **6746** 例（7 failures / 9 errors / 104 skips，35m45s）、pytest **295** 例（272 passed / 10 failed / 2 errors / 11 skipped）、前端 **264 passed**、静态检查通过，进程 exit=1。28 个 failure/error 里绝大多数是平台/环境（GBK 解码、`fcntl`、Windows 文件锁、缺 `web/out`、时序断言），但其中 **3 个暴露真实 Windows 可移植性缺陷**（`server/backup_application.py:9` 顶层 `import fcntl`、`server/qtgcore/config.py:69` 把 `/opt/...` 当相对路径、测试/脚本的 GBK 假设）。

**最大的 4 个 P0**（详见 D 节）：
1. **更新器供应链**：默认仓库不是本仓库、包与摘要同源、无签名、`pip install` 无 hash（`deploy/update.py:75,1253,1340`）。已有一个绿 PR #59 在等合并。
2. **DAN-23 在崩溃恢复路径失效**：回执重放只认 `completed`，同一份 `client_cancelled` 回执会落成永不归档的 unknown、把 credit 配额密钥永久锁 429（`server/ledgerreplay.py:341` vs `server/budget.py:342`）。
3. **中继把容量拒绝当 drain**：`503+Retry-After` 判据与准入拒绝完全重合，一条被拒请求被重放 6 次（约 22.5s），过载被放大 6 倍（`server/rollingrelay.py:69-76` vs `server/observability.py:1216-1234`）。
4. **蓝绿切流后 1 秒就停候选**：无在途判据，超 90s 的长流必被 SIGKILL，而发布脚本随后统计「零 5xx」把故障静默（`deploy/rollout-rolling.sh:422-424`）。

**一句话判断**：工程纪律和证据密度高于同类项目（hash 锁、受保护字节、门禁清单、审计文档都很少见），但**钱的边界与发布的边界仍有真口子**；当前最该做的不是加功能，是把上面 4 个 P0 和 D 节 P1 里的预算出口/备份/签名口径补齐。

## F. 同行对照（3–4 个成熟项目）

（每条都带 URL 与日期；完整三段式见 `audit/06-upstream.md`）

| 项目 | 它做了我们没做的（具体机制） | 它做得比我们好的 | 适不适合我们 |
|---|---|---|---|
| **LiteLLM**（64k stars，MIT，v1.111.0 / 2026-11-25） | 同一逻辑模型名挂多个 deployment 的路由层：cooldowns、fallbacks、timeouts、Redis 跨实例 tpm/rpm | 预算按「个人/团队/成员/Agent」四层在 DB 强制；文档明确 DB-less 模式下预算不生效 | 借层级维度（`budget.py` 按 key 查 `api_keys`，加 owner/team 是加列改查询），**不借 DB-less 静默降级**——我们的预算失效必须显式报错 |
| **one-api / new-api**（37k/52k stars，MIT/AGPL） | 「渠道→模型→令牌」三级抽象；会话保持三档 + `model_regex`/`path_regex`/`key_sources` 规则化 | 请求日志记录「经过哪些渠道、重试几次、策略怎么决策」，我们的 ledger 只记结果 | 借「请求策略配置化」方向（现在会话保持是 `gateway.py` 代码分支），**不借 AGPL 代码**（new-api 会传染许可证） |
| **Portkey**（13k stars，MIT，v1.15.2 / 2026-01-12） | 配置驱动负载均衡（targets 权重）+ fallback + circuit breaker；guardrail 是插件目录，前后置 hook | 开源版与企业版边界清楚；guardrail 加规则不改代码 | 借「配置即路由 + guardrail 目录」；我们是 Python+Go，不借 Node 运行时；先核实开源版能力边界 |
| **Higress**（9.8k stars，Apache-2.0，v2.2.6 / 2026-11-10） | `ai-quota` 按 consumer 固定配额、`ai-token-ratelimit` 规则级/按 consumer 两级（Redis） | `ai-statistics` 四维观测：网关/路由/服务/模型，输入输出 token、首 token RT、总 RT | 不照搬 Wasm/Envoy；借「consumer 维度限流」和「四维观测」两个口径，落到现有 SQLite 表；Redis 依赖换成本地计数 |
| **Kong AI Gateway**（44k stars，Apache-2.0，3.9.5 / 2026-11-19） | AI Model 实体上的 balancer：均衡/缓存命中/降延迟/按成本/failover 五种算法，内置同 target 重试或改投 | `AI Rate Limiting Advanced` 用 provider 返回的 token 算成本；`ai_metrics` 暴露 requests/cost/tokens/latency/cache | 不借 Nginx/Lua 形态；借「按成本选 target」（账号选择现在是固定权重 + TTFB 降权）与「provider/model 指标 label」 |

**5 条可借鉴但不要照搬**（对应本仓库模块）：
1. LiteLLM 的预算层级 → `server/budget.py`/`ledger.py`，加 owner/team 维度；**拒绝**「DB 不接就静默不生效」。
2. new-api 的请求策略配置化 → `server/routers/gateway.py` 的会话保持/重试分支抽成配置；**拒绝** AGPL 代码。
3. Portkey 的 guardrail 目录 → `sanitize` 从硬编码规则改成「规则目录 + 前后置 hook」；不换运行时。
4. Higress 的 consumer 限流 + 四维观测 → `server/bodyguard.py`/`observability.py` 加维度；不用 Envoy/Wasm。
5. Kong 的按成本选 target + provider/model 指标 → 账号选择加「成本」权重项，观测加 label；不写 Lua。
