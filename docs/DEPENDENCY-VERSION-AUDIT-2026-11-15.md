**结论：直接依赖与几个有 CVE 历史的间接依赖，版本都在修复线之后。**
没有发现已知易受攻击的版本。

**但这份审计的边界必须说清楚**（见第五节）：它是**按已知 CVE 清单逐项核对**，
不是全量扫描。

## 五、这份审计的边界

**它是逐项核对，不是全量扫描。**

| 做了 | 没做 |
| --- | --- |
| 43 个直接依赖的锁定版本 | **全量依赖树的 CVE 扫描** |
| 12 个有 CVE 历史的间接依赖 | 编译产物里实际打包了哪些代码 |
| 对照已知修复线判断 | 跑自动化审计工具（主机没装、且被工具链限制） |

**所以准确的说法是：没有发现已知易受攻击的版本，而不是「已证明没有漏洞」。**

## 六、为什么没跑自动化工具

主机上跑 `npm audit` 需要 Node 运行时。当前环境对「直接执行 Node」有拦截规则
（`interpreter-inline-code`），而这类扫描本来也应该在**构建机**上做，
不是在**生产机**上做。

**建议**：把 `npm audit --audit-level=high` 加进 CI 的构建阶段。
那是它该在的位置，也避免在生产机上引入一个 Node 运行时。

## 七、如果要继续

1. **把依赖审计挪到 CI** —— 构建时跑，不通过就不发布
2. **查构建产物** —— `web/out/` 里实际打包了哪些第三方代码，那是真正进入生产的部分
3. **给直接依赖加版本上限策略** —— 现在用的是 `^` 范围，锁到新版本是好事，
   但也意味着「重新安装可能引入未测过的次版本」
