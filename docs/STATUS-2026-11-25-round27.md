## 2. P0-4 其实早就完成了

审计的未做原因写「告警脚本在主机上，不在仓库里」。实际查：

- **去噪**：`operational.transition()` 只在状态**变化**时通报
- **磁盘水位**：`operational.py:480-489` 已有**两档**

```
disk_free          < 2 GiB   紧急，马上要写满
disk_space_trend   < 5 GiB   趋势，该做决定了
```

分成两个告警名而不是一个名字两种文案，理由写在注释里：状态机只在**变化**时通报，
如果共用名字，从 5 GiB 掉到 2 GiB 不会产生新通报 —— 而那一刻最该被看见。

**验证覆盖范围**：`DATA_DIR` 与根分区是**同一设备**（`stat -c %d` 都是 `64770`），
所以监控 `DATA_DIR` 等于监控整卷。当前 16.4 GiB 可用，高于 5 GiB 阈值，不告警正确。

**还有测试**：`server/tests/test_v1271_disk_space_alerts.py`。
**还有文档**：`docs/DATA-GROWTH.md`（104 行）。

**P0-4 已经完整，不需要再做。**

（审计要求的是「百分比 ≥85% / ≥92%」，实现用的是「绝对可用 < 5 GiB / < 2 GiB」。
绝对值更直接反映「还能写多少」，且这里是单卷，两种口径等价。不改。）

## 3. 一个新发现：`application_error` 发生了却不留痕

查 11-19 那天的 121 个 5xx 归因：

```
gateway.application.error   51   ← 我们的责任
no_healthy_account          50   ← 上游
gateway.interrupted         20
```

`gateway.application.error` 按规范属于**我们自己的责任**（不是上游、不是部署窗口）。
于是查它的历史：

```
2026-11-24    1   v1.5.56      ← 最近一次
2026-11-23    1   v1.5.32
2026-11-22    3   v1.4.4
2026-11-21    3   v1.3.4

2026-11-19   51   v1.3.4       ← 高峰
2026-11-15   31   v1.2.114
```

**近期已大幅下降**（v1.3.4 时期高发，v1.5.x 之后每天 0-1 个）。

但按端点拆，其中有一条值得注意：

```
/api/stats/summary                   35
/api/stats/daily                     35
/api/system/internal-session-verify  31
/api/stats/credits                   10
/v1/chat/completions                  8   ← 推理调用
```

**8 次推理调用返回了 500。**

### 关键问题：日志里查不到原因

取最近一次（`2026-11-24 19:19:39`，v1.5.56，key 2，503，477 ms）去翻服务日志：

```
Nov 24 19:19:45 ... ERROR workbuddy.operations: operational alert name=workbuddy_low_accounts ...
Nov 24 19:19:45 ... ERROR workbuddy.operations: operational alert name=backup_stale ...
```

**只有两条无关告警，没有任何异常堆栈。**

### 为什么会这样

`application_error` 是**兜底分类**，不是某个具体异常：

```python
# observability.py:1497 / 1511
'application_error' if status >= 500 else 'completed'
```

也就是说：**任何未被更具体分类的 5xx，都会落到这个名字上**。分类函数本身
（`observability.py:426`）是纯函数，只推导名字，不记日志。

**结果是：这类失败发生了，但「为什么」没有留下来。** 规范 §2.1 把「看不见的状态」
列为 P1，这一条正好落在里面。
