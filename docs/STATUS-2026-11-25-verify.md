# v1.5.76 在真实流量下的验证（第 33 轮）

## 1. 关键问题：那 1 条「内部错误」是哪来的

24 小时统计里有 1 条 `gateway.application.error`，5xx 分类里是 503。需要确认它是不是
修复没生效。

查它的归属：

```
release_id   at                   endpoint              http_status  latency_ms
v1.5.56      2026-11-24 19:19:39  /v1/chat/completions  503          477
```

**v1.5.56，昨天 19:19。**而 v1.5.76 是今天 13:16:51 才部署的。

**所以它是修复前的旧记录，不是新产生的。**修复后的版本里 0 条。

这个区分很重要：如果只看「24 小时有 1 条」就下结论「修复没生效」，会误判；
如果不看时间就下结论「已经根治」，也是误判。**必须看 `release_id` 与部署时间的先后。**

## 3. 401 到底是谁在打

`gateway.auth.denied` 401 共 235 条（含 403 之外的单列统计口径差异）。按 key 拆：

```
key_id    n
(none)  235
```

**全部是无 key 的匿名请求。**不是「某个用户的 key 失效」，也不是「鉴权被绕过」——
是没带凭据的访问被正常拒绝。

235 次 / 24 小时 ≈ 10 次/小时，量级很小，不需要限流。

## 4. v1.5.76 的推理质量

| 指标 | v1.5.75（同一半小时窗口） | v1.5.76 |
|---|---|---|
| 推理请求 | 80 | 35 |
| 5xx | **0** | **0** |
| `terminal_state` | — | 全部 `completed` |

`error_stage` 全为 null —— **这是正常的**：成功请求没有错误阶段。
只有失败才有阶段标记。把「null 多」当成「观测缺失」是错的，
这一点第 28 轮已经吃过一次教训（当时把 `application_error` 的 null 理解成异常）。

## 5. 样本问题，如实说

v1.5.76 部署至今只有约 **4 分钟**、**35 次推理**。

**这个样本能说明什么**：修复没让系统当场坏掉；新代码路径是通的；两版之间没有
肉眼可见的性能变化。

**不能说明什么**：修复是否在所有失败路径上都正确；是否会有新的未预期错误。
这些要跨天、跨更大流量。

## 6. 本轮没有改代码

线上只跑了 4 分钟。此时再发一版，一旦出问题无法归因。
规范 §2.2「一次只动一件事」的精神也包含「不要在上一个改动的效果还没显现时叠加新的」。

本轮做的是把「修复了」变成「在真实流量下验证过，并区分清楚哪些是旧账」。
