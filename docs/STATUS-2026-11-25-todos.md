## 2. 四个「从未成功」的端点——是滚更窗口，不是缺陷

审计 §4.2 勘误里列了四个端点，说它们「只有 404/401」。用 `MAX(ts)` 复核：

| 端点 | 近 7 天次数 | 最后发生 | 30 天里的成功记录 |
|---|---|---|---|
| `/api/members` | 10 | 2026-11-20 14:30 | 无 |
| `/api/logs/attempts` | 7 | 2026-11-20 14:31 | 无 |
| `/api/checkin-logs/clear` | 11 | 2026-11-21 14:48 | 无 |
| `/api/usage/token/` | 27 | 2026-11-23 21:49 | **200 × 804** |

**四个全部停止于 2026-11-20 ~ 11-23，最近 2 天再没有任何调用。**

`/api/members` 与 `/api/logs/attempts` 的最后时间都是 **11-20 14:30**，正是审计自己指出的「前后端版本错配的滚更窗口」。

### 一处更正

审计说 `/api/usage/token/` 「只有 404/401」——**不对**：

```
/api/usage/token/  200 × 804   last_seen = 2026-11-13 08:18
```

**它曾经成功过 804 次**，之后才变成 404/401。所以它不是「后端没有这个路由」，而是
在那之后路由或调用方式变了。近 7 天 200 次数为 0，说明改动之后没有恢复。

这仍属于历史事件（近 2 天无调用），但**结论不能写成「从未成功」** —— 那会把人引向
「删掉这个调用」而不是「查为什么改了之后不通」。

## 3. 方法上的教训（第三次同类）

审计 §4.2 自己总结过：**只看累计次数会漏掉「已停止」这件事**，必须同时看 `MAX(ts)`。

本轮验证这个方法有效 —— 四条待办里三条被它直接判为历史事件。

**但它还有一层没覆盖**：`MAX(ts)` 只说「最近一次是什么时候」，不说「有没有成功过」。
`/api/usage/token/` 就是被这一层漏掉的：它的 `MAX(ts)` 很近（11-23），照「近就够了」
的直觉会当成当前故障；而它的成功记录停在更早（11-13），照「只看状态码」又会当成
从来没有过。

**完整判据要三个一起看**：

```sql
SELECT endpoint, http_status, count(*) n,
       datetime(MAX(ts),'unixepoch','+8 hours') last_seen
FROM request_outcomes
WHERE ts > strftime('%s','now') - 30*86400
  AND endpoint = ?
GROUP BY endpoint, http_status ORDER BY n DESC;
```

1. **有没有 200**（它是否工作过）
2. **200 的最后时间**（什么时候起不工作的）
3. **任意状态码的最后时间**（还在不在被调用）

三者组合才能区分「从未实现」「实现过但坏了」「坏了但现在没人调」。
