# 账号池调度的机制与一处被推翻的建议 — 2026-11-15 补充

上一篇 `ACCOUNT-POOL-BALANCE-2026-11-15.md` 里提了一个「可以先试的」办法：
**给闲置账号设更高权重，观察请求数是否上升。**

**这一篇记录：那个办法大概率无效。** 原因是从配置里读出来的。

---

## 一、上游确实有调度，按「空闲时间」加权

`workbuddy2api` 的配置里有三个相关键：

| 键 | 值 | 含义 |
| --- | --- | --- |
| `idle_weight_max` | **2.0** | 空闲账号的权重上限 |
| `idle_weight_per_hour` | **0.5** | 每空闲一小时加多少权重 |
| `schedule` | 定时任务 | **与账号选择无关**（见第三节） |

按这两个值推：账号空闲 1 小时 → 权重 1.5；空闲 4 小时 → 权重封顶 2.0。

**所以上游的期望分布上限是 2:1。**

## 二、实际是 228:1 —— 这才是问题所在

| 实测 | 值 |
| --- | --- |
| 最多 / 最少用量 | **228 倍** |
| 上游权重的期望上限 | **2 倍** |

**差距不是「策略不同」，是「这个策略没有按配置生效」。**

可能是上游有 bug，也可能有别的因素盖过了它（错误率、冷却、粘性会话），
**但从配置和结果对不上这一点看，它没有在按设计工作。**

## 三、`schedule` 是定时任务，不是选择策略

容易误读：`config.json` 里的 `schedule` 块长这样：

```
"schedule": {
  "activity_enabled": true,
  "checkin_enabled": false,
  "keepalive_enabled": true,
  ...
}
```

**那是签到、活跃度、保活这些定时任务的开关** —— 与「这次请求用哪个账号」毫无关系。

同理 `"mode": "passthrough"` 属于 `prompt` 块，是「prompt 透传、不做改写」，
也不是选择策略。

## 四、被推翻的那条建议

上一篇说：「给一个闲置账号设明显更高的权重，观察 10 分钟」。

**现在看，那个权重和上游用的权重不是同一个东西：**

| 机制 | 存在哪 | 谁在用 |
| --- | --- | --- |
| `idle_weight_*` | `workbuddy2api/config.json` | **上游调度器自己算** |
| 智汇的 `set_account_weight` | 账号 JSON 文件的字段 | **看不出有谁读** |

**上游按「空闲时间」算一个派生权重，而智汇写的是账号文件里的一个静态字段。**
两者没有证据表明有关联。

**所以「设权重看效果」很可能得到「没变化」的结论 —— 而那不能证明「权重不影响调度」，
只能证明「这个字段不被读」。**

**上一条建议因此撤回。** 它给出的验证方法会指向一个错误的结论。

## 五、还剩下什么可做

### 可以确认的（只读）

1. **上游是否有日志能显示每次选择**——有的话，看它按什么排序
2. **`state.json` 里有没有「上次选中时间」之类的字段**——有的话能反推排序键

### 不能安全做的

**改 `config.json` 的 `idle_weight_*` 然后重启上游** —— 那会中断数据面，
而当前不均衡的代价（容量闲置）远小于一次重启的风险。

**除非先把「为什么配置没生效」查清楚**，否则改配置只是换一个未知状态。

## 六、上游日志里的直接证据

上一篇用的是**请求记录**（网关自己记的）。这一篇补上**上游日志**（容器 stdout）——
那是真正做选择的一方，它的记录比网关侧的复述更直接。

### 最近 3000 行的分布

| 账号 | 次数 |
| --- | --- |
| `糕手小沈(3077172d)` | **514** |
| `顺风顺水(6b5daf5f)` | **448** |
| `风(74255fd5)` | **362** |
| `昴(5ccb46d9)` | **230** |
| `182****8596(28934775)` | 118 |
| `DayDreamer(e6b4dee4)` | 84 |
| `人世间(2d08e459)` | 54 |
| `oo(4c4db6fd)` | 26 |
| `黑木(032d2815)` | 16 |
| 尾部几个 | **6 / 6 / 8** |

**不同账号 37 个，最多 / 最少 = 86 倍。**

**上游自己的日志也显示同样的形态** —— 这不再是「网关记录的角度问题」，
而是调度本身的结果。

### 为什么这里的数字和上一篇不同

| 来源 | 窗口 | 账号数 | 最大/最小 |
| --- | --- | --- | --- |
| 请求记录 | 24 小时 | 48 | 228 倍 |
| **上游日志** | **最近 3000 行（约数小时）** | **37** | **86 倍** |

**窗口不一样，所以数字不一样。** 但**形态一致**：少数账号扛大部分请求，
尾部有一批几乎不参与。

**两边的方向一致，这比某一个数字更有说服力。**

### 连续同账号的现象

抽样看连续几条请求的时间戳与账号：

```
04:27:31  顺风顺水(6b5daf5f)
04:27:34  顺风顺水(6b5daf5f)
04:28:45  顺风顺水(6b5daf5f)
04:28:48  顺风顺水(6b5daf5f)
04:28:52  顺风顺水(6b5daf5f)
04:28:56  顺风顺水(6b5daf5f)
```

**同一个账号连续命中六次**，跨越一分半钟。

如果调度真的按「空闲时间加权」（配置是每空闲一小时 +0.5、上限 2.0），
那么一个刚被用过的账号权重会降到 1.0，而空闲了四小时的账号权重是 2.0 ——
**那个 2:1 的差别应该很快把负载推开。**

**它没有推开。** 这是「配置没有按设计生效」的最直接观察。

## 七、这份记录没有回答的

- 上游实际用的是哪种策略（那需要读它的源码，不在这个仓库）
- 权重为什么没有生效（bug？被别的因素覆盖？配置读的是另一份？）
- **尾部那批账号是否在某些条件下会被选中**（只在少数场景出现，还是永不出现）

## 八、结论汇总

| 问题 | 答案 | 证据强度 |
| --- | --- | --- |
| 上游有调度机制吗 | **有**，按空闲时间加权，配置上限 2 倍 | 配置 |
| 它生效了吗 | **没有** | 请求记录（228×）+ 上游日志（86×）+ 连续同账号 |
| 智汇能调整它吗 | **不能**，写的字段与上游算的权重不是同一个 | 代码与配置对比 |
| 上一篇的「设权重看看」建议 | **撤回** | 验证方法会得出错误结论 |
