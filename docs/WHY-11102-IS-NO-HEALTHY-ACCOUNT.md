# 为什么 `11102` 被归类成「没有健康账号」 — 2026-11-15

**结论：这不是错误归类，是有现场证据支撑的设计。不要「修」它。**

---

## 一、看起来像 bug 的地方

`request_logs` 里有一条 503：

```json
{
  "upstream_status": 503,
  "code": "no_healthy_account",
  "message": "{\"code\":11102,\"msg\":\"model [claude-sonnet-4-5] service info not found\"}"
}
```

**上游说的是「模型不存在」，网关归类成「没有健康账号」** —— 看起来像把两件事混在一起了。

**我一度准备把它当缺陷修掉。** 查了代码之后发现不能修，原因写在这份文档里。

---

## 二、现场证据（2026-10-28）

`server/routers/gateway.py` 里有一段取证记录：

> 上游把**内容拒绝**伪装成 `11102 模型不存在`，而且是 1–2 分钟的短窗口 ——
> 单日 421 次、涉及 31/32 个账号，同一分钟同一模型既有 200 也有被拒，
> 同一账号同时出现在成功侧与被拒侧。

**这段证据排除两种解释**：

| 解释 | 为什么被排除 |
| --- | --- |
| 账号缺这个模型 | 同一账号同时出现在成功侧和被拒侧 |
| 模型映射没生效 | 失败请求的映射结果都是同一个有效模型 |

**剩下的解释只有一个**：上游在那段时间**主动拒绝**，而拒绝文本是伪装过的。

---

## 三、所以归类是对的

**「没有健康账号」这个 code 表达的不是「字面上的账号问题」，而是「上游现在不接这个请求」。**

对调用方真正重要的问题是：**这个请求被处理了吗？可以重放吗？**

**答案是可以。** 这类响应意味着：

- **没有生成**（没有内容产出）
- **没有 usage**（没有用量）
- **没有计费**（没有扣费）

**所以重放是安全的** —— 不会重复生成，也不会重复扣费。

---

## 四、网关已经做了该做的事

**它内部已经有了一次有界重试**（默认最多两次尝试，可调设置项 `upstream_rejection_retry`，不用发版）。

**这个重试的意义**：上游拒绝是**短窗口**（一到两分钟），客户端默认重试八次且间隔更长。
**网关内补一次短重试，就能把窗口挡在客户端之外**，省掉那八次等待。

**所以「客户端重试很多次」不是设计缺陷** —— 网关已经先把短窗口吃掉了一部分，
剩下返回给客户端的是「重试之后仍然不行」。

---

## 五、那 status 为什么是 503 而不是 4xx

**因为从调用方视角看，这确实是「服务暂时不可用」** —— 不是请求本身有问题。

- 请求格式是对的
- 模型名是对的（映射生效了）
- 是**上游**在那几十秒里不接

**用 4xx 会让客户端认为「这个请求永远不该重试」**，而那与事实相反：
一分钟后同一个请求通常会成功。

**这也正是它必须是 503 的理由。**

---

## 六、这条判断的边界

**上面所有结论都依赖那段 2026-10-28 的取证。**

如果上游改变了行为（比如**真的**开始因为「账号缺模型」返回 11102，而不是伪装拒绝），
那么这条归类就会变成错的 —— **而它不会自己暴露**，因为现象一样：503 + 同样的错误文本。

**判断方法**：如果某天 `11102` 的失败**集中在同几个账号、且长期不缓解**，
那就不是短窗口拒绝，而是真的缺模型。那时这条归类需要重新审视。

**短窗口 + 涉及面广 = 伪装拒绝（现在的归类对）**
**长期 + 集中在少数账号 = 真的缺模型（归类需要改）**

---

## 七、这份文档存在的理由

**代码里已经有那段取证注释**，但它藏在 `gateway.py` 的第三百行附近，
而错误归类发生在 `budget.py` 的一份标记表里 —— **两处相隔很远**。

**下一次看到 `no_healthy_account` 配着「模型不存在」的文本，很可能又会有一个人（或一个模型）
把它当成 bug 去修。** 修了之后重试逻辑就失效，而失效的表现是「偶发失败变多」——
**没人会把它和这次「修复」联系起来。**

所以单独写一份，放在能被搜到的地方。
