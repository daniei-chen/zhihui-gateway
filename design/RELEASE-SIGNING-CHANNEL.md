# 全新签名与发布渠道（设计 + 自测结果）

日期：2026-10-26T14:50+08:00。状态：**渠道已实现并自测通过；尚未用于任何生产发布**。

## 一、为什么要"全新"而不是复用

此前发布被卡住的一部分原因是：既有生产信任链的私钥、旧 release 与其 trust 材料都拿不到，而规则又禁止擅自用新密钥替换生产公钥。本轮按你的决定，**新建一条独立渠道**：生成全新的 Ed25519 密钥对，签新的发布包，公钥随包分发。

边界说清楚：

- 新渠道**不替换**生产上现有的任何公钥，也不声称与旧 release 同源。
- 旧 release 若仍要恢复，需要用旧材料单独验证；新渠道只对**新包**负责。
- 这条渠道现在只证明"包可被验签、内容未被改"，不等于"生产已可部署"。

## 二、工具与格式

工具：`tools/release_sign.py`（离线工具，不进运行时依赖）

| 子命令 | 作用 |
|---|---|
| `keygen` | 生成 Ed25519 密钥对；私钥用口令加密成 PKCS8 PEM，`chmod 600`；`key_id = sha256(pubkey)[:16]` |
| `bundle` | 复制源树 → 生成 `BOM.json`（每文件 `path/bytes/sha256/mode`）→ 对 BOM 字节签名 |
| `verify` | 用公钥验签 → 逐文件复核 sha256/bytes/mode → 报告未被 BOM 列出的多余文件 |

发布包结构：

```
release-<label>/
  files/                      # 运行文件树（不含 __pycache__/.pytest_cache/.git）
  BOM.json                    # 签名对象：文件清单 + 来源 archive/版本元数据
  BOM.json.sig.json           # {algorithm: ed25519, key_id, signed_sha256, signature_hex, signer}
  trust/release-pub-<key_id>.pem
  README-INSTALL.md           # 安装前必须验签
```

**为什么签 BOM 就够**：BOM 覆盖每个文件的 `sha256 + bytes + mode`，签名覆盖 BOM 的**精确字节**，因此传递性完整；不需要第二套清单格式去保持同步。

**为什么验签必须重新算哈希**：签名有效但载荷被改是常见攻击面，所以 `verify` 不只验签，还逐文件重算并比对，同时列出未登记的多余文件。

## 三、密钥生命周期规则

1. 私钥只在**离线环境**生成；不入仓库、不入发布包、不上服务器（自测用的临时密钥在测完后立即删除）。
2. 口令只经环境变量传入（`--passphrase-env`），禁止出现在命令行、脚本或文档里。
3. 公钥随包分发；建议另有一条独立渠道公布 `key_id` 指纹，防止包与公钥一起被换。
4. 轮换：新 `key_id` 并存一段时间，旧包用旧公钥验；**吊销清单要落在包外**，否则等于让包自己决定自己是否可信。
5. 双人控制、HSM 托管属于流程层，本渠道只提供技术底座；未落地前不能声称满足安全审计要求。

## 五、接到真实发布上还差什么

1. **正式密钥对**：需要在一个受控的离线环境生成；本轮只在本地生成过一次性的自测密钥。
2. **签名对象的最终 BOM**：候选包 `workspace-c6cd5e802e377ab4.tar.gz`（1527 文件）应作为 `--source` 生成正式 BOM，而不是继续用 `RELEASE-BOM-H01.json`（那是审查用清单，字段口径不同）。
3. **安装侧接入**：现在 `verify` 是独立命令；要真正阻断未签名安装，需要把它接进发布/回滚脚本，并让回退包同样签名。
4. **旧包处理**：生产上正在运行的旧版本没有本渠道签名；回退时不能因为"验签失败"就拒绝恢复——需要一条明确规则（旧包按旧材料验证，或接受已知未签名状态并留痕）。
5. **公钥分发与吊销**：需要与包分离的公布渠道，否则同包替换无法被发现。

## 六、本轮没做

- 没有生成或保存任何正式私钥。
- 没有把新渠道接进 `release/` 现有脚本，也没有改动生产。
- 没有做 HSM / 双人控制的实操流程。
