缺的是**版本号、登记、收缩边界**。

## 2. 候选实现

新增两个模块（不替换既有机制）：

### 2.1 `manager/server/schemaver.py` —— 通用引擎（纯 sqlite3）

- **登记表** `schema_migrations(version PK, name, phase, state, required_reader, checksum,
  app_version, started_at, applied_at, duration_ms, detail)`；
- **`PRAGMA user_version`** 与「已 applied 的最高版本」同步（只前进、不回退）；
- **先扩后收的硬守卫**：`phase='expand'` 的步骤执行前后各取一次 schema 指纹
  （表→列、索引→定义），出现**删表/删列/删索引**立即 `SchemaDrift` 并登记 failed；
- **收缩闸门**：`phase='contract'` 默认**不执行**（登记 `deferred`）；即使
  `allow_contract=True` 也必须带 `contract_check` 且返回 ok，否则 `ContractRefused`；
- **大回填**：`backfill_batches()` 按 `schema_backfill_progress` 水位分批，每批独立
  commit，中断后从水位续跑；只有读到空批才置 `done=1`（被 `max_batches` 截停时保持 0）；
- **混合版本**：`assert_readable(conn, code_version)` —— 库的 `required_reader` 高于
  代码支持版本时拒绝启动（「新库 + 旧代码」）；反过来「旧代码读新库」由先扩后收保证；
- **漂移检测**：已 applied 步骤的代码指纹（`sha256(version|name|phase|co_code)`）变化
  视为原地改历史 → `SchemaDrift`（改实现必须升版本号）。

### 2.2 `manager/server/migrations.py` —— Manager 的版本计划

| 版本 | 名称 | 阶段 | 内容 |
|---|---|---|---|
| v1 | `baseline` | expand | 校验既有形状（17 张表 + 关键列）后登记，不执行 DDL |
| v2 | `log_query_indexes` | expand | K25 的两个索引 |
| v3 | `archive_runs` | expand | K24 归档台账 |
| v4 | `attribution_columns` | expand | K27 的 `request_logs.actual_platform/upstream_ref` |
| v90 | `contract_units_only` | contract | 候选收缩：units 列全量就位后删 REAL `credit`；默认 deferred，需 `settings['schema.approve.contract.v90']='1'` 人工批准 |

`CODE_SCHEMA_VERSION = 4` 表示**本代码能安全读取**的版本（不是已知最高版本）：
v90 执行后 `usage_daily.credit` 被删，而当前代码还在读写它，所以代码版本必须留在 4，
一旦有库真的执行了 v90，旧代码会被 `assert_readable` 拒绝启动而不是误读。

### 2.3 接入点（`db.py` 唯一改动，6 行）

```python
_conn.executescript(SCHEMA)
_migrate(_conn)
# K23：schema 版本登记 + expand 计划（既有 _MIGRATIONS 补列之后执行，不替代它）
from . import migrations as _migrations
try:
    _migrations.ensure(_conn)
    _migrations.schemaver.assert_readable(_conn, _migrations.CODE_SCHEMA_VERSION)
except _migrations.schemaver.MigrationError as exc:
    ...关闭半开连接...
    raise RuntimeError(f'数据库 schema 迁移失败：{exc}') from exc
```

`_MIGRATIONS` 与 `SCHEMA` 的既有内容**一行未改**（K01 追加的 `api_keys.source` 与
`legacymig.SCHEMA` 原样保留）。

## 3. 测试（`manager/server/tests/test_schema_versioning.py`，18 个用例）

| 场景（对应 K23 §5） | 断言 |
|---|---|
| 空库 | `user_version == 4`，v1..v4 applied，v90 deferred |
| 当前库 | expand 对象（两个索引、`archive_runs`、两列）都在 |
| 重复执行 | 第二次 `ensure()`：`applied=[]`、`deferred=[90]` |
| 上一版库（拆掉 v2..v4 对象 + `user_version=0`） | 升级后对象恢复、**数据不丢**、历史行新列为 NULL（不伪造） |
| 迁移中断重入 | 手工把 v2 置 `started` 且删索引 → 重连后索引重建、状态 applied |
| 失败步骤重试 | v3 置 failed → 重连后 applied |
| 旧代码读新 schema | 旧列 `SELECT` + 旧列 `INSERT` 在升级后仍可用 |
| 漂移 | 改 checksum → `SchemaDrift` |
| 收缩 | 无批准 → `ContractRefused`；有批准 → 执行且之后启动被 `ReaderTooOld` 拒绝 |
| 先扩后收 | 自定义 expand 步骤删表 → `SchemaDrift` + 登记 failed |
| 大回填 | 分批 2 行 + `max_batches=1` 截停 → 续跑不重不漏，完成后再次调用直接 skipped |

## 5. 回退

- 代码回退即可：删 `schemaver.py`/`migrations.py`，撤掉 `db.connect()` 里那 6 行。
  `schema_migrations`/`schema_backfill_progress` 成为无害残留（可 `DROP TABLE`）。
- **禁止**用「还原旧 DB 文件」来回退（会丢新增 key/用量/预算/审计，见审计包 §5 勘误表末行）。
- v2..v4 全部是 `CREATE TABLE/INDEX IF NOT EXISTS` / `ADD COLUMN`，旧代码读到它们只是
  多了列/表/索引，不影响读路径。

## 6. 未验证项

3. 混合版本（新旧代码同时跑同一库）未做双进程实测，只有 schema 兼容性论证 + 单进程测试。
