# K11 回退兼容性预检（未部署）

**问题**：现网回退脚本与当前拓扑不匹配——历史回滚指向已下线子域/8791/8792，部分备份早于
`auth_request` 安全修复。直接执行"看起来像备份"的文件，可能把入口回滚成更不安全或直接不可用。

**原则**：回退前先证明"目标版本与当前拓扑匹配"，而不是"文件名带 backup"。

## 回退前必须核对的 8 项

| # | 检查 | 判据 | 不通过时 |
|---|---|---|---|
| 1 | 目标版本 release_id | 与当前架构兼容（三平台分流 + auth_request） | 停止，另选目标 |
| 2 | 目标 Nginx 配置来源 | 含 `auth_request /__zh_session` 与安全头 | 停止（会重开匿名管理面） |
| 3 | 端口可达 | 7864 / 8795 / 8799 / 7863 / 8080 / 8081 的实际监听 | 停止（回退到死端口） |
| 4 | 软链目标 | `zhihui-console-current` 指向的 release 存在且完整 | 停止 |
| 5 | DB 兼容 | 目标代码能读当前 schema（或已备份 schema） | 走前滚，不覆盖 DB |
| 6 | 凭据 | 目标配置引用的 secret 文件仍存在（指纹一致） | 停止（不要为回退恢复已撤销凭据） |
| 7 | 备份时间 | 备份晚于最近一次安全修复 | 停止 |
| 8 | 回退影响面 | 只回退本次批次涉及组件 | 停止扩张 |

## 使用顺序

1. 只读跑 `preflight.sh`（不写、不 reload、不重启）；
2. 8 项全绿才允许进入 03 方案的短窗口流程；
3. 任何一项红 → 停止当前变更链，保留证据，不现场换方案。

## 边界

- 预检通过 ≠ 回退一定成功；回退后仍要按 03 方案记录 `T_admission`、`N_cut`、账本一致性。
- 常规回退只切代码与配置，**不覆盖已写入的新数据**；不兼容迁移走前滚或专门的数据恢复授权。
