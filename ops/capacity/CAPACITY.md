# K51 容量与高可用（设计，未启动）

## 现状

- 单机：3.7GB 内存、59GB 单盘（余 37GB）、同一主机跑 Manager/QTG/三个引擎/8081/容器；
- 故障域：**同一台机器、同一块盘、同一个内核**。两个进程"互为备份"不成立；
- 当前资源快照（20:15：available 1696MB）不等于容量极限，也没有性能曲线。

## SLO 基线（先测量，再承诺）

| 指标 | 初始目标 | 测量方法 |
|---|---|---|
| 有效推理请求可用性 | 99.5% | 外部探针 + 应用日志，按平台分开 |
| 计划变更导致的流式截断 | 0 | 发布记录里的 `N_cut`（K12 排空） |
| TTFB（首字节） | 按平台/模型分布统计 | 不把单个长尾当 p95 |
| 发布回退时间 | 实测后承诺 | `T_rollback` |

## 拆分条件（有数据才做）

1. 单机内存峰值 > 70% 持续一周；
2. 单盘 I/O 等待影响请求延迟；
3. 备份/恢复 RTO 无法在单机满足（K10 已证明异地未闭环）；
4. 发布期间必须有第二个活跃实例（K12 的双实例前提：schema/预算/调度/准入全部验证通过）。

满足条件后再考虑：拆机、引入共享准入（Redis 或 PG）、入口层多实例。
**不在本阶段**引入 K8s/服务网格/新框架。

## 当前可做的低成本改进

- 把备份目录与日志目录的容量阈值接进告警（K46）；
- WAL 定期 checkpoint 的耗时与磁盘预算（K23/K24）；
- 数据库单表增长趋势（request_logs/outcomes）月度统计，提前触发归档而不是等磁盘满。

## 明确不做

- 不复制 live DB 到新实例做"双写"；
- 不把"同机两个进程都 healthy"当成 HA；
- 不在没有容量数据时承诺多实例。
